mica: ublk zero copy

Progress report. Updated 2026-10-30 04:10 IST. Local lab only (one laptop, RustFS in Docker).

Now: the zero-copy build works and passes the data check. A clean A/B benchmark against the old build runs next. Then the crash tests on btrfs, XFS and ext4.

Context

mica serves a disk to Linux through ublk. ublk is a kernel driver that sends each block request (read, write, flush) to a program in user space. Here, that program is the mica daemon.

Before this change, each request tag had its own 512 KiB buffer in the daemon. A tag is one slot for a request in flight. One disk has 4 queues of 64 tags, so a disk can use up to 128 MiB of buffers. The kernel copies each request's data into this buffer or out of it. With many disks on one host, this memory is the main cost. The copy also costs CPU.

The change

The device now uses two ublk features:

  • UBLK_F_AUTO_BUF_REG: before a request reaches the daemon, the kernel registers the request's own pages as a fixed buffer in the queue's io_uring. The daemon reads and writes the pages in place with ReadFixed and WriteFixed. Nothing is copied.
  • UBLK_F_USER_COPY: the daemon can also read or write the request's pages through the char device /dev/ublkcN. This is one copy. mica uses it only on the slow paths, where the data is in memory anyway (S3 downloads, FUA writes).

If the kernel cannot register the pages (for example, when memory is low), it still sends the request with the flag UBLK_IO_F_NEED_REG_BUF. mica then serves the request through the copy path, and logs a count.

Kernel probe

The lab kernel is Linux 7.0.12. A small test program made a device with both flags. It checked five operations: ReadFixed from a file (two parts at different buffer offsets), ReadFixed from /dev/zero, WriteFixed to a file, and copies in both directions through /dev/ublkcN. All five returned the correct data. Kernels before 6.16 do not have UBLK_F_AUTO_BUF_REG, so they cannot run this build.

Correctness

A wrong buffer offset would corrupt data without an error. A new lab tool, datacheck.py, checks this. It sends random reads and writes of 4 KiB to 1 MiB at any 4 KiB offset, so requests cross chunk borders and touch parts that were never written. It also sends FUA writes, FLUSH, discard and write-zeroes. It compares every read with a model of the disk content. The disk has a 32 MiB cache and a 64 MiB pending-write budget, so many requests take the slow paths. After a detach and a reattach, a full read compares the whole disk again.

  • Old build: pass (3 × 3000 operations, 3 full reads).
  • First zero-copy build: failed with I/O errors. Under load, a read from /dev/zero can return fewer bytes than asked. io_uring retries short reads only for files and block devices, not for char devices. Fix: the queue thread now submits the rest of a short transfer again.
  • Fixed build: pass, same seeds.

First numbers (provisional)

8 disks at the same time. A Python load tool reads and writes each /dev/mica/* device with O_DIRECT. CPU is the daemon's user and system time, divided by the number of operations. The host was busy during this run (I/O pressure 28–43 %), so only large differences count. A clean back-to-back A/B follows.
