Test setup

The server is one VM in a Hetzner location. There are two S3 stores: RustFS in Docker on the same VM, and Hetzner Object Storage in the same location. A round trip to Hetzner Object Storage is 0.7 ms. The final binary ran the last 12 crash runs. The 24 crash runs and the soak tests before them used a build that differs only in its restart takeover, and that takeover went back to the code the earlier crash tests covered.

Writes to saved chunks

A saved chunk is a chunk that S3 has. Each saved chunk used to leave the local data files after each checkpoint, so its next write had to copy it back or download it. Now saved chunks stay local up to the disk's cache budget. The rewrite rows are 4 KiB random writes for 15 s, or 4 s for the rows inside the budget, with RustFS on the VM.

Context

mica serves a disk to Linux through ublk. ublk is a kernel driver that sends each block request (read, write, flush) to a program in user space. Here, that program is the mica daemon.

Before this change, each request tag had its own 512 KiB buffer in the daemon. A tag is one slot for a request in flight. One disk has 4 queues of 64 tags, so a disk can use up to 128 MiB of buffers. The kernel copies each request's data into this buffer or out of it. With many disks on one host, this memory is the main cost. The copy also costs CPU.

The change

The device now uses two ublk features:

  • UBLK_F_AUTO_BUF_REG: before a request reaches the daemon, the kernel registers the request's own pages as a fixed buffer in the queue's io_uring. The daemon reads and writes the pages in place with ReadFixed and WriteFixed. Nothing is copied.
  • UBLK_F_USER_COPY: the daemon can also read or write the request's pages through the char device /dev/ublkcN. This is one copy. mica uses it only on the slow paths, where the data is in memory anyway (S3 downloads, FUA writes, writes into chunks that are not local).
PathBeforeNow
Read of a local chunkfile → daemon buffer → requestfile → request (ReadFixed)

Read through S3 or the cacheVec → buffer → request (2 copies)Vec → request through /dev/ublkcN (1 copy)
FUA write, or chunk not localrequest → buffer → Vec (2 copies)request → Vec through /dev/ublkcN (1 copy)

If the kernel cannot register the pages (for example, when memory is low), it still sends the request with the flag UBLK_IO_F_NEED_REG_BUF. mica then serves the request through the copy path, and logs a count.

Kernel probe

A small test program made a device with both flags. It checked five operations: ReadFixed from a file (two parts at different buffer offsets), ReadFixed from /dev/zero, WriteFixed to a file, and copies in both directions through /dev/ublkcN. All five returned the correct data on the lab kernel (Fedora, Linux 7.0.12) and on a second server (Ubuntu, Linux 7.0.0). Kernels before 6.16 do not have UBLK_F_AUTO_BUF_REG, so they cannot run this build.

Correctness

A wrong buffer offset would corrupt data without an error. A new lab tool, datacheck.py, checks this. It sends random reads and writes of 4 KiB to 1 MiB at any 4 KiB offset, so requests cross chunk borders and touch parts that were never written. It also sends FUA writes, FLUSH, discard and write-zeroes. It compares every read with a model of the disk content. The disk has a 32 MiB cache and a 64 MiB pending-write budget, so many requests take the slow paths. After a detach and a reattach, a full read compares the whole disk again, and those reads come from S3.

  • Old build: pass (3 × 3000 operations, 4 full reads).
  • First zero-copy build: failed with I/O errors. Under load, a read from /dev/zero can return fewer bytes than asked. io_uring retries short reads only for files and block devices, not for char devices. Fix: the queue thread now submits the rest of a short transfer again.
  • Fixed build: pass, same seeds.

Crash tests

The crash test writes self-describing 4 KiB blocks to a 1 GiB disk, with FLUSH between some writes, and then breaks the node at a random time (2 to 20 s):

  • Power cut: the data folder sits on a device-mapper target that drops every later write. The daemon and the writer are killed, the ublk device is deleted, and the folder is mounted again as the SSD had it. The new daemon uploads what is left and detaches. Every block written before the last FLUSH must be there.
  • Daemon kill: only the daemon dies, mid-write. The new daemon takes over the same /dev/ublkbN, and the writer goes on. Every write that returned must be there, flushed or not. This also checks that a zero-copy device recovers.

A/B results

Setup. 8 disks at the same time. A Python tool reads and writes each /dev/mica/* device with O_DIRECT: 4 threads per disk for 1 MiB I/O, 8 threads per disk for 4 KiB I/O, 20 s per phase, over the first 256 MiB of each disk. All chunks are local, so this measures the queue thread, not S3. The disk limit of the lab is off. CPU is the daemon's user and system time. The two builds ran in turns, two rounds each, and each run started only when the host's I/O pressure was below 2 %. Numbers are the mean of the two rounds; the table below has each round.

The buffers were the memory. With the old build, RSS reaches about 700 MiB as soon as the first writes touch the buffers, and stays there. With zero copy, RSS stays near 30 MiB until the write phases start. After those phases, both builds grow by a similar amount: a checkpoint keeps chunk data in memory while it uploads. That part does not come from I/O buffers.

Large reads gain the most: each 1 MiB read was two copies of 1 MiB, and now it is one (page cache to request). The daemon used the same CPU in both builds, about 11.6 cores, but moved 2.3 times more data. At 4 KiB, the copy is small, so the CPU per request stays the same. 1 MiB writes use 5 % less CPU.

The fill phase uses about 12 % more CPU per write. These writes go to chunks that are not local yet, so they take the slow path: the queue thread copies the request out through /dev/ublkcN, then tokio writes it. The phase is short (2048 writes, about 1 s), so the figure is not precise. This path waits for the engine anyway; I will look at it again if a profile shows the copy.

Local write throughput moved in both directions in this test: 1 MiB writes were 1007 vs 791 MiB/s in round 1 and 633 vs 824 MiB/s in round 2 (old vs new). The SSD and the checkpoint uploads (RustFS writes to the same SSD) set these numbers. So a second test measured writes alone.

A lab finding: idle disks look like an I/O stall

The first try of the write test waited forever for a quiet host. With 8 disks attached and no load, /proc/pressure/io showed about 95 %, and vmstat showed 32 blocked tasks, but the SSD did almost no I/O. 32 is 8 disks × 4 queue threads. Each queue thread waits in io_uring_enter while requests are in flight (the ublk fetch commands), and the kernel counts that wait as iowait. Both builds do this. On a production host, each attached disk adds up to 4 blocked tasks, and I/O pressure and iowait look high. The load average does not change, because io_uring waits are interruptible. An earlier version of this page said that it did. io_uring has a flag to stop this (IORING_ENTER_NO_IOWAIT, Linux 6.15), but libublk makes the wait call, and the kernel uses iowait to raise the CPU clock for low-depth I/O. So this needs its own A/B.

Fix, merged (38f770d): the queue thread runs libublk's event loop with its own wait, the same in every way but with IORING_ENTER_NO_IOWAIT. With 8 idle disks: 0 blocked tasks and 0 % iowait (before: 32 and about 95 %). The data check passes. In the A/B above, single requests are the same or faster, and FLUSH p50 is the same. The mean of idle write + fdatasync was lower (833/s against 922/s, lower in 4 of 5 paired runs), from a heavier tail, but the spread between runs is wide. The fix improves host metrics, not speed, and adds a small unsafe wait loop. It is merged because host monitoring must not see a stall that does not exist. The write + fdatasync tail stays on the watch list.
