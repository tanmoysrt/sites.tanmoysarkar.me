Beacon telemetry map

Beacon is the incident manager and status page of Frappe Cloud V2. Each product sends its telemetry to the Datum of its region. Beacon reads Datum, matches each row to a resource, and turns failing rows into alerts, incidents and pages. This page shows what each product sends, how Beacon maps it, the services and their SLOs, and the 59 alert rules (Atlas 32, Cargo 15, Central 7, Pilot 5).

State of the open pull requests on 14 November 2026: datum#20, atlas#607, cargo#141, central#714, pilot#828. The contract is docs/telemetry.md in frappe/beacon.

How it fits

The problem: many products send data, but an alert must name one resource that a person can fix. So every product sends with one ID for each machine, and the resource sources list the same IDs.

  1. A producer collects a value and sends it to the Datum of its region with a token. The token holds the resource ID.
  2. Datum validates the request and writes the rows to ClickHouse. Materialized views copy new samples to samples_recent (2 days) and machine metrics to samples_5m (90 days).
  3. Each minute, Beacon reads the resource list of each region from Atlas. It keeps the resources, their parents and their status.
  4. Beacon runs each rule and each SLI on ClickHouse as the select-only beacon user. It keeps a row only when its resource_id is a known, checked resource.
  5. Beacon turns rows into alerts, alerts into incidents, and incidents into pages and chat posts. A person decides what the status page shows.

Parents and incident scope

A resource has a path, such as host, VM, proxy node. An alert joins an open incident whose scope covers it or a parent. A rule with scope_includes_descendants, such as a host that is down, opens an incident that covers everything under the host. So the VM and Pilot alerts that follow join that incident and do not page again. An incident of a resource with a parent waits 90 seconds before it pages, so the incident of the parent can take the alert first.

Services and SLOs

A service measures what customers feel. Each minute, Beacon runs the SLI query of each service in each region and stores good and valid counts. The SLO is the target over 30 days. A fast burn of the error budget pages.

ServiceOwnerGood meansSLOHow it counts
SitesPilotSites answer requests on the servers that run them.99.9%sort_order: 1 Pilot pings /api/method/ping on each site once a minute and sends pilot_sites by state. App request hooks run on the ping, so an app fault can count as bad. A sample more than 1 minute in the future comes from a wrong clock, and must not stay the newest value.
ServersAtlasServers that should run are available.99.9%sort_order: 2
NetworkingAtlasThe proxies pass requests to sites without errors of their own.99.9%sort_order: 3 A proxy error is a 5xx that the proxy made itself (origin proxy). A 5xx from the site's own code is good here.
Object StorageCargoS3 requests to object storage succeed.99.9%sort_order: 4 A 5xx answer is bad. 403 and 404 are normal S3 answers, so they are good. The Garage nodes send with their own resource IDs, but the resource list has one resource for Cargo, so the query reports the object storage of the region as the one reporter 'cargo'. The window is 3 minutes, so a counter that the Datum agent scrapes each minute has the 2 samples that an increase needs.

  • A responder acknowledges a call by pressing 1. An incident has one severity: the highest of its alerts.
  • When ClickHouse of a region fails 2 probes, Beacon raises one Critical "Region unreachable" alert, skips the rules of the region, and shows its services as Unknown.
  • A rule query error never resolves an alert. Beacon never publishes an incident. A person decides what customers see.
  • If Beacon stops, its external heartbeat stops, and the heartbeat service calls the team.
  • A postmortem is required for an incident that is public or Critical, that took more than 1 hour, or that a customer found first.

Customer or infrastructure

Two systems send alerts. Pilot tells the customer about one server or one site. Beacon tells the Frappe Cloud team when many customers share a problem, or when the platform fails. So Beacon does not add a rule for one site or one customer server.

What Pilot sends to the customer

Pilot sends each event to the webhooks of the customer. It also sends an alert by email, to the recipients set on the server, and to Central, which shows it to the customer. Central accepts only the event types that it defines.

Gaps

I checked each resource ID from the sender to the resource list, and each customer-facing part for a service and a paging rule.

Fixed: Pilot sent under the wrong resource ID central#714

Central gave the Pilot token the Central name of the server, not the Atlas VM name that Atlas lists. Beacon dropped every Pilot rule row, pilot-silent could never fire, and the Sites SLI had no reporters. Central now uses atlas_vm_id, and refuses a server that Atlas has not bound yet.

1. No check from outside of the customer entry points

All signals come from inside. If the web tier of Central or Atlas stops while its scheduler runs, no rule fires. Proposal: HTTP rules for the dashboard, the Central API, the Atlas API of each region, a site behind each proxy, and the status page.

2. No service for the dashboard and API

Central is customer-facing in every region, but it has no SLO. Central already sends API requests by status class. Proposal: a global "Dashboard and API" service.

3. No service for server actions

Create, resize, start and stop have durations in Datum, but only Insights reads them. Proposal: a "Server actions" service with a time limit for each action.

4. Grove is not covered

Grove boxes send as grove:<machine>, and no resource source lists them. Beacon drops their rows. Decide: add a Grove resource source and rules, or leave Grove out of Beacon.

5. The "Telemetry IDs" source has no user

Beacon can map a second ID through a Central list, but Central does not serve it, and every sender now uses its Atlas name. Proposal: remove it from Beacon. This changes a DocType, so it needs a mockup first.

6. Rule resource types are labels that do not match the registry

5 rules say Machine, and Central and some Pilot rules say Region or Server. Beacon does not read them for matching, so nothing breaks. Proposal: use the registry types, or remove the line.

7. Certificate alerts do not reach Central

Pilot sends certificate_expiry and certificate_failed only to webhooks and email, because Central defines no event type for them. A customer without webhooks or email recipients does not learn that a site certificate will expire. Proposal: add both event types in Central and map them in Pilot.
