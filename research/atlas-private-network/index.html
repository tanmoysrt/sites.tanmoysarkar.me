Atlas private host network

Atlas manages the bare-metal hosts that run customer virtual machines (VMs). This note explains how Atlas now reaches each host only through an encrypted tunnel, and what a test on two cloud providers found.

The problem

Atlas is the control plane. It sends commands to each host. Before this change, each host accepted those commands on its public internet address.

Three services were open to the internet on every host:

  • SSH on port 22. Atlas uses SSH to install and repair the host.
  • The Metal API on port 9000. Metal is the agent on each host that starts and stops VMs.
  • WireGuard on port 51820. WireGuard is an encrypted network tunnel. Hosts use it to connect to each other.

Each open port is a target for attacks. Atlas must also know the public address of every host. The goal is simple: a host accepts no management traffic on its public address.

The simple case: one Atlas, one host

The hosts already have a WireGuard interface, wg0, for host-to-host traffic. The change adds Atlas as one more WireGuard peer of each host. A peer is one end of a WireGuard tunnel.

Atlas then sends SSH and Metal API requests to the host wg0 address. The host firewall drops these requests on all other interfaces.

Addresses

Each region has its own address space. Atlas gives each host and each VM an IPv6 address from that space.

fdab:<region>:<host>
The wg0 address of a host.
fdaa:<region>:<tenant>::<vm>
The mesh address of a VM. A tenant is one customer account. Tenant 0 holds the regional services, such as the HTTP proxy.
fdaa:<region>::ffff:ffff:ffff:ffff
The Atlas address. It is a tenant-0 VM address with the last VM number, so no real VM can take it.

Atlas uses a VM address, not a host address, on purpose. The mesh treats an fdab sender as a host and trusts it to carry VM traffic. Atlas does not need that trust. With a tenant-0 address, Atlas cannot send traffic into a customer network. Only tenant-0 VMs can reach Atlas.

How Atlas gets inside the provider network

Each host has a private network address at the cloud provider. Atlas connects to that private address, not to the public one. So Atlas must have a path into the provider private network.

Production

In production, Atlas runs in its own VM, the Atlas VM, on one host of the region. The parent host masquerades the Atlas VM traffic to the private network. Masquerade is a form of network address translation (NAT): the parent host replaces the VM source address with its own private address. Other hosts then see a normal private-network sender.

Development

A developer runs Atlas on a laptop, outside the provider network. The laptop uses a gateway. The gateway is the same Atlas VM program in a gateway mode. It runs on one host and forwards WireGuard packets to the private network.

The gateway uses the public address of its host, port 51821. It needs no extra public IPv4 address.

Trace: Atlas opens a shell in a VM

A VM has no public address for SSH. Atlas reaches it through its host in four steps:

  1. Atlas connects to the host wg0 address over atlas0.
  2. The host firewall accepts SSH because the source is the Atlas address on wg0.
  3. On the host, SSH runs nc inside the network namespace of the VM. A network namespace is the isolated network stack that holds one VM.
  4. nc connects to port 22 of the guest. The SSH session runs through that pipe.
ssh -o ProxyCommand="ssh root@fdab:<region>:<host> ip netns exec metal-<vm> nc 172.16.0.2 22" root@<vm>

Host firewall

Each host loads one input firewall table at boot. It controls traffic to the host itself. It does not change VM traffic.

Traffic to the hostAccepted from
WireGuardThe provider private network, and the local Atlas VM
SSH and the Metal APIThe Atlas address on wg0
VM migrationOther host addresses on wg0
SSH for recoveryThe provider private network
ICMP, DHCP, and repliesAny address

A separate rule drops VM packets to the provider private network. A VM can reach the internet, but it cannot reach the hosts.

Evidence: an end-to-end test on AWS

The design first ran on three bare-metal hosts at one provider. Then it ran on a second provider, AWS, with two virtual hosts that have nested virtualization. Atlas created the first host. The second host was started by hand and then added with the new Import Server action.

What failed first

The test found these faults. Each one is fixed.

Atlas did not list tenant-0 VMs

Host names are UUIDs, so the database stores the VM host field in a native UUID column. The query filter "field is set" compares that column with an empty string. That comparison never matches, so the result was always empty. The query now omits that filter.

The gateway lost NAT on AWS

The masquerade rule named one output interface. It took the interface from the route to one probe address. On AWS, traffic to other hosts uses a second network interface, so the rule did not match, and AWS dropped the packets. The rule now matches only the private network range, on any interface.

The Atlas VM did not start after a restart

Firecracker, the VM monitor, does not start when its old API socket file exists. Also, the service was not enabled at boot. The service now deletes the socket file first, and setup enables it.

The Atlas VM kernel had no TUN device

The VM needs TUN for a user-space WireGuard. The first kernel did not have it. The Atlas VM now uses the same Ubuntu kernel as other VMs.

A single-interface host did not isolate VMs

The drop rule named the private interface. On a host with one interface for both networks, the rule was skipped. The rule now matches the private network range on any interface.

Limits and next steps

  • The first host of a new region still uses public SSH during its setup. The firewall closes it at the end of the setup.
  • The AWS test did not cover the HTTP proxy, the object store service, the IPv6 router, or the production Atlas VM.
  • A new Atlas key needs console access to every host. Keep a backup of the key.
  • One development laptop connects to one region at a time, because two test regions use the same private range.

Status: the change is complete on a feature branch and waits for review.
