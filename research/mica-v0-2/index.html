mica v0.2: how it works and how fast it is

mica gives a VM or a container a disk whose data lives in an S3 bucket. The disk runs at local SSD speed, and it can move to another machine in a few seconds. This page explains how mica does that, and shows what it measures on a host and in Firecracker.

Why a disk in S3

A sandbox is a small VM or a container that runs one user's work. A platform stops idle sandboxes and starts them again when the user comes back. If the disk is on the SSD of one machine, the sandbox can start only on that machine. If that machine is full or down, the user waits.

mica keeps the shared copy of each disk in S3, and uses the local SSD as a cache. Any machine can attach the disk. The guest reads and writes at SSD speed, because writes go to the SSD first, and mica uploads changes in the background.

Three rules hold in every part of mica:

  1. A write never waits for S3. Writes and FLUSH go to the local SSD only.
  2. A read never waits for data that it does not need. An attach copies nothing. Prefetch runs behind the guest's reads.
  3. After a detach, S3 has everything. Then the disk can attach on any machine.

The parts

A machine runs one mica daemon. For each attached disk, the daemon makes a block device, /dev/mica/<disk>. It uses ublk: a Linux driver that sends each block request of a device to a program in user space. A VM, a container or the host uses the device like any other disk.

The local SSD holds two kinds of data:

  • Local chunks of each disk, in sparse data files. A data file covers 1 GiB of the disk, and each chunk sits at its own offset. Some local chunks are not in S3 yet.
  • The cache: clean chunks that S3 also has. All disks on the machine share it, so a base image downloads once.

A disk in S3

mica splits each disk into chunks of one size, 256 KiB by default (64 KiB to 4 MiB). A 100 GiB disk has 409,600 chunks. A chunk is stored as an S3 object. Its key is the SHA-256 of its content, and its body is a zstd frame. So:

  • Two equal chunks are one object. Disks made from one image share their chunks.
  • mica checks each downloaded chunk against its key.
  • An all-zero chunk is not stored. A new disk stores nothing.

A page lists the hashes of 1,024 chunks (256 MiB of disk). A root lists the hashes of all pages of a disk: 12.5 KiB for 100 GiB. The head of a disk names its current root. Pages and roots are immutable and named by their hash, so a change writes only new pages, a new root and the head.

chunks/<xx>/<chunk hash>     one chunk, zstd, immutable
pages/<xx>/<page hash>       the hashes of 1,024 chunks, immutable
manifests/<root hash>        one root: the hash of each page
disks/<disk>/head            the current root and the read profile
disks/<disk>/attached        the machine that owns the disk now
snapshots/<name>             a named root

Writes and FLUSH

A guest write goes into the disk's data file, at the chunk's offset, and returns. It does not sync. If the chunk was not local yet and the write covers only part of it, mica first copies the chunk's content from the cache into the data file. On XFS and btrfs, that copy is a reflink. On ext4 it is a copy. A chunk of zeros needs no copy, because every range that is not local is a hole.

Most writes never leave the ublk queue thread: an io_uring write into the data file, and an update in memory. Writes to new chunks, FUA writes and FLUSH go to the disk engine.

A FLUSH is the guest's request for durability, for example at fsync or at a journal commit. On FLUSH, mica:

  1. Syncs the data files written since the last FLUSH.
  2. Appends the chunks that became local to the dirty log, and syncs it. The dirty log lists the local chunks of a disk.

The order matters: the log never lists a chunk whose data a power cut can lose. Most FLUSHes are one fdatasync. A FLUSH never touches S3.

Linux starts writeback late: after 10% of free memory is dirty, or after 30 s. So after each 16 MiB of writes, mica starts writeback of the data files itself, with sync_file_range. Then a FLUSH after a large write finds little left to write.

A write that returned also survives a crash of the daemon before any FLUSH. The kernel's page cache keeps the data, and a bitmap in /run (recent) lists the chunks that became local since their last FLUSH. /run is a tmpfs: it survives a daemon crash, as the page cache does, and a reboot clears it, as it clears the page cache.

One local layout for every filesystem

mica needs only plain Linux file calls: sparse files, fdatasync, copy_file_range and hole punching. It works on ext4, XFS and btrfs. A reflink only makes the first copy of a chunk cheaper.

Reads

mica splits a read by chunk. For each part, the first match wins:

  1. A local chunk: read the data file.
  2. A zero chunk: return zeros.
  3. A chunk in the cache: read the cache file.
  4. Else: get the chunk from S3, decompress it, check its hash, store it in the cache, then read it.

Many reads that miss the same chunk share one GET. Steps 1 to 3 run on the queue thread with io_uring, with no lock wait and no other thread.

Three kinds of download run behind the guest's reads, in this order of priority:

  • Reads by the guest come first.
  • Likely reads. When reads follow each other, mica fetches the next chunks: 1 MiB ahead first, then up to 8 MiB (read-ahead). At attach, mica also fetches the read profile: the chunks that the guest read first in its last session, up to 64 MiB.
  • Fill. When the link has nothing else to do, mica downloads the rest of the disk, in disk order. Then every read is local.

Checkpoints

A checkpoint uploads the local chunks that S3 does not have, then commits a new root. It starts 30 s after the last one, or earlier when 512 MiB of changes wait. It also runs at detach and at snapshot.

  1. Take the list of unsaved chunks. Later changes go to the next checkpoint, so a busy writer cannot make a checkpoint last for ever.
  2. For each chunk, read it into memory and PUT it. Up to 64 MiB are in flight. The guest keeps writing in place.
  3. PUT the changed pages and the new root.
  4. Check that this machine still owns the disk. Then write the head.

A chunk stays local after its upload, so the next write to it costs nothing extra. Saved chunks leave the data files only when local data passes its limit, and at detach. They go into the cache.

Garbage collection (GC) deletes objects that no root needs and that are older than 24 hours. A GC can see a new upload as old only if it runs while the PUT ends. So during an upload, mica reads the GC state once a second. Until a check shows that no GC ran, the first write to an uploaded chunk keeps a copy of the uploaded content. If a GC ran, the checkpoint checks every committed chunk and page, and uploads a deleted one again.

Moving a disk

This is the main use of mica. A sandbox stops on machine A and starts on machine B.

Only one machine may write a disk. With S3 conditional writes, the claim is one atomic create: a PUT with If-None-Match: *. Of two machines that claim at the same moment, only one creates the marker. RustFS, AWS S3, R2 and MinIO support this. For a store without it, such as Garage, mica writes a claim, waits 1 s and reads it back. Then an attach takes about 1 s.

Crash safety

  • After a FLUSH returns, its writes survive a crash of mica and a power cut.
  • After a write returns, it survives a crash of mica, also without a FLUSH. The daemon restarts with ublk user recovery: the kernel holds the device's I/O, and the new daemon takes the device over. The guest sees a pause of about 1 s.
  • After a detach, S3 has all data, and the disk can attach anywhere.

A test harness checks the first two promises. A writer fills a 256 MiB area with 4 KiB blocks that each name their block, their write and a CRC. It FLUSHes now and then. At a random moment, a device-mapper target under the data folder drops every write: a power cut. Then the daemon dies, and the folder is mounted again as after a reboot. Every block must hold its last write before the last completed FLUSH, or a later one.

Memory snapshots

A Firecracker memory snapshot stores the guest RAM in a file. A restore starts a new Firecracker from that file. The guest continues without a boot. In the test, the guest runs an HTTP server that holds 384 MiB of random data in RAM, and each GET returns a hash of all of it. So the first answer needs all app memory back, and the hash proves that it is correct. Every restore returned the correct hash.

The memory file (2 GiB) is an ordinary file on a second mica disk. mica stores it in 307 MiB: zero chunks are not stored, and the rest is compressed. Each restore uses a new clone of the root disk's snapshot.

Warm, ssh answers 0.23 s after the snapshot load. A warm boot needs 2.28 s from attach until ssh. A cold restore is limited by bytes: the app's 384 MiB of random data does not compress, and alone it takes about 4 s on a 95 MiB/s link. A restore that touches less memory starts faster.

mica uses Firecracker's File backend: the kernel loads each page from the memory file when the guest first uses it. A test with a userfaultfd handler, which installs a recorded set of pages first, was no faster cold (4.77 s against 4.82 s, both limited by the link), and slower warm on demand (3.19 s against 0.77 s). So mica stays a plain block device, not tied to Firecracker. VMs that restore from one snapshot on one machine share mica's chunk cache, so each chunk downloads once.

Limits

  • The link sets the cold speed. mica can change the order of downloads, not the bytes that the guest needs. Compression and small chunks lower the bytes.
  • Firecracker does not pass discard to the disk. Space that a guest frees stays in mica and in S3. In the guest fill test, 4 GiB of deleted data uploaded.
  • An attach takes about 1 s without conditional writes, for example on Garage.
  • Writes during a large upload share the SSD with the upload and with its writeback.
  • Two GC gaps. A page that GC deletes between a commit and its repair is lost if the machine loses power in that window. Without conditional writes, two GCs at the same time can hide each other.
  • One lab machine. S3 runs on the same SSD as mica, and the machine also ran other work, so tail latencies here are worse than on a dedicated node.
