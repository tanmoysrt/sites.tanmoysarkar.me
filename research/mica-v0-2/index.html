mica v0.2: how it works and how fast it is

mica gives a VM or a container a disk whose data lives in an S3 bucket. The disk runs at local SSD speed, and it can move to another machine in a few seconds. This page explains how, and shows what mica measures on a host and in Firecracker.

01Why a disk in S3

A sandbox is a small VM or container that runs one user's work. A platform stops idle sandboxes, and starts them again when the user comes back. If the disk is on the SSD of one machine, the sandbox can start only on that machine. If that machine is full or down, the user waits.

mica keeps the shared copy of each disk in S3, and uses the local SSD as a cache. Any machine can attach the disk. Three rules hold in every part of mica:

  1. A write never waits for S3. Writes and FLUSH go to the local SSD only.
  2. A read never waits for data that it does not need. An attach copies nothing. Prefetch runs behind the guest's reads.
  3. After a detach, S3 has everything. Then any machine can attach the disk.

02Where mica sits

mica is a program in user space, not a kernel module. It uses ublk, a Linux driver that makes a block device whose requests go to a user-space program. For each attached disk, mica asks ublk for a device: /dev/ublkb0, with the link /dev/mica/<disk>. To the rest of the system it is a normal disk. Firecracker, QEMU, a container or a host mount can use it.

The diagram follows one 4 KiB write from an app in a Firecracker guest to the SSD.

  1. In the guest, the app writes a file. ext4 turns it into a block write, and the virtio-blk driver puts it on a virtqueue that Firecracker shares with the guest.
  2. Firecracker takes the request and writes it to /dev/mica/disk on the host, with io_uring.
  3. The host kernel sends the block request to the ublk driver.
  4. The ublk driver hands the request to mica. Each mica queue thread keeps io_uring commands waiting on /dev/ublkc0. The driver completes one with the request: operation, offset and length. For a write, the data is copied into the queue thread's buffer.
  5. The queue thread finds the chunk, and writes the data into the disk's data file with io_uring. Then it tells ublk that the request is done, in the same call that waits for the next request.
  6. The host filesystem keeps the data in the page cache. It goes to the SSD with writeback, and for sure at the next FLUSH.
  7. Later, the disk engine uploads changed chunks to S3. It also downloads a chunk when a read needs one that is not local.

The queue thread serves most requests alone: reads and writes of chunks that are local, with no lock wait and no other thread. A request that needs more goes to the disk engine, on a tokio runtime in the same process. Examples: the first write to a chunk that is not local, a read that misses the cache, a FLUSH, a FUA write. Each device has one queue thread per CPU, up to 4.

If the mica daemon stops, the kernel keeps the device and holds its requests. The next daemon takes the device over with ublk user recovery, and the guest sees a pause of about 1 s.

03From a disk to chunks

To mica, a disk is a row of bytes, cut into chunks of one size. The size is set when the disk is made: 256 KiB by default, from 64 KiB to 4 MiB. A 20 GiB disk has 81,920 chunks. A chunk is the unit of everything that follows: the local data, the upload, the download and the dedup.

Take a 4 KiB write at byte 1,056,768 of a 20 GiB disk. mica finds its place with three divisions:

Chunk
1,056,768 ÷ 262,144 = 4, rest 8,192: chunk 4, 8 KiB into it
Data file
1,056,768 ÷ 1 GiB = 0: dirty/data-0, at byte 1,056,768
Page
chunk 4 ÷ 1,024 = 0, rest 4: page 0, slot 4

On the local SSD, a disk has sparse data files, one for each GiB of the disk. Each chunk sits at its own disk offset, so a write needs no lookup table: it goes to the same offset in the data file. A data file uses space only for the chunks the guest wrote.

In S3, a chunk is an immutable object. Its key is the SHA-256 of its content, and its body is a zstd frame. So:

  • Two equal chunks are one object. Disks made from one image share their chunks.
  • mica checks each download against its key.
  • An all-zero chunk is not stored. A new disk stores nothing.

A request that crosses chunk borders is split. A 512 KiB read at byte 200 KiB covers chunks 0, 1 and 2, and each part is served on its own.

Pages, roots and snapshots

A page lists the hashes of 1,024 chunks: 32 KiB, for 256 MiB of disk. A root lists the hashes of all pages of a disk: 12.5 KiB for 100 GiB. The head of a disk names its current root. Pages and roots are also named by their hash. So a change writes only the new pages, a new root and the head, and everything else is shared.

chunks/<xx>/<chunk hash>    one chunk, zstd, immutable
pages/<xx>/<page hash>      the hashes of 1,024 chunks
manifests/<root hash>       one root: the hash of each page
disks/<disk>/head           the current root and the read profile
disks/<disk>/attached       the machine that owns the disk now
snapshots/<name>            a named root

04Writes and FLUSH

A guest write goes into the data file and returns. It does not sync. If the chunk is not local yet and the write covers only part of it, mica first copies the chunk from the cache into the data file. On XFS and btrfs that copy is a reflink. On ext4 it is a real copy. A chunk of zeros needs no copy, because every range that is not local is a hole.

A FLUSH is the guest's request for durability, for example at fsync or a journal commit. On FLUSH, mica syncs the data files written since the last FLUSH. Then it appends the chunks that became local to the dirty log, the list of a disk's local chunks, and syncs the log. In that order, the log never lists a chunk whose data a power cut can lose.

Linux starts writeback late: after 10% of free memory is dirty, or after 30 s. So after each 16 MiB of writes, mica starts writeback itself, with sync_file_range. A FLUSH after a large write then finds little left to write.

A write that returned also survives a crash of the daemon before any FLUSH. The page cache keeps its data, and a bitmap in /run lists the chunks that became local since their last FLUSH. /run is a tmpfs: it survives a crash of mica, as the page cache does, and a reboot clears it, as it clears the page cache.

mica needs only plain Linux file calls: sparse files, fdatasync, copy_file_range and hole punching. It works on ext4, XFS and btrfs.

05Reads

For each chunk of a read, the first match wins:

  1. A local chunk: read the data file.
  2. A zero chunk: return zeros.
  3. A chunk in the cache: read the cache file. The cache holds clean chunks that S3 also has, and all disks on the machine share it.
  4. Otherwise: get the chunk from S3, decompress it, check its hash, store it in the cache, and read it.

Many reads that miss one chunk share one GET. Behind the guest's reads, three kinds of download keep the link busy, in this order:

  • Reads by the guest always come first.
  • Likely reads. When reads follow each other, mica fetches ahead: 1 MiB first, then up to 8 MiB. At attach it also fetches the read profile: the chunks that the guest read first in its last session, up to 64 MiB.
  • The fill. When the link has nothing else to do, mica downloads the rest of the disk, in disk order. It starts at attach, also when the guest reads nothing. Then every read is local.

06Checkpoints

A checkpoint uploads the local chunks that S3 does not have, and commits a new root. It starts 30 s after the last one, or earlier when 512 MiB of changes wait. It also runs at detach and at snapshot.

  1. Take the list of unsaved chunks. Later changes go to the next checkpoint, so a busy writer cannot make a checkpoint last for ever.
  2. For each chunk, read it into memory and PUT it, with up to 64 MiB in flight. The guest keeps writing in place.
  3. PUT the changed pages and the new root.
  4. Check that this machine still owns the disk. Then write the head.

A chunk stays local after its upload, so the next write to it costs nothing extra. Saved chunks leave the data files only when local data passes its limit, and at detach. They go into the cache.

Garbage collection (GC) deletes objects that no root needs and that are older than 24 hours. A GC can see a new upload as old only if it runs while the PUT ends. So during an upload, mica reads the GC state once a second. Until a check shows that no GC ran, the first write to an uploaded chunk keeps a copy of the uploaded content. If a GC ran, the checkpoint checks every committed chunk and page, and uploads a deleted one again.

07Moving a disk

This is the main use of mica: a sandbox stops on machine A and starts on machine B.

Only one machine may write a disk. With S3 conditional writes, the claim is one atomic create: a PUT with If-None-Match: *. Of two machines that claim at the same moment, only one creates the marker. RustFS, AWS S3, R2 and MinIO support this. For a store without it, such as Garage, mica writes a claim, waits 1 s and reads it back, so an attach takes about 1 s.

08Crash safety

  • After a FLUSH returns, its writes survive a crash of mica and a power cut.
  • After a write returns, it survives a crash of mica, also without a FLUSH.
  • After a detach, S3 has all data, and any machine can attach the disk.

A test harness checks the first two. A writer fills a 256 MiB area with 4 KiB blocks that each name their block, their write and a CRC, and FLUSHes now and then. At a random moment, a device-mapper target under the data folder drops every write: a power cut. Then the daemon dies, and the folder is mounted again, as after a reboot. Every block must hold its last write before the last completed FLUSH, or a later one.

12Memory snapshots

A Firecracker memory snapshot stores the guest RAM in a file. A restore starts a new Firecracker from that file, and the guest continues without a boot. In the test, the guest runs an HTTP server that holds 384 MiB of random data in RAM, and each GET returns a hash of all of it. So the first answer needs all app memory back, and the hash proves that it is correct. Every restore returned the correct hash.

The memory file (2 GiB) is an ordinary file on a second mica disk. mica stores it in 307 MiB: zero chunks are not stored, and the rest is compressed. Each restore uses a new clone of the root disk's snapshot.

Warm, ssh answers 0.23 s after the snapshot load. A warm boot needs 2.28 s from attach until ssh. A cold restore is limited by bytes: the app's 384 MiB of random data does not compress, and alone it takes about 4 s on a 95 MiB/s link. A restore that touches less memory starts faster.

mica uses Firecracker's File backend: the kernel loads each page from the memory file when the guest first uses it. A userfaultfd handler that installs a recorded set of pages first was no faster cold (4.77 s against 4.82 s, both limited by the link), and slower warm on demand (3.19 s against 0.77 s). So mica stays a plain block device, not tied to Firecracker. VMs that restore from one snapshot on one machine share mica's chunk cache, so each chunk downloads once.

13Limits

  • The link sets the cold speed. mica can change the order of downloads, not the bytes that the guest needs. Compression and small chunks lower the bytes.
  • Firecracker does not pass discard to the disk. Space that a guest frees stays in mica and in S3. In the guest fill test, 4 GiB of deleted data uploaded.
  • The cache evicts by last use, from any disk. An attached disk can lose cached chunks, and the fill stops once the cache is 90% full. A mode that keeps attached disks fully local is planned.
  • An attach takes about 1 s without conditional writes, for example on Garage.
  • Writes during a large upload share the SSD with the upload and its writeback.
  • Two GC gaps. A page that GC deletes between a commit and its repair is lost if the machine loses power in that window. Without conditional writes, two GCs at the same time can hide each other.
  • One lab machine. S3 runs on the same SSD as mica, and the machine also ran other work, so tail latencies here are worse than on a dedicated node.
