Beacon on staging: from Unknown to a tested alert path

Report of the night of 14 to 15 November 2026. Beacon is the incident manager, SLO panel and status page of Frappe Cloud V2. It reads telemetry from Datum, the regional ClickHouse store. This note records why the staging status page showed Unknown, what changed, how the full alert path was tested, and what is still open.

The starting point

A Beacon service has a status only when its query finds valid events. When a query finds none, the status is Unknown. This is on purpose: grey "Status unavailable" is more honest than an old green.

At the start, four of six services on staging were Unknown. Each one had a different cause:

ServiceWhat it readsWhy it was Unknown
SitesUptime pings that each Pilot sendsNo Pilot sent telemetry. The Pilots were old, and Central had no Datum address to give them.
Object StorageS3 requests that Garage countsStaging has almost no S3 traffic, so most 3-minute windows had no request.
Dashboard and APIRequest counts that Central sendsCentral could not reach Datum.
Server actionsServer actions that finished in the last hourCentral could not reach Datum, and staging has few actions.

Who can reach Datum

The telemetry host reports one address to Central: an internal- name on the WireGuard mesh. Central gives that address to each Pilot. Two problems were in this path.

  • Tenant VMs could not reach the mesh name. A request from a Pilot VM to the internal name got no answer. Atlas lets a tenant VM reach a platform VM only when the platform VM is privileged. The Datum host VM and the S3 gateway VM were not. Both are now privileged, and the same request answers 200.
  • Central is not on the mesh. Central runs outside the region, so the internal name never works for it. Central #725 makes Central send its own telemetry to https://telemetry-svc.<region domain>. It still sends nothing while the telemetry host does not report itself Available. Pilots keep the internal address.
  • The Cargo webhooks had an old secret. Cargo copies the Central webhook secret into its webhooks only when it sets them up. After Cargo was enrolled with the staging Central again, the two webhooks were rebuilt, and Central recorded the telemetry and storage services.

Testing the alert path

A chat webhook can show whether Beacon sends notifications, but only if someone receives them. A small local request logger was put behind a temporary tunnel and set as the Beacon chat webhook. Then one real failure was made on purpose: the Pilot monitor on a VM with no sites was stopped.

A bug the test found

The first time the alert fired, Beacon muted it. The reason was "held removal". Small staging Pilot VMs sleep after 10 idle minutes, and Atlas then lists them as Suspended. Four VMs fell asleep in the same minute that two builders were terminated. That was 6 of 41 resources, more than the 10% limit, so Beacon held the whole change for an admin. A held resource mutes its alerts.

The limit is there to stop a broken resource list from removing everything. A Suspended VM is not a removal: the source reports it on purpose, and the VM comes back. Beacon #1 counts only terminations and missing resources. Without it, every group of sleeping trial servers in production would mute real alerts.

A second bug: the wrong name on a new server

The probe server sent its site samples, but Beacon dropped them. Datum had them under the Central name of the server, not the Atlas name of its VM. Central builds the boot settings of a new server before Atlas creates the VM, so the first Datum token could only name the Central server. Beacon matches telemetry by the Atlas name, and the first token lasts 7 days. Central #726 gives the endpoint at boot and lets Pilot fetch the token later. Pilot already treats a missing token as one to fetch.

Open items

  • Object storage backup. The staging cluster has no offsite bucket for its metadata backups, so the backup alert is correct. It needs bucket credentials from the team. Production needs the same setting.
  • Merge and revert. After Cargo #144 merges, set the staging Cargo definition source back to develop. After Beacon #1 merges, deploy Beacon on staging; the bench has the patch in place now.
  • Temporary test parts. The chat webhook points to a temporary tunnel. Replace it with a real channel, and add responders.
  • Admin API key. The probe timer uses a new API secret of the staging Central administrator. Any old use of that key stops working.

Checklist for production

  1. Make the Datum host VM and the S3 gateway VM privileged. From one tenant VM, check that the internal telemetry name answers 200 on /health.
  2. Deploy Central #725. Check that Datum has central_requests samples from Central.
  3. After Enroll Cargo, rebuild the two Cargo webhooks and send each once. Check that the request log says "recorded".
  4. Update the Pilots and run pilot setup telemetry. Check pilot_info and pilot_sites in Datum.
  5. Merge Central #726, Cargo #144, Cargo #145 and Beacon #1 before go-live.
  6. Set an offsite metadata backup bucket on the object storage cluster.
