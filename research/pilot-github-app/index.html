Architecture note · Proposed design

Connect GitHub once.
Deploy with clear limits.

Let Central manage the GitHub App. Let Pilot receive short-lived repository credentials. Keep clone and fetch traffic between Pilot and GitHub.

Scope: Central-managed PilotFirst release: read-only repository access

Pilot manages Frappe apps from Git repositories. A personal access token (PAT) works today, but users must create and maintain it. This proposal replaces that setup step with a GitHub connection flow. It explains where access belongs and what happens when a service fails.

01

The recommended design

Use one GitHub App for managed Pilot resources. Central is the credential broker: it checks access and issues limited credentials. A deployment grant is a saved rule that allows one Pilot resource to read selected repositories.

Assumptions: Central knows the team and the Pilot resource. It can verify who may manage them. The host is trusted to receive a temporary read credential.

This design reduces secret distribution and avoids routing Git data through Central. It adds a Central dependency when Pilot needs a new credential. It is a proposed balance, not a measured availability claim.

02

Start with what exists

Verified in Pilot

  • One credential record per bench lives in .bench.git.info.
  • The Git API validates a PAT through GET /user. It browses repositories through GET /user/repos.
  • Git commands receive credentials through environment configuration. Remote URLs remain free of credentials.
  • CentralClient uses a host token from instance metadata.

Proposed additions

  • Verified GitHub connections and explicit repository grants in Central.
  • One Central browser callback.
  • A shared credential resolver for API requests, CLI commands, and workers.
  • Expiry-aware tokens restricted to approved repositories.

The Central implementation has not been inspected. Its GitHub integration, team permissions, resource mapping, and secret storage must be checked before implementation. No end-to-end flow or availability target has been tested.

A bench path is a configuration scope. It is not a host security boundary. Pilot benches on one host share an operating-system user. Central must derive the allowed resource from verified host credentials and its own records.

04

Trace one account connection

A team wants to deploy one private app. An authorized person must approve both the Pilot target and the GitHub source. The flow must support an App that is already installed.

01

Start from the target Pilot resource

Pilot checks the local session. Central creates a short-lived, single-use connection attempt for a verified target resource.

A supplied team ID or return URL cannot change the target.
  1. Authenticate the human in Central. The host token proves the host identity. It does not prove who the browser user is. Central checks that the person can manage the target resource.
  2. Authorize the GitHub user. Use a fixed Central callback, random state, and PKCE. PKCE binds the code exchange to the flow that started it. Central exchanges the code on the backend. [2]
  3. Choose an installation. An installation is the App's approved access to a GitHub account. Use GET /user/installations and GET /user/installations/{id}/repositories. If needed, install the App, then resume the saved attempt. [3]
  4. Check delegation rights. Seeing a repository is not enough to grant ongoing deployment access. Define a policy, such as repository administration rights or explicit approval by a designated organization administrator. Confirm the policy and required permissions before building.
  5. Save the grant once. Bind the team, target resource, installation, and selected repository IDs. Verify callback values against GitHub. Recheck permissions before final save. Repeated callbacks return the existing result.

Bind the attempt to the initiating session and resource. Protect the start action from cross-site request forgery. Use an approved return address. Pilot polls through its backend. No GitHub credential appears in the browser return URL.

05

Trace one deployment

A user token represents a person. Its access is limited by both the user and the App. An installation token represents an approved App installation. Use user authorization for discovery and actions attributed to that person. Use installation authorization for an explicitly approved deployment grant. [2] [4]

  1. A worker loads the repository reference when it starts. Task arguments contain no token.
  2. The shared credential resolver asks Central for read access. Central checks the host, resource, active grant, installation, and repository.
  3. Central creates an installation token restricted to that repository and contents: read. Omission of the repository restriction can grant all repositories in an installation. Tokens expire after one hour. [1]
  4. Pilot supplies the token through the existing Git environment mechanism. Clone and fetch go directly to GitHub. Contents permission supports HTTP Git access. [5]
  5. Pilot reuses a token only for the same connection, repository, permissions, and grant version. It refreshes before expiry. Expiry does not disconnect the account.
Proposed request: connection reference + repository ID
Central derives: host → resource → active repository grant
GitHub restriction: repository_ids = [approved repository]
GitHub permission: contents = read
Backend response: token + expires_at + repository ID + grant version

Use the same resolver for branches, app metadata, clone, pull, and scheduled updates. Installation repository listing uses GET /installation/repositories. Do not validate every credential through GET /user. [3]

Cache policy is a trade-off. A memory cache can bridge a short outage. Each worker has its own cache. A restarted worker must ask Central again. A proposed two-minute refresh margin is a value to test, not a GitHub rule.

Prevent duplicate refreshes within a process. Apply a refresh result only if the connection and grant version still match. A stale result must not restore a disconnected grant. Keep network calls outside database and configuration locks.

06

Design for the failed request

Choose a failure to see its effect and recovery path. These are proposed behaviors, not results from a running implementation.

Effect
New credentials cannot be issued. Existing deployments keep running.
Recovery
Use a still-valid cached token for the same grant. Otherwise report Central unavailable and allow a safe retry.
Limit
Expired tokens and worker restarts require Central recovery.
How should retries work?

Retry bounded network failures and safe reads with delay. Respect provider retry headers. A confirmed credential rejection may justify one safe retry with a fresh token. Inspect partial Git state before repeating a clone, fetch, or pull. Do not repeat a migration just because its Git step failed.

How do missed events recover?

A webhook is an HTTP event from GitHub. Verify its signature, save the delivery, and process it idempotently. Track installation suspension, deletion, repository changes, and personal authorization revocation. Use periodic reconciliation to compare Central records with GitHub. Also recheck access on credential issuance. GitHub does not automatically redeliver failed webhooks. Arrange redelivery or reconciliation. [6] [7]

What should we measure?

Track connection completion, callback failures, token issuance latency, provider failures, rate limits, and reconciliation delay. Alert on sustained issuance failure and stuck attempts. Record safe resource references and operation types. Redact authorization headers and tokens. Set availability and recovery targets after measuring Central's dependency.

Make access changes explicit

GitHub supports revoking the installation token used for the revocation call. Scope cached tokens per resource and repository. Do not share one token between unrelated resource grants. [3]

Direct token delivery has a revocation window. A changed Central rule alone cannot invalidate a token already held by a host. Revoke known tokens where possible. If every new Git request requires a Central policy check, choose a Git proxy and accept its operational cost.

Product decision: should deployments survive the connecting person's departure? This proposal uses an explicitly approved team grant. It lasts until an administrator or GitHub installation change removes it. State this rule during connection. Provide an administrator review and removal path.

Start with read-only access. Do not request push, workflow, or repository creation permissions for this feature. GitHub sign-in to Pilot needs separate account-linking rules. A repository connection must not create an admin session.

08

Build the smallest complete flow

  1. Inspect Central. Confirm existing GitHub integration, membership rules, host identity, resource ownership, secret storage, and callback support.
  2. Define grant policy. Decide who can connect, who may delegate repository access, how ownership changes work, and how to disconnect.
  3. Build Central authorization. Add single-use attempts, a fixed callback, verified selection, and restricted token issuance. Use explicit authenticated methods. Do not expose an arbitrary proxy.
  4. Build Pilot resolution. Extend connection status with the authentication method. Keep old PAT fields and requests working. Support multiple installations. Use locked, atomic config writes and a patch if stored state changes.
  5. Finish recovery. Show connected, approval required, repair required, and temporarily unavailable states. Add reconciliation and disconnect. Approve the connection screen layout before implementation.
  6. Roll out in development. Check a private repository end to end. Keep an explicit PAT rollback path. Enable managed users only after the failure checks pass.

Checks that can disprove the design

  • Isolation: a host cannot obtain another resource's or team's credentials, including through modified IDs.
  • Delegation: repository read access alone cannot create an ongoing grant unless the approved policy allows it.
  • Callback: expired, replayed, mismatched, and interrupted attempts cannot attach the wrong installation.
  • Lifecycle: expiry, restart, and simultaneous refreshes return a valid token or a specific recoverable error.
  • Revocation: disconnect blocks issuance. Check token revocation and measure the remaining access window.
  • Recovery: a missed webhook, Central outage, and provider rate limit each reach the expected recovery state.
  • Compatibility: PAT users, public repositories, metadata reads, CLI commands, and updates still work.
  • Secrets: tokens stay out of browser storage, logs, task arguments, Git URLs, and saved Git config.

10

Keep the service recoverable

Keep the App private key and OAuth client secret in Central's secret store. Rotate them with a verified overlap procedure. Back up the grant records and required secret material through Central's existing recovery process. A restored database must not reactivate a grant that was revoked after the backup.

For the first scope, discard the user token after verified discovery and grant creation if no later user action needs it. Ask for authorization again when the person changes repository selection. If later features need long-lived user authorization, add encrypted token storage, serialized refresh, expiry handling, and revocation as a separate lifecycle. Installation tokens are newly issued credentials; they are not renewed with a user refresh token.

Review private dependencies and Git submodules before rollout. Every private source needs its own verified access. One repository-scoped token does not grant access to unrelated dependency repositories.

First scope: managed Pilot · Read-only private repositories · Explicit team deployment grants · PAT compatibility. This page does not implement or authorize a production change.
