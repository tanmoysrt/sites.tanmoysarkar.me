Pilot migration UI and sandbox: scenario check for v1.0.0-beta

Checked on 2026-11-17 against Pilot develop at f2459a11. Live tests ran on an Ubuntu 26.04 test server (4 vCPU, 15 GB RAM).

Pilot has a new update and migration UI, and a new workload sandbox. Before the v1.0.0-beta release, this page checks two things:

  • Does the migration workflow handle every case that a user can reach, and does the UI give the right action in each case?
  • Do the main apps work when the sandbox is on?

Each problem that I found has a pull request. A few problems need a decision first. They are in Open items.

Live pass means that I ran the case on the test server. Unit test means that a test in the Pilot suite covers the case. Fixed means that the case was broken and a pull request fixes it. Gap means that the case is not handled yet.

How the migration workflow works

An update or a site migration is a migration operation. The operation is a JSON record in <bench>/migrations/. It holds the state, the sites, the app revisions and the recovery data. Small tasks do the work, one step at a time. After each step, the operation selects the next task.

The normal path is: preparing → backing_up (one task per site) → updating (one task) → migrating (one task per site) → completed. When a step fails, the operation stops in needs_attention. The user can then choose Retry, Skip patch, Restore or Dismiss. While the backups run, the user can also choose Stop.

Sources: docs/migration.md, pilot/core/bench/migration/, and the UI in admin/frontend/dashboard/src/pages/updates/.

Sandbox

The sandbox runs each workload process (web, workers, redis) with an empty home folder, without the other benches, and with a read-only system. A new systemd bench has the sandbox on by default. Before Pilot writes the units, it starts a trial unit. If the trial fails, Pilot runs the bench without the sandbox and only logs a warning.

Finding: the sandbox never runs on Ubuntu 24.04 and later

Ubuntu 24.04 and 26.04 set kernel.apparmor_restrict_unprivileged_userns = 1. systemd then cannot make the user namespace that the sandbox needs, and the trial fails with exit code 226. On the test server both benches ran without the sandbox, and no one saw a warning.

An AppArmor profile that lets systemd-executor make user namespaces fixes this. With that profile, both benches started in the sandbox. #861 adds the profile to install.sh. It is a draft, because the profile applies to the whole host. See Open items.

Finding: Helpdesk article search fails on Pilot

Helpdesk's knowledge-base search uses the RediSearch module (FT.SEARCH, FT.CREATE). Ubuntu 26.04 ships Redis 8.0.5 without that module, so helpdesk.api.article.search gives HTTP 500, and the search index job fails. The sandbox does not cause this. Article saves still work, because Helpdesk checks for the index first. To fix it, Pilot must run a Redis build that has the search module, for example from packages.redis.io. That choice affects licensing, so this page lists it as an open item.
