How to read this
  • Status: Fix pass on a branch: 23 commits fix 23 findings; 2 are partly fixed, 1 stays open, 1 is unchanged on purpose, and 5 are deferred. Fault tests T14, T19, T21, T26 and T27 were run again on development hosts and now pass. Atlas dependency tests D1 to D8 ran on the local site; they found one issue in Frappe itself (F33, kept out of the Atlas and Metal scores); F34 and F35 turned out not to be issues.
  • Scenarios has one row per failure: what breaks, what the system does, and whether it recovers. "Handled" means it recovers without an operator and without data loss. "Partial" means it recovers with a gap. "Not handled" means an operator must act, or state or data can be lost. "Untested" means code reading only.
  • Findings lists bugs and missing fallbacks, most severe first. Critical means data loss or a stuck system with no automatic recovery. High means a customer outage or a stuck operation that needs an operator.
  • Fault injection ran only on development hosts and the local development Atlas site. The fix pass is on a branch of the Atlas repository; "After fixes" and "Resolution" show its result. Host names and addresses are left out on purpose.

Reliability matrix

One row per area. The score is the average of its scenario scores at audit time; "After fixes" is the same average after the fix pass on 2026-10-23. The score weighs failed customer requests and data loss. A control write that its caller retries, such as a route change from Central, counts as a short impact, not a failure. A score is out of 10: 10 means the system recovers by itself with no data loss and no customer impact; 7 to 9 means it recovers with a short impact or a small gap; 4 to 6 means an operator must act, but no data is lost; 0 to 3 means data can be lost or the area stays broken.

Reliability checklist per feature

✓ the feature has this property. ~ partly. ✗ missing.

VM create

  • ✓ Draft is committed before the Metal call; the VM name is the Metal ID, so a retry is idempotent (T3).
  • ✓ A draft whose create never reached Metal is deleted after a confirmed 404 (T3).
  • ✓ Concurrent creates do not double-book a host (T9).
  • ~ Placement can pick a host that stopped answering less than 2 min ago (T3).
  • ✗ Placement does not count provisioned thin disk, so disk can be oversold without limit (F12).
  • ~ While an image downloads, Atlas shows state unknown instead of a clear starting phase (T12).

VM delete

  • ✓ Destroy runs in checkpointed steps (runtime, network, storage) and resumes after a crash.
  • ✓ Atlas deletes the record only after Metal confirms absence; all host resources were removed (T9).
  • ~ A host that cannot write state (full pool) cannot destroy a VM to free space (F1).

Power and restart

  • ✓ Metal stores desired state and the reconciler converges; a killed guest restarts in 2 s (T2).
  • ~ A guest that cannot shut down costs the full 30 s graceful timeout per restart (T4).
  • ✗ No crash-loop limit or crash counter for a guest that keeps failing.

Migration

  • ✓ Destination daemon crash during copy: resumed and completed with intact data (T6).
  • ✓ 2-min network cut during copy: stream resumed, data intact (T7).
  • ✓ Atlas commits ownership before Metal destroys the source; finish and abort are exclusive.
  • ✗ A 10-min Atlas-to-destination network cut at cutover makes Atlas roll back and lose the guest's writes (T28).
  • ~ Abort after the destination booted discards destination writes (F7).
  • ✗ Stall and throughput are not visible in Atlas (F15, F16).
  • ✗ No operator action to recover a source when the destination host is lost (F32).

Host sync and control

  • ✓ Hosts keep running VMs and last sync when Atlas is down or cut off (T3).
  • ✓ Controller sets (peers, images, privileged addresses) are complete and replace the old set, so a missed sync heals on the next one.
  • ✗ A host that cannot reach Atlas is not marked unreachable; errors go to Error Log every 10 s (F6).

Host daemon (metald)

  • ✓ Crash and reboot recovery: ready in 3 s, VMs restarted after boot (T1, T8).
  • ✓ State files are written atomically with fsync.
  • ✗ Start limit can leave the daemon failed after 5 quick failures (F2).
  • ✗ One corrupt record stops the whole daemon (F3).

Host storage

  • ✓ fsync-acknowledged guest writes survive a full pool (T4b).
  • ✗ No reservation for Metal state, no pool alert, no placement stop near full (F1).

Machine images

  • ✓ Downloads verify SHA-256 and retry transient errors; partial imports are removed.
  • ✗ Archived images lose artifacts while VMs still use them (F8).
  • ✗ A transient Metal error during image upload marks the image Failed for good (F18).

Atlas dependencies

  • ✓ Central outage: the last valid key set stays in use for token checks.
  • ✗ Queue Redis hang blocks requests with no timeout (F14).
  • ~ VM state webhooks to Central stop after 3 retries (about 2.5 h) and can arrive out of order (F19).

HTTP proxy

  • ✓ Each node serves from its local route map; DNS health checks drop a bad node.
  • ~ With 3 or fewer nodes, one bad node blocks route writes (F17).

Fleet operations

  • ✓ metald rollouts use a canary batch, health checks, and stop on the first failure.
  • ✓ Daemon upgrade restarts in place; VMs keep running.

Host provisioning

  • ✓ Provider create is idempotent by name; setup runs as one deduplicated job and each step is safe to repeat.
  • ✓ Storage setup refuses a device that has any partition table, file system or signature, so it cannot wipe data.
  • ✗ The state dataset gets no space reservation (F1); the pool is one md device, not a ZFS mirror (F22).

Host networking

  • ✓ WireGuard peers are re-applied on every sync, so a wg0 restart heals peers in 10 s (T14).
  • ✗ The WG Mesh program is not re-attached after a wg0 restart (F21).
  • ~ Per-VM NAT and FORWARD rules are reconciled; the shared masquerade and isolation rules are not (F29, F30).
