How to read this
  • Status: Code review, first pass done. Fault injection on development hosts starts next.
  • Scenarios has one row per failure: what breaks, what the system does, and whether it recovers. "Handled" means it recovers without an operator and without data loss. "Partial" means it recovers with a gap. "Not handled" means an operator must act, or state or data can be lost. "Untested" means code reading only.
  • Findings lists bugs and missing fallbacks, most severe first. Critical means data loss or a stuck system with no automatic recovery. High means a customer outage or a stuck operation that needs an operator.
  • Fault injection ran only on development hosts and the local development Atlas site. No code in the Atlas repository was changed. Host names and addresses are left out on purpose.

S1AtlasAtlas web, workers, and scheduler are down for hours.Hosts keep the last complete sync (peers, image policies, privileged addresses) and keep running every VM. No create, change, or migration is possible. Telemetry and proxy configuration stop updating.UntestedCode reading: Metal does not depend on Atlas to run VMs.

S3Metalmetald fails at startup 5 times in 10 seconds.systemd stops restarting it. The daemon stays down until an operator acts. VMs keep running but nothing manages them.UntestedStartLimitBurst=5, StartLimitIntervalSec=10s (defaults).See F2.
S4MetalOne VM record on a host is corrupt.Startup validation fails for the whole daemon, so no VM on the host is managed.UntestedrecordStore.validateAll returns the first error.See F3.
S5VMA Firecracker process exits (guest crash or kill).The VM unit has Restart=no. The reconciler sees a stopped VM with desired state running and starts it on its next pass.UntestedCode reading.
S6StorageThe host ZFS pool becomes full.VM disks are thin clones with no reservation, and Metal state lives in the same pool. Guests get write errors. Metal cannot write its observed record, so every reconcile fails before its first step.Untestedzfs list: refreservation=none on VM volumes and metal/state.See F1.
S7AtlasA host is unreachable for hours.Sync fails every 10 seconds and writes one Error Log row each time. VM reads in Desk and API calls wait for the client timeout.Untestedsync_server logs each failure.See F6.

Writes the guest made on the destination are discarded.UntestedMigration rollback table in the handbook.See F7.

Findings

#SeverityAreaProblemEffectFallback or fixWhereVerified
F1HighStorageVM volumes are thin ZFS clones, and the Metal state dataset has no reservation in the shared pool.When guests fill the pool, every guest on the host gets write errors at the same time. Metal cannot write records, so it cannot even destroy a VM to free space.Reserve space for metal/state (for example refreservation=1G). Report pool free space in sync and stop placement on a host below a threshold. Write the destroy intent without a phase write first, or keep a small slop for state.metal/internal/storage/disk.go, host installCode reading and zfs list on a host
F8HighImagesArchived images lose their artifacts after the retention time even while VMs use them. Hosts prune images that are not in the cache policy.A VM with an archived image cannot start again after a restart, resize, or migration.Keep the kernel and root file system artifacts while any VM references the image.Image reclaim in Atlas, ensureImage in MetalKnown open issue, seen on a pre-production host
F2MediumMetalmetal.service uses the default start limit (5 starts in 10 s) with RestartSec=1.A transient startup failure at boot (pool import, wg0 not up) can put the unit in the failed state permanently.Set StartLimitIntervalSec=0 or a longer RestartSec with backoff, and alert on a failed unit.Host install unit for metal.servicesystemctl show metal.service
F3MediumMetalOne unreadable VM or migration record stops daemon startup.Blast radius is the whole host instead of one VM.Quarantine the bad record (skip it, report it in sync and the API), and start the daemon for the other VMs.metal/internal/vm/records.go validateAllCode reading
F4MediumMetalThe VM reconciler runs 4 workers and waits for the whole pass. One VM operation can take up to 35 minutes (for example an image download).4 slow VMs delay stop, restart, and delete for every other VM on the host.Do not wait for the slowest VM before the next pass: keep a per-VM in-flight set and start new work for idle VMs.metal/internal/reconciler/virtual_machines.goCode reading
F5MediumAtlasNetwork and route changes lock the Virtual Machine row (FOR UPDATE) and then call Metal twice.A slow host holds the row lock for up to about 90 s. The migration worker and other writers fail with lock wait timeouts.Serialize with a short-lived lock that is not a database row lock, or read Metal before the lock and compare generations.atlas/vm/core/vm_service.py lock_networkCode reading
F6MediumAtlasEach failed host sync, draft check, and termination check writes an Error Log row on every pass.One host down for a day writes about 8,640 rows for sync alone, plus rows per VM. Real errors get lost in the noise and the table grows.Log the first failure and state changes. Keep a last error and failure count on the Metal Server.atlas/metal_server/usage.py, atlas/vm/core/reconciliation.pyCode reading
F7MediumMigrationA disk-only migration cold-boots the destination before Atlas commits ownership. An abort in that window restores the source from the final snapshot.Writes made by the guest on the destination are lost. The window is short, but an operator abort or a commit error can hit it.Keep the destination guest paused or without network until finish, or reject abort after the destination started and only allow finish.metal/internal/vm/migrationCode reading and handbook
F9LowAtlasThere is no check that compares the VMs on each host with Atlas records.After an Atlas database restore, VMs created after the backup run on hosts but Atlas does not know them. Placement does not count them. A new VM can reuse a name that a host already has.Report unknown VM IDs from sync and show them on the Metal Server. Never adopt a VM whose create fingerprint differs.atlas/metal_server/usage.pyCode reading
F10LowAtlasA disk resize stores disk_mib in Atlas after Metal accepts it, in a later write.If the Atlas write fails, placement counts the old, smaller disk on the host.Read the disk size from the synced VM state for placement, or write it before the Metal call.atlas/vm/core/vm_service.py update_diskCode reading
F11LowMigrationTerminal destination records stay on the host with no cleanup.Directories collect over time. Seen on a development host 8 days after an aborted migration.Remove terminal records after a retention time.metal/internal/vm/migration/records.goSeen on a development host
