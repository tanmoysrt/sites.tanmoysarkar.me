04:40 — Why restarts killed jobs and why idle workers hung (issue 4)

systemd's default KillMode=control-group sends SIGTERM to every process of a unit, and also SIGCONT. For a worker pool, that includes:

  • the job process (RQ calls it the "horse"). It exits at once on SIGTERM. So the running job was lost.
  • each worker. The worker also gets SIGINT from the pool. With these signals at the same moment, the worker often did not run its stop handler and stayed blocked on Redis.

Evidence:

TestResult
SIGTERM only, sent to an idle worker, 6 timesExited in 2 s, 6 of 6
SIGTERM + SIGCONT + SIGINT (what systemd and the pool send), 6 timesStuck after 15 s, 5 of 6
Restart with a 60 s job running, developRestart took 1 s. Job failed: Work-horse terminated unexpectedly; waitpid returned 15
Same test with KillMode=mixedRestart waited 51 s. Job completed: Job OK
5 idle restarts of pools that ran for 75 s, with KillMode=mixed1 to 3 s each (one took 91 s before)

Fix: worker pool units now set KillMode=mixed. systemd sends SIGTERM only to the pool. The pool asks each worker to stop once. A worker finishes its job, then exits. After 90 s, systemd still kills what remains. This is the same as Frappe's supervisor setup, which signals only the main process.

04:20 — Retry and Restore race (issue 6)

Restore failed with TaskConflictError ... 'bench:update' in a test. The action task reads its own ID from the operation record to hand its locks to the next task. The API writes that ID only after the task is queued. The task now uses its own running ID.

03:30 — Root causes of the reported issues

Issues 1 and 2. Pilot puts the sites in maintenance mode and starts the backup, update and migrate at once. It does not wait for running jobs. At the end, Pilot restarts web and the workers. systemd lets a unit take 90 s to stop. Pilot gave the complete systemctl restart only 90 s, so one slow unit made the restart fail.

The Frappe Cloud agent puts the site in maintenance mode, then runs bench --site X ready-for-migration again and again for up to 300 s. It continues only when the site has no queued or running job.

Issue 3. Under systemd, Pilot runs Frappe's worker-pool. It merged all worker groups into one pool that listens to every queue. The counts per queue in the settings had no effect.

Changes on the branch

  • Before a site's backup, before the app update, and before a site's migrate, Pilot waits until ready-for-migration reports no jobs for the site, for up to 300 s. If the jobs do not finish, the operation goes to needs_attention before the step starts, and nothing changes. Pilot skips the wait when the workload is stopped.
  • A systemd restart gets the slowest unit's stop limit (90 s when the unit sets none) plus 120 s to start. Before, it got 90 s in total.
  • One worker pool per worker group, for example worker_pool_default. A bench with one group keeps the worker_pool name. Frappe's scheduler takes a bench-wide lock, so several pools still run one scheduler.
  • Worker pool units set KillMode=mixed.
  • A failed final restart records its error in the diagnosis and pauses for a retry.
  • Retry, Restore and Skip Patch hand over their locks from their own task ID.
  • Bench(path) makes the path absolute.
