mica v0.2 optimization

Part 1: the baseline. These are measurements of mica v0.1 on a small cloud VM, before we change any code.

Measured 25 October 2026 · baseline only

Context

mica gives a VM or a container a disk that lives in an S3 bucket. mica keeps the shared copy of the disk in the bucket. It uses the local SSD of the machine as a cache. A chunk is a 4 MiB part of the disk. mica downloads a chunk when a reader needs it. It uploads changed chunks in the background. The upload is a checkpoint.

The speed of mica depends on three things: the network link to S3, the local disk, and the CPU. Before we optimize mica, we must know how fast each of these is, and how fast mica is on top of them. This page records that baseline. Later parts compare each optimization against these numbers.

The data

A script writes 42,048 files with random content: 7.93 GiB in total. The content comes from an AES-CTR stream, so no two chunks are equal and no chunk is all zeros. mica cannot skip or share any of the data.

The best S3 rate is about 45–55 MiB/s, and only with many requests at the same time. One stream gets much less: 11–20 MiB/s. The single vCPU is the limit for PUT, because TLS and request signing use it fully. The disk is much faster than S3. Thus, on this machine, S3 and the CPU set the limits for mica, not the disk.

The first disk tests showed only 12 MiB/s for all block sizes. The provider's throttle counted each request as size ÷ 4 KiB operations against a limit of 3,000 IOPS. The provider removed the limits and rebooted the VM. All numbers on this page come from after that change.

What the baseline shows

1. The upload does not overlap with the write

mica must start a checkpoint early when local data not in S3 reaches half of dirty_limit_gib. Here that is 5 GiB, at about 33 s. But the first PUT goes out at about 55 s, after the write and the sync are complete. The first checkpoint then contains all 2,101 chunks. The second contains only 15.

The cause is in the freeze step of the checkpoint (src/checkpoint.rs). It goes through all chunk slots in order. For each changed chunk, it waits for sync_data(), then renames the file. The upload starts only after the loop ends:

for index in 0..self.slots.len() {
    let mut slot = self.slots[index].lock().await;
    if let Some(working) = slot.working.clone() {
        ...
        blocking(move || Ok(file.sync_data()?)).await?;   // one chunk at a time
        blocking(move || folder.freeze(index)).await?;
        ...
    }
}
// upload_all(frozen) starts here

A sequential write fills chunks in index order. The loop syncs the chunks one at a time, and the writer adds new chunks ahead of the loop. Thus the loop does not end until the writer stops. The write phase and the upload phase run one after the other. If the two phases overlapped, the total time could go down from 236 s to about the upload time alone. This is an estimate: about 180 s.

2. One cold reader gets one chunk at a time

One cold reader gets 22 MiB/s. S3 gives 39 MiB/s to 8 readers, and 85 MiB/s to disk warm with 32 downloads. mica downloads a chunk only when a read touches it. Thus one sequential reader waits for one S3 GET after the other, about 180 ms for each 4 MiB chunk. A read-ahead of the next chunks for sequential reads can close most of this gap.

3. Warm reads are CPU-bound on this machine

Warm reads reach about 107 MiB/s with 1 reader and with 8 readers. The single vCPU runs the reader, the checksum and mica together. The disk can do much more. This number will change on a machine with more CPUs.

4. A mount without writes still makes a checkpoint

Each mount writes the ext4 superblock. Thus each mount and unmount cycle uploads a few chunks and commits a new manifest, also when no file changed. The cost is small (about 1.2 s for each unmount), but it adds S3 requests.
