mica v0.2 optimization

Part 1: the baseline. These are measurements of mica v0.1 in a local lab, before we change any code.

Measured 25 October 2026 · baseline in progress

Context

mica gives a VM or a container a disk that lives in an S3 bucket. The bucket holds the shared copy of the disk. The local SSD of the machine is a cache. A chunk is a 4 MiB part of the disk. mica downloads a chunk when a read needs it, and uploads changed chunks in the background. One upload round is a checkpoint.

The goal of v0.2 is a fast wake: a VM that stops on one machine must start on another machine quickly. Before we change mica, we must know how fast it is now, and where the time goes. This page records that baseline. Later parts compare each change against these numbers.

The lab

All tests run on one machine. Three parts simulate a real node:

  • S3: RustFS 1.0.1 in Docker. A shaper container limits its network link with tc: 100 MiB/s in each direction, with 1 ms round trip.
  • Local disk: a separate mica daemon (mica-lab.service) keeps its chunks on the NVMe disk, on btrfs. A cgroup limit (io.max) caps this daemon at 300 MiB/s for reads and for writes.
  • VM: Firecracker 1.16.1 boots Ubuntu 24.04 from a 100 GiB mica disk.

What these numbers show

  • The link and the disk set the limits. Cold reads with 8 or more readers and disk warm run at the link limit (≈ 95 MiB/s). Warm reads run at the disk limit (296 MiB/s).
  • One cold reader loses about 27%. It gets 69 MiB/s, because it waits for one chunk download after the other. At 1 ms round trip the cost is small. At a higher round trip, it will grow.
  • A mount costs about 1.1–1.3 s, also with a warm cache. The next step is to find where this time goes.
  • Moving a disk is serial. Write, sync and upload do not overlap, so the time to move a disk is their sum.

Firecracker on a mica disk

The VM has 2 vCPUs and 2 GiB RAM. Its root disk is a 100 GiB mica disk with ext4. The guest is Ubuntu 24.04 with systemd, sshd and the test tools: 270 MiB of files. The disk device goes straight to Firecracker as a virtio block device (io_engine = Async, cache_type = Writeback).

The detach uploads 12.2 GiB, not 8 GiB. The other 4 GiB is the fio test file. The guest deleted it, but fstrim in the guest fails: "the discard operation is not supported". Firecracker's virtio block device does not pass discard to the host. Thus, space that a guest frees on a mica disk stays in the disk, and mica uploads and stores it.

What these numbers show

  • A cold boot downloads almost the full root filesystem. 250 MiB for a 270 MiB system, because each small read costs a 4 MiB chunk.
  • Attach is about a third of a warm boot. A warm boot takes 3.3 s, and the attach takes about 1.1 s of this.
  • Freed guest space is never released. Without discard from Firecracker, deleted data stays in S3. A fix needs discard support in the VMM, or a periodic trim through another path.
  • A clone of a snapshot is free. The snapshot and the clone take less than 0.05 s, and the clone boots warm from the shared cache.

Memory snapshots

A Firecracker memory snapshot stores the full guest RAM in a file, and the device state in a small second file. A restore starts a new Firecracker process from these files. The guest continues from the moment of the snapshot, without a boot.

The test VM runs an app before the snapshot: an HTTP server that holds 384 MiB of random data in RAM. Each GET returns a hash of all 384 MiB. Thus the first answer after a restore needs all app memory back in RAM, and the hash shows that the memory is correct. All restores returned the correct hash.

Make the snapshot

  1. Pause the VM.
  2. Write the snapshot files to an ext4 filesystem on a second mica disk (4 GiB). The memory file is 2,048 MiB.
  3. Make a mica snapshot of the root disk while the VM is paused. Thus the disk and the memory are from the same moment.
  4. Detach both disks. Each restore starts from a new clone of the root disk snapshot.

Restore with the File backend

With the File backend, Firecracker maps the memory file into the guest. A page loads from the file when the guest first uses it. On a mica disk, this read goes through ext4 and the mica device. On a cache miss, mica downloads the full 4 MiB chunk from S3.

The times start at the snapshot load request. "Attach" is the time before it: a clone of the root disk, the attach of both disks, and the mount of the memory disk.

What these numbers show

  • A warm restore is 5 times faster than a warm boot. ssh answers 0.20 s after the load, and the app 0.63 s after the load. A warm boot needs 2.2 s until ssh, and then the app must start.
  • A cold restore is limited by the bytes it downloads. The app answer needs 630 MiB: at 95 MiB/s that is 6.6 s, and the measured time is 6.7 s. The guest uses only a part of each 4 MiB chunk, but mica downloads the full chunk.
  • The mica read profile does not help here. The profile has 157 chunks (628 MiB), and the prefetch downloads them in about 6 s. These are the same chunks that the page faults need, so the link is the limit again. Only fewer bytes for each page fault can help: smaller chunks, or a handler that knows which pages are in use.
  • The attach takes more time than a warm restore. Two disks attach one after the other, and with the clone and the mount this takes 2.2–2.8 s. Parallel attach and a faster attach path are important for a fast wake.

Next: two restore variants with a userfaultfd handler (pages on demand, and a recorded page profile that loads first). These need one more permission on the lab machine.

1. Attach: an atomic claim, and no global lock

Problem. An attach took about 1 s, also with a warm cache. Of this, 1 s was a fixed wait. mica writes a marker to S3 to claim the disk. Without conditional writes, two nodes can claim at the same moment. So mica waits 1 s, then reads the marker back. Also, the daemon held one global lock during the full attach, so attaches of different disks ran one after the other.

Change.

  • A new setting, s3.conditional_writes. When the store supports it, the claim is one atomic create (PUT with If-None-Match: *). Of two nodes that claim at the same moment, only one can create the marker, so there is no wait. RustFS, R2, AWS S3 and MinIO support this. Garage does not, so the old claim with the 1 s wait stays as the default.
  • With the old claim, mica now loads the disk metadata during the 1 s wait, not after it.
  • Each disk has its own attach lock. The global registry is locked only for short updates. Two attaches of the same disk wait for each other and get the same device.
  • Each attach logs and returns the time of each stage.

Result. One attach now takes 24 ms (p50). The stages are: claim and metadata load 16 ms, open the disk 2 ms, start the ublk device 2 ms. Four attaches at the same time take 45–64 ms. With conditional_writes = false, an attach still takes 1.03 s, as before.

2. Small chunks and paged metadata

Problem. A cold boot downloaded 250 MiB to read a part of a 270 MiB system, because each small read cost a 4 MiB chunk. Smaller chunks fix this, but they make the old manifest large. A manifest listed every chunk: 32 bytes for each chunk, so 12.5 MiB for a 100 GiB disk with 256 KiB chunks. mica uploaded the full manifest on each commit, and downloaded it on each cold attach. The daemon also held a lock and a slot for every chunk in memory.

Change.

  • Chunk size for each disk. mica disk create --chunk-size takes 64K to 4M. The default is now 256 KiB.
  • Paged metadata. A page holds the hashes of 1,024 chunks (32 KiB; it covers 256 MiB). The root holds one hash for each page: 12.5 KiB for 100 GiB. Pages are immutable, and their key is their hash, so checkpoints, snapshots and clones share every page they do not change. A page of zero chunks is not stored. A commit uploads only the changed pages and the new root.
  • Lazy state. The daemon loads a page, and makes the slots of its 1,024 chunks, when the guest first uses it. A node-level page store keeps verified pages in memory and in local files.
  • Checkpoint. The checkpoint takes the set of local chunks at its start, and freezes and uploads each chunk in one stream. Up to 64 MiB of uploads are in flight. A writer that keeps writing cannot make the checkpoint run for ever.
  • No HEAD for each chunk after a commit. v0.1 checked every committed chunk with a HEAD request, in case a GC deleted it during the commit. Now GC writes a record at the end of each run. A checkpoint reads the GC lock and this record before and after it. It checks the chunks and pages only when a GC ran in this time. The cost is four requests for each checkpoint, not one for each chunk.
  • No sync for cache downloads. A cold read no longer waits for a sync of the cache file. After a crash, a torn file is found by its hash before its first read.
  • No sync for a new chunk file of zeros. A new chunk file without content to copy is no longer synced before its rename. Recovery restores its length after a power loss.

Review. A second model (codex) reviewed the change for crash and race problems. It found four real problems, which are fixed: pages also need the GC check; the GC lock and record must be read one after the other; a failed upload must not stop other chunks in the middle of a freeze; a chunk file can be short after a power loss.

Result. A cold boot downloads 136 MiB instead of about 250 MiB, and takes 2.8 s instead of 4.6 s. Small cold reads are 2–16 times faster. The upload speed does not change, because the link is the limit. The cold memory restore improves less: the app reads 384 MiB of its own memory, and this alone takes about 4 s at 100 MiB/s.

3. Prefetch, read-ahead and background fill

Problem. mica downloaded a chunk only when a read touched it. A single reader waited for one download after the other, and a disk never became fully local.

Change.

  • Read-ahead. When reads continue each other, mica fetches the next chunks: 1 MiB ahead at first, then twice as much each time, up to 8 MiB.
  • Startup prefetch, on by default. At attach, mica fetches the chunks of the read profile: the first 64 MiB that the disk read in its last session.
  • Background fill. After that, mica downloads every other chunk of the disk, in disk order, until the cache is nearly full. Then all reads are local, also if the link goes down.
  • An order of priority for downloads. Reads by the guest come first (64 at a time). Likely reads, from read-ahead and the profile, start only while no read waits. The fill starts only while no read and no likely read is in flight.

Review. codex found six problems in this step, all fixed: a cancelled read could leave a counter high for ever; read-ahead could pile up tasks without limit; fetches could continue after a detach; the fill could hold the slots that read-ahead needs; a shutdown time-out could cancel a checkpoint in the middle of a freeze; and a repair check could run before a running GC sent its last delete.

Result. One cold reader is now at the link speed: 87 s for 7.9 GiB, which is 91 MiB/s. After a cold attach, the background fill makes the full disk local in 84 s, which is also the link limit. Boot times do not change.

A regression. The cold memory restore became slower: 6.60 s, with 652 MiB downloaded. The startup prefetch of the root disk downloaded its 64 MiB boot profile in 0.6 s. A restored guest does not read its boot files again, so this download only took bandwidth from the restore. Small fill downloads in the gaps between reads also took some. The fix for step 4: likely reads start only while fewer than 8 read downloads are in flight, and the fill starts only after 250 ms without a new read download.

4. Compression and continuous checkpoints

Problem. After step 3, cold reads and uploads are limited by the link. The only way to make them faster is to send fewer bytes. Also, a disk that the guest fills uploads only at detach, so write, sync and upload run one after the other.

Change.

  • zstd compression. Each chunk is stored as a zstd frame (level 1), and each page too (level 3). The key stays the SHA-256 of the plain data, so equal chunks still share one object. A download is decompressed, then checked. The local cache keeps plain files, so local reads do not decompress.
  • Continuous checkpoints. A checkpoint now starts every 30 s (was 3 minutes), and also when 512 MiB of local data waits. Since step 2, a commit writes only the changed pages and a small root, so frequent checkpoints are cheap.
  • mica disk checkpoint uploads the changes of an attached disk on request.
  • The two scheduling rules from the step 3 regression.

Result. The test data of the file tests is random, so it does not compress, and those numbers do not change. Real system data does compress: a test with /usr/bin and Python libraries (2.0 GiB) uploaded 675 MiB. The memory file of the snapshot shrinks from 996 MiB to 358 MiB in S3. A cold restore answers ssh after 0.55 s instead of 2.38 s. The app answers after 4.66 s. Most of its 451 MiB is the app's own 384 MiB of random data, which does not compress. A cold boot takes 2.35 s, down from 4.61 s in v0.1.

Problems found.

  • Writes during an upload became slower. The checkpoint synced each chunk before it renamed it to .frozen. Under heavy writes, up to 64 of these syncs at the same time stalled the writer for seconds, and the upload ran at only 17 MiB/s during the write. Also, a write to a frozen chunk must first copy it. Thus fdatasync in the guest went from 427 to 263 per second while an upload ran. The fix: the freeze no longer syncs. The upload reads the file through the page cache, and a guest FLUSH now also syncs the .frozen file of a chunk it wrote. Measured in the next run.
  • The Alpine guest did not get a network address, because its network service needs a package that the image does not have. Fixed with a start script. ssh now answers 1.34 s after the start of Firecracker, against 2.17 s for Ubuntu.

Review. codex found one more bug, also present in v0.1: with wait_when_behind, a checkpoint woke the waiting writers before it cleared the "behind" state, so a writer could wait for ever. Fixed.
