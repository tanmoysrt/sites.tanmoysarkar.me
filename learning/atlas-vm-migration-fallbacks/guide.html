What a migration does

A migration moves one VM from a source host to a destination host. Atlas is the control plane. It picks the destination and records which host owns the VM. Metal is the host daemon. Destination Metal pulls the disk from source Metal.

The most important idea is the commit point. Atlas keeps the source as the owner until destination Metal reports ready. Then Atlas changes the owner to the destination in one transaction. Before the commit, a failure rolls back to the source. After the commit, a failure must go forward on the destination.

A migration must meet three goals. It must not abort for a temporary problem. It must not stay stuck forever. It must not lose data.

Disk-only and memory snapshot modes

Metal first copies a full ZFS snapshot while the VM runs. Then it copies smaller changes. When the change is small enough, Metal starts cutover: it stops the source and copies the last change.

ModeAt cutoverOn the destinationGuest memory
Disk-onlySource stops normally.Cold boot from the copied disk.Lost
Memory snapshotSource saves its memory, then stops. Memory moves beside the last disk change.Load the guest paused. Resume it at finish.Kept

A memory snapshot migration needs compatible hosts. Atlas checks the CPU profile, CPU vendor, Firecracker build, kernel, VM shape, and clock before it starts. A host with the CPU template disabled reports the profile native. It can only take memory from a host with the same CPU model and features.

The disk-only fallback

The migration record has the option Allow Disk-Only Fallback. It is on by default. It decides what happens when memory cannot move.

OptionAtlas pre-check failsDestination restore fails
OnAtlas clears Memory Snapshot. The migration continues with the disk only. The reason goes to Error Message.Metal removes the failed runtime, recreates the network, and cold-boots the received disk. memory_snapshot_status stays failed after the migration completes.
OffThe migration fails with migration_incompatible. No transfer starts.The transfer fails. Atlas rolls back to the source.

The pre-check also fails when the VM desired state is stopped, because a stopped VM has no memory to move. It also fails for a resize, because a memory snapshot cannot change the VM shape.

A fallback costs a guest reboot. The guest loses its RAM state but keeps its disk. Use the option off when a reboot is worse than a failed migration.

The Abort button sends only the record name. The server reads the latest record. This avoids a stale form save while the worker records progress.

The inspect-first recovery rule

A restore or resume can report an error after it worked. For example, a socket can time out after Firecracker resumed the guest. A blind cold boot would then kill a healthy guest and lose its RAM. So Metal always inspects the guest before it decides.

Guest state after the errorAt finish (destination)At rollback (source)
In its desired stateKeep the memoryKeep the memory
Still pausedRetry the resume on the next passRemove and cold-boot
Process gone or failedRemove and cold-bootRemove and cold-boot

A cold boot keeps the disk consistent. Only the guest RAM state is lost. A cold boot that fails keeps the migration in its phase for another try.

The 25 MiB/s floor is the minimum supported migration throughput. A slower link can hit the copy limit on a large disk.

Sleeping VMs

A sleeping VM has saved memory on disk and no running process. Atlas shows it as stopped, but its desired state is running. That is how Atlas tells it apart from a VM that a user stopped.

ModeWhat Metal doesResult
Memory snapshotSends the existing saved state. It does not wake the VM on the source.Memory kept. The VM is awake on the new host.
Disk-onlyWakes the VM, shuts it down cleanly, then cold-boots it on the new host.Memory lost

Outside migration, a failed wake-up keeps the saved state for another try. Migration rollback is the one exception: Metal cold-boots the source so the migration cannot stay stuck.
