How the HTTP proxy gets a request to a VM

A proxy node handles each web request with its own route map. A separate control service keeps those maps in sync. This guide shows both paths and what happens when a node fails.

The big picture

Each region has 1 to 5 proxy nodes. Each node runs OpenResty for web traffic and a control daemon for route changes.

OpenResty serves traffic

It reads the local route map and sends the request to a VM.

The daemon changes routes

It validates a change, shares it with peers, and updates OpenResty.

WG Mesh finds the VM

The proxy uses a stable VM address. The VM can move between hosts.

Key idea: A web request does not wait for the control cluster. A node can still serve its known routes when route changes stop.

Follow one web request

A client opens a site in the regional wildcard domain.

For example, erp.par-1.example.com uses the erp site route. That route points to a VM mesh address, such as fdaa:1:0:2::b.

The mesh address belongs to the VM, not its host. If the VM moves, WG Mesh finds its new host. The proxy route stays the same.

How a route change reaches every node

Central changes site and custom-domain routes. Atlas changes the routes it owns.

Every node saves its route map and a generation number. A node that misses a change can get a full copy of a newer map from a peer.

How many nodes must confirm?

For 1 to 3 nodes, every node must acknowledge a route change. A 4 or 5 node cluster needs 3 acknowledgements, including the leader.

What happens when something fails?

SituationWeb requestsRoute changes
A proxy node stopsHealthy nodes continue to serve their local routes. DNS normally removes the failed node.The remaining nodes elect a leader if they have enough votes.
A node loses its peersIt can serve routes already in its local map.It cannot confirm a new change without the required acknowledgements.
A node comes backIt loads its saved map, then gets a newer copy if one exists.It can acknowledge new changes after it catches up.

If a route change returns 503: Its outcome is uncertain. Some nodes may already have the change. Send the same change again. Atlas route changes are safe to repeat.

A new node must synchronize and know the leader before Atlas publishes it in DNS. This prevents a node with an empty map from receiving public traffic.

A route without a saved map entry

An auto-proxy hostname encodes a VM identity. OpenResty calculates the VM's mesh address from that name.

This is useful when a VM needs a URL before anyone writes a site route. For an example region, tenant 2 and VM 11 produce this result:

Hostname
site-lpc8lqa.example.com
Encoded label
lpc8lqa
VM mesh address
fdaa:1:0:2::b

OpenResty checks the configured auto-proxy prefix and decodes the label. It then sends HTTP to port 80 on that VM. HTTPS ends at the proxy.

The name identifies a destination. It does not create a VM or grant access. The tenant and guest firewall rules still apply.

Scope: Auto-proxy names work inside the regional wildcard domain. Custom-domain HTTPS takes a different path: the proxy passes TLS to the VM.
