Atlas HTTP proxy: HA and static routing

A region has one public entry point for web traffic: a cluster of 1 to 5 proxy nodes. This guide explains how those nodes agree on routes, what happens when nodes fail, and how an "auto-proxy" hostname reaches a VM with no stored route at all. Each idea is shown as a scenario.

1. Two jobs, two programs

Every proxy node runs two programs. They have different jobs and fail independently.

ProgramJobNeeds the cluster?
OpenRestyAccepts public HTTP and HTTPS. Reads routes from shared memory and forwards each request to a VM's mesh address.No. It serves from its local copy.
Control daemonAccepts route changes from Central and Atlas. Elects a leader, replicates changes and writes them into OpenResty.Yes, for writes.

This split is the main HA property. Reading routes never depends on the cluster. A node that loses every peer still serves every route it already has. Only new route changes stop.

OpenResty sends each request to the VM's mesh address, such as fdaa:1:0:2::b. This address names the VM, not the host it runs on. WG Mesh finds the current host. So a VM migration never requires a route change on the proxy.

2. The state every node keeps

Each daemon keeps one file, /var/lib/nginx/cluster-state.json. It writes the file to a temporary path, calls fsync, then renames it into place. A crash leaves the old file or the new file, never half of one.

FieldMeaning
sites, domainsThe complete route maps.
generationA counter. It goes up by 1 for each route change.
operation_idA UUID for the last change. It tells apart two nodes that have the same generation but different contents.
term, voted_forThe election round and this node's vote in it.
mutation_termThe term in which the last change was made. Elections compare it before the generation.

There is no log of changes. When a node falls behind, it gets a full copy of the leader's state, called a snapshot. The maps are small, so a full copy is cheap and much simpler than log replay.

The timers are fixed in cluster.py:

TimerValue
Leader heartbeatevery 100 ms
Election timeout (random per node)300 to 450 ms
One peer request200 ms
A follower forwarding a write to the leader1500 ms (enough to repair one stale peer)

3. HA scenarios

Scenario 1

A route change arrives at a follower

Central sends PATCH /v1/sites/erp to any node through the regional control name. DNS picked a follower.

  1. Follower B does not change anything. It forwards the change to leader A.
  2. A takes its write lock, so changes are applied one at a time. It applies the change to its own OpenResty, assigns generation g+1 and a new operation_id, and saves the file.
  3. A sends {base_generation: g, generation: g+1, change} to every peer in parallel.
  4. A peer applies the change only if its own generation is g. The change then goes into its OpenResty too.
  5. A counts acknowledgements, including itself. When there are enough, B returns 200 and the header X-Atlas-Proxy-Generation: g+1.

How many acknowledgements are "enough" depends on the cluster size:

NodesAcks needed (includes leader)Nodes that can be down and writes still work

Clusters of 3 or fewer need every node. That is stricter than a majority: a small cluster chooses "every node has the route" over "writes survive one failure".

Scenario 2

A peer missed an earlier change

Peer D was restarting while change g was made. Now D is at g-1 and the leader sends change g+1 with base_generation: g.

  1. D sees that the base does not match its own generation. It returns 409 generation mismatch.
  2. The leader sends D the snapshot from before the new change (generation g).
  3. The leader sends change g+1 again. D now matches and acknowledges.

This repair takes up to three peer calls. That is why a forwarded write has a 1500 ms budget and not 200 ms.

A peer that does not answer at all is not repaired during the write. The next heartbeat repairs it: each heartbeat carries the leader's generation and operation_id. A follower whose values differ downloads the leader's snapshot.

Scenario 3

The leader crashes

Leader A's VM stops. B, C, D and E stop getting heartbeats.

  1. Traffic: no change. Every OpenResty keeps serving its maps. Route 53 stops returning A's address once A's health check fails.
  2. Writes: during the gap, a follower still tries to forward to A. The connection fails and the client gets 503 leader unavailable.
  3. After a random 300 to 450 ms, the first follower whose timer runs out, say C, starts an election. It moves to the next term, votes for itself and asks the others for votes.
  4. A voter gives at most one vote per term. It votes only if C's (mutation_term, generation) is at least as new as its own. So a node that is missing changes cannot become leader and lose routes.
  5. C gets 3 of 5 votes and becomes leader. It starts heartbeats. Writes work again.

The write gap is about one election timeout plus one vote round trip, usually well under a second. The random timeout makes it unlikely that two nodes start an election at the same moment and split the vote.

Scenario 4

One node is down in a 3-node cluster

Node C is down. A is leader, B is healthy.

  • Elections still work: A plus B is a majority of 3.
  • Writes do not: 3 acknowledgements are needed and only 2 are possible.

A write now goes like this. A applies it, B applies it, and A returns 503 with "required": 3, "acknowledged": 2, "retryable": true. The change is not rolled back. A and B keep it and serve it.

When C comes back, it loads its old file, asks its peers for their status, and downloads the newest snapshot. The change that "failed" is now on all three nodes.

Rule: a 503 from a write means "the outcome is unknown", not "nothing happened". Send the same change again. Every route change is a set, update or delete of a whole value, so repeating it gives the same result.

With 2 nodes, losing one is worse: 2 votes are needed for a leader, so the survivor never becomes leader. Its /readyz returns 503. Its /healthz stays healthy, so it keeps serving traffic.

Scenario 5

The network splits the leader away

A 5-node cluster splits into {A, B} and {C, D, E}. A was leader.

  1. A keeps sending heartbeats. Only B answers: 2 of 5 is less than a majority. A steps down after its next heartbeat round. A leader that cannot reach a majority does not keep acting as leader.
  2. C, D and E elect C in a new term. Writes to that side succeed with 3 acknowledgements.
  3. A and B keep trying elections and keep failing, because 2 votes is not enough. Each attempt raises their term. Both keep serving traffic from their maps, but those maps no longer get new changes.

A write that raced the split. Suppose A accepted a write just before it stepped down. A and B applied it, and the client got 503. That change now exists only on the minority side. What happens to it depends on the other side:

  • C's side made newer changes. Their mutation_term is higher, so they win any later election. When the network heals, heartbeats show A and B a different operation_id. They download C's snapshot and the raced write is gone.
  • C's side made no changes. A's raced write can be the newest state. It can win the next election, and then it spreads to every node.

Either way the client saw 503, and the rule from Scenario 4 applies: repeat the change.

When the network heals, A and B have a higher term from their failed elections. C sees that higher term in a heartbeat reply and steps down. The cluster runs one more election, which causes one more short write gap. Traffic is not affected.

Scenario 6

A new node joins

Atlas adds proxy node 4 to a 3-node region.

  1. Atlas creates the VM, installs the package and writes the configuration with all peers. Atlas does not send routes to the new node.
  2. The daemon starts. It has no file yet, so it creates one from OpenResty's current (empty) maps.
  3. It asks all peers for status, picks the one with the highest generation and downloads that snapshot.
  4. /readyz returns 503 until the node has synchronized and knows who the leader is. Atlas waits for 200 before it publishes the node in DNS. So public traffic never reaches a node with empty maps.

A node that restarts after a crash takes the same path, but it starts from its saved file. That lets OpenResty serve routes before any peer answers.

Scenario 7

The cluster password is rotated

Peers authenticate with the header X-Atlas-Cluster-Password. During a rotation, some nodes have the new password and some still have the old one.

Each node accepts the current password and, until a set expiry time, the previous one. When a peer call gets 401, it retries once with the previous password. Heartbeats and replication keep working while the new configuration reaches every node.

If a follower forwards a write and the leader rejects its password, the client gets 502 cluster authentication failed. This is kept separate from 503 because repeating the write will not fix it.

Scenario 8

Every node fails its health check

Route 53 multivalue answers normally leave out unhealthy nodes. If every node is unhealthy, Route 53 returns all of them. Clients still try the proxies, and any node whose OpenResty works still serves them.

4. Static routing scenarios

A normal site route is a stored entry: erp → fdaa:1:0:2::b. Someone has to write it, and the cluster has to replicate it. For some traffic that is too slow or unnecessary, for example a preview URL for a VM that was just created.

Auto-proxy puts the route inside the hostname. OpenResty computes the VM's mesh address from the name. It needs no map entry, no daemon and no cluster.

The encoding

A mesh address has three parts after the fixed fdaa:

The VM number is the numeric suffix of the Atlas ID, so VM-00011 is 11. For tenant 2 and VM 11:

(11 << 32) | 2  = 47244640258
base 36          = lpc8lqa
hostname         = site-lpc8lqa.<regional zone>
mesh address     = fdaa:1:0:2::b   (region 1)

Atlas configures two host prefixes (AUTO_PROXY_HOST_PREFIXES):

PrefixMatchesExample
site-exactly site- before the labelsite-lpc8lqa
*-vm-any non-empty text, then -vm-, before the labelerp-vm-lpc8lqa, staging-vm-lpc8lqa

The wildcard form lets a name carry a human-readable part. The proxy ignores that part.

Scenario 9

A request for erp-vm-lpc8lqa.<zone>

  1. OpenResty lowercases the host, removes any port and removes the regional zone. The result is erp-vm-lpc8lqa.
  2. Control names (proxy, proxy-NNN) are checked first. This is not one.
  3. auto_proxy.lua splits the name with ^(.-)([0-9a-z]+)$. The prefix is erp-vm- and the label is lpc8lqa.
  4. The label has no leading zero, and the prefix matches *-vm-.
  5. The label is decoded into six 16-bit parts. Lua numbers cannot hold 96 bits exactly, so the code keeps the value as parts and carries between them.
  6. The parts become fdaa:1:0:2:0:0:0:b. OpenResty sends HTTP to [fdaa:1:0:2::b]:80. HTTPS ends at the proxy with the regional wildcard certificate.

The site map is never read. If the name had not decoded, the router would look it up in the site map next.

Scenario 10

The VM moves to another host

Nothing changes on the proxy. The name encodes tenant and VM, not a host. The mesh address stays the same, and WG Mesh delivers the packet to the new host. This is the same reason stored routes survive migration.

Scenario 11

Someone tries to store a route named site-docs

The daemon rejects it with 409 site-docs is reserved for auto proxy traffic.

Without this check, a stored entry and a computed address could both claim one name. OpenResty checks auto-proxy first, so the stored route would never be used. The daemon prevents the conflict at write time instead.

The daemon's check for *-vm- is broader than OpenResty's. It rejects any key that contains -vm- after the first character, even if the rest is not a valid label. It can reserve too many names but never too few.

Scenario 13

A valid name for a VM that does not exist

site-docs is valid base 36. It decodes to some tenant and VM number. The proxy does not check Atlas records, so it tries that address and the connection fails.

This is by design. The name is a formula, not a permission. Access still depends on the tenant and guest firewalls, and WG Mesh delivers only to a VM that exists. An auto-proxy name reaches exactly what the mesh address would reach from the proxy, and nothing more.

Scenario 14

Turning static routing off

Atlas writes [auto_proxy] into /etc/atlas/proxy-control.toml with address_prefix (for example fdaa:1) and host_prefixes. The apply step writes both to /var/lib/nginx/auto-proxy, and OpenResty reads that file at startup (init_by_lua_block).

Leave out the section and the file holds no address prefix. Then get_virtual_machine_address returns nothing for every name, and all traffic uses the site map.

5. Limits to remember

  • A 503 on a write has an unknown outcome. The change can be on some nodes, on all nodes later, or dropped after a split. Always repeat the same change.
  • Clusters of 2 or 3 nodes accept no writes with one node down. Use 4 or 5 nodes when writes must survive a node failure.
  • A healed minority causes one extra election. Failed elections raise its term. There is no pre-vote step to prevent this. Writes pause briefly; traffic does not.
  • Full snapshots, not a log. Repair copies the whole map. This is fine for route maps of this size. It would not be fine for large state.
  • Auto-proxy is HTTP to port 80 only. TLS ends at the proxy. Custom domains, which pass TLS through to the VM, never use it.
  • Auto-proxy does not grant access. It only computes an address.
