How the Atlas HTTP proxy works

A site name must lead to the right virtual machine (VM). Follow one request and one route change to see how Atlas handles VM moves and proxy failures.

The problem One request One route change Failures Auto-proxy Sources

What problem does the proxy solve?

A browser knows a name such as erp.par-1.example.com. It does not know which tenant VM serves that site or which host runs the VM.

Atlas puts 1 to 5 proxy nodes in each region. Domain Name System (DNS) sends the browser to a node. That node looks up the site and sends the request to the VM's stable private address.

DNS
Chooses a proxy node. It does not choose the tenant VM.
Route map
Connects a site name to a VM mesh address. Each proxy node keeps a local copy.
WG Mesh
The private network that delivers traffic to the VM's current host.

The useful separation: A route names the VM, while WG Mesh finds its host. A VM move does not require a proxy route change.

What happens to one web request?

Assume the site route maps erp to fdaa:1:0:2::b.

  1. DNS returns a proxy node. The browser connects to that node with the site name.
  2. OpenResty reads its local map. The erp entry gives it the VM mesh address.
  3. OpenResty forwards the request. For site HTTPS, it ends TLS and sends HTTP to port 80 on the VM.
  4. WG Mesh delivers the packet. It knows which host currently runs the VM.

OpenResty does not ask another proxy node or the control daemon for each request. This is why an isolated node can still serve routes it already knows.

Where did the route map come from?

Each proxy node also runs a control daemon, a background service that changes its local map. Central sends site and custom-domain changes. Atlas sends the changes it owns.

The daemons elect one leader. That leader orders route changes and copies them to the other nodes.

Suppose Central changes erp to point to a new VM in a 5-node region.

  1. A follower forwards the change. Clients can contact any ready node; only the leader orders writes.
  2. The leader applies the change locally. It advances the generation number, updates OpenResty, and saves the new map.
  3. The leader sends the change to its peers. A peer updates its own map and acknowledges.
  4. The leader answers after enough acknowledgements. In a 5-node region, it needs 3, including itself. The other 2 can catch up later.

The generation number increases after each change. Nodes compare it with the last operation ID to find differences. A node that missed a change can install a full, newer copy of the map.

A 3-node region can elect a leader with 2 votes, but it still needs all 3 nodes to confirm a route change. Election and write confirmation have different rules.

What changes when a node fails?

Two operations have different needs. Serving a known route reads one node's local map. Changing a route needs the leader and enough acknowledgements.

Why a failed write can still change a route

In a 3-node region, suppose one node is down. The leader and the second node can apply a change, but the required third acknowledgement never arrives. The client gets 503.

The two live nodes do not roll back their maps. The returning node can later copy the newer snapshot. A failed response therefore does not prove that the route stayed the same.

For a route-change 503, send the same change again. Atlas route changes are safe to repeat. A retry can succeed after the missing nodes return.

Atlas waits for a new node to synchronize and know the leader before it publishes that node in DNS. Later, DNS health checks test whether it can serve traffic, even during a write outage.

How can a URL work with no saved route?

An auto-proxy name is useful when a new VM needs a URL before anyone saves a site route. Its hostname carries the tenant and VM numbers. OpenResty calculates the VM address directly, with no cluster write.

For example, take tenant 2 and VM 11 in region 1. VM 11 is the numeric part of an Atlas ID such as VM-00011. Atlas combines the tenant and VM numbers, then writes the result with digits and letters in base 36:

Numbers
(11 << 32) | 2 = 47244640258
Base-36 label
lpc8lqa
Example URL
site-lpc8lqa.par-1.example.com
Decoded address
fdaa:1:0:2::b

For this example, site- is a configured auto-proxy prefix. The proxy checks that prefix and decodes lpc8lqa. Its region configuration supplies fdaa:1. It then sends HTTP to port 80 on the calculated VM address.

The name carries VM identity, not host location. If the VM moves, WG Mesh still finds it. The name does not create a VM or grant access through tenant or guest firewalls.

Know the boundary: Auto-proxy works in the regional wildcard domain. Custom-domain HTTPS takes another path: the proxy passes TLS to the VM, which owns that certificate.
