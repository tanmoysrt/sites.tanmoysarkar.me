WG Mesh: how a VM packet finds its host

Every Atlas VM has a private IPv6 address that stays the same when the VM moves to another host. WG Mesh is the set of small eBPF programs that decides, for each packet, which host it goes to. It keeps no central map of VM locations.

Source: services/wg-mesh and docs/networking in frappe/atlas. Checked on 27 September 2026. All addresses on this page are examples.

The problem it solves

Atlas picks a host when it creates a VM. Other hosts must then find that VM before they can send it a packet. The VM address names the VM, not the host. After a migration the address stays and the host changes.

A central controller could push every VM location to every host. Then every move needs an update on every host, and one missed update sends traffic to the wrong place.

WG Mesh asks the network instead. When a host does not know where a VM is, it sends a Neighbor Discovery Protocol (NDP) question on the private host network: "who has this address?" The host that runs the VM answers. The sender stores the answer and sends later packets through WireGuard.

Atlas still assigns addresses and sends each host its WireGuard peers and the list of privileged VMs. It does not send a VM-to-host map. WG Mesh is not a daemon: it is eBPF programs plus a CLI that loads them and writes their maps.

Three layers

Each layer rides on the one below. A VM never sees the host tunnel or the provider network.

LayerAddressesJob
1. Host network (underlay)Provider private IPv4Carries packets between hosts. Also carries NDP lookups.
2. WireGuardfdab::/16, one per hostEncrypts all VM traffic between hosts. Every host has a tunnel to every other host in the region.
3. WG Meshfdaa::/16, one per VMeBPF decides where each VM packet goes, and drops what policy forbids.

Read an address

The address carries the facts the data path needs. The eBPF code reads the tenant field directly for isolation, so it needs no lookup to know who owns a packet.

fdaa | region 16 bits | tenant 32 bits | VM ID 64 bits     one per VM
fdab | host WireGuard address                              one per host

A privileged VM is a tenant-0 VM that Atlas lists during host sync, such as the HTTP proxy or the IPv6 router. It may talk to every tenant.

What runs on each host

All hooks are tc (Linux traffic control) eBPF programs. They come from one BPF object and share one set of maps pinned at /sys/fs/bpf/atlas-wg-mesh.

VM hookingress on each VM interface · bpf/vm.h

Checks every packet a VM sends. Then lets Linux deliver it, tunnels it, sends it to a gateway, starts a lookup, or drops it.

WireGuard hookingress on wg0 · bpf/wireguard.h

Runs after decryption. Removes the tunnel header and delivers, answers NOT_HERE, or handles a NOT_HERE.

Uplink hookingress and egress on the private uplink · bpf/uplink.h

Learns which host answered a lookup. In unicast mode it wraps NDP in IPv4 for each peer.

Public hookingress on the public interface · bpf/uplink.h

Answers NDP for public prefixes that a local VM owns. Forwards traffic for a prefix that moved away.

A remote_vms entry stays until LRU eviction or a valid NOT_HERE removes it. There is no timer.

The VM hook, in order

This order matters. For example, gateway routing happens before the source check for non-mesh destinations, and local delivery happens after the tenant check.

  1. Drop a packet to the host range fdab::/16.
  2. For a destination outside the mesh, check that the VM owns its source, then send it to the gateway that its route names. With no route, leave it to normal host routing.
  3. Drop a packet whose source address the VM does not own. Only a gateway interface may send a non-mesh source.
  4. Drop a packet to another tenant, unless one side is privileged.
  5. Drop a non-mesh source to a local VM that has no gateway route back to that source.
  6. Let Linux deliver a packet for a VM on this host.
  7. Tunnel a packet for a known remote VM through WireGuard.
  8. For an unknown destination, replace the packet with an NDP lookup. Each interface may start 10 lookups a second, with a burst of 50.

Discovery and moves

How a lookup works

The VM hook replaces the first packet to an unknown VM with a Neighbor Solicitation and sends it out of the private uplink. That packet's data is lost. The transport resends it.

On the host that runs the VM, vm sync added a proxy NDP entry (ip -6 neigh replace proxy) on the uplink. Linux answers for the VM with the host's uplink MAC.

The asking host's uplink hook reads the answer. It matches the frame's source MAC in peer_list and stores that peer's fdab address in remote_vms.

configure sets proxy_delay to 0 on the uplink. By default Linux waits up to 0.8 seconds before a proxy answer, and the mesh would drop packets for that time.

Multicast or unicast NDP

On a network that carries multicast, NDP works as normal. Some provider networks drop multicast. For them, peers sync --unicast attaches the uplink egress hook.

That hook wraps each solicitation (for a remote VM) and each advertisement (for a local VM) in an IPv4 header with protocol 41 and sends one copy to every peer. The receiving uplink hook accepts a wrapped packet only from a peer IPv4 address, learns from it, and removes the IPv4 header. The mode changes only discovery, not throughput.

When a VM moves

The new host runs vm sync, which sends an unsolicited Neighbor Advertisement. Every peer that hears it updates remote_vms at once.

NOT_HERE repairs a missed advertisement. The old host replies with IPv6 next header 253 and the VM address. The sender deletes the entry only if the reply came from the host that the entry names, then starts a new lookup. A host cannot erase an entry that points to a different host.

Next header 253 is an IPv6 value reserved for experiments. The format is Atlas-specific, not an Internet standard.

Gateway traffic

Some traffic has one end outside the mesh, such as a public IPv6 client. A gateway VM carries it. The mesh transports the packets and enforces two rules. The gateway's own software does address translation and firewalling.

A gateway VM needs two flags from Atlas:

FlagEffect in WG Mesh
PrivilegedThe address is in privileged_vms, so it passes the tenant check with every tenant. Tenant 0 only.
Network gatewayThe interface is in gateways, so it may send packets with a non-mesh source, and hosts can deliver gateway tunnels to it.

Gateway routes

A gateway route belongs to one VM. It says: for this destination prefix, send to this gateway. Example: 2000::/3 via fdaa:1::56 sends public IPv6 to the IPv6 router. vm sync --route 2000::/3=fdaa:1::56 writes it.

The gateway_routes key is the VM address followed by the destination. One longest-prefix trie therefore holds a separate table per VM. A route to 2000::/3 is stored with prefix length 128 + 3 = 131.

The same route also guards the way in. A packet with a non-mesh source reaches a VM only when that VM has a gateway route covering the source. So a public address that maps to a valid VM still gets nothing until Atlas attaches it and adds the route.

The gateway tunnel

A reply to a public client has a public destination. The receiving host could run several gateways and cannot tell which one to use. So the sending host uses IPv6 next header 254 and puts the 16-byte gateway address before the client packet.

It fits the tunnel MTU: 1380 (VM MTU) + 40 (outer header) + 16 (gateway address) = 1436, and wg0 carries 1440.

Public prefixes that move

The provider router sends a public prefix to one host and asks for each address with NDP. The public hook answers for addresses in owned_prefixes. The provider caches that host's MAC and does not ask again.

When the gateway moves, the old host keeps the prefix in moved_prefixes for 5 minutes and forwards its traffic through the mesh. The new host sees that forwarded packet and sends an unsolicited advertisement with the override flag. The provider then updates its cache. The first packet can be lost.

The tracer has both paths: Public IPv6 via router and Router moved. The IPv6 router maps public addresses to mesh addresses with bit arithmetic, so it needs no table. It changes the destination on the way in and the source on the way out, and the tenant VM sees the real client address.

Commands

The atlas-wg-mesh binary embeds the BPF object, so the host needs no Clang or bpftool. Run it as root. Metal calls it; these are for inspection and manual work.

# Load or upgrade the hooks. Loads new programs before it replaces any hook.
atlas-wg-mesh configure --uplink eno1.1680 --wireguard wg0

# Write the peer map. Add --unicast when the network drops multicast.
atlas-wg-mesh peers sync /var/lib/metal/wireguard-peers.json

# Register one VM. Replaces all its prefixes and routes.
atlas-wg-mesh vm sync --interface vh-100001 --address fdaa:1:10:20::5 --mtu 1380

# A gateway VM with a public prefix and a route
atlas-wg-mesh vm sync --interface vh-100002 --address fdaa:1:0:0::1 --mtu 1380 \
  --gateway --prefix 2001:db8:100::/64 --route 2000::/3=fdaa:1:0:0::2

# Look
atlas-wg-mesh status
atlas-wg-mesh inspect fdaa:1:10:20::5
atlas-wg-mesh vm list --json

inspect reports local state, a learned remote host, or an unknown location. Unknown is normal until a local VM sends to that address.

For a private traffic fault, check in this order: Metal's WireGuard peers, the VM namespace, then local_vms and remote_vms. WG Mesh cannot repair a wrong Atlas address or a missing Metal link.

Numbers from one test

Two Scaleway bare-metal hosts, 1 GbE private network, Firecracker guests with 2 vCPU. TCP with iperf3 for 10 seconds, single stream, median of 3 runs.

PathThroughputAvg ping
Raw private network939 Mbit/s0.28 ms
Host-to-host WireGuard886 Mbit/s0.76 ms
VM to VM, two hosts847 Mbit/s1.75 ms
VM to VM, one host14.3 Gbit/s0.92 ms

The mesh delivers 96% of WireGuard throughput. The cost is the 40-byte tunnel header and the smaller VM MTU. A new VM was reachable about 5 ms after vm sync, and a moved VM within one 10 ms ping. Full results: benchmarks.md.

Check yourself

The first packet to a new VM disappears. Is that a bug?

No. The VM hook turned it into an NDP lookup. The retry uses the location that the uplink hook learned.

Host 5 sends NOT_HERE for a VM that host 1 has stored at host 2. What happens?

Host 1 drops it. Only the host that remote_vms names can clear the entry.

Two VMs of different tenants are on the same host. Can they reach each other?

No. The VM hook checks the tenant before it hands local traffic to Linux.

Why does a reply to a public client use next header 254 and not 41?

The inner destination is public. The receiving host needs the gateway address to pick the right gateway VM.

A public address maps to a valid VM, but the VM gets no traffic. What does WG Mesh check first?

The VM's gateway return route, such as 2000::/3 via the router. Without it the WireGuard hook drops packets with a non-mesh source.

Why does configure set proxy_delay to 0?

Linux otherwise delays a proxy NDP answer by up to 0.8 seconds, and lookups would stall.

Limits

  • The first packet to a new or moved VM can be lost. Clients retry.
  • NDP trusts the private host network. It does not authenticate hosts by itself.
  • The mesh covers one region. It does not connect regions.
  • NOT_HERE (253) and the gateway tunnel (254) are Atlas formats, not standards.
