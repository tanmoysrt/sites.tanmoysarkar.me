Beacon: the Incident and Alert Manager

This guide is for a new engineer. It tells what we track, how we alert and who gets the call. It also tells how customers learn about a problem, and who fixes what. It covers every app that sends data to Beacon: Atlas, metald, Cargo, Datum, Central and Pilot.

State on 16 November 2026, read from the develop branch of each repository. Production rollout of Beacon is a later phase. Until then, the old Insights alerts stay on.

  • We page on symptoms and explain with causes. A fast burn of a service's error budget calls a person. About 70 cause rules name the broken host, node or app, so the responder knows where to start.
  • One problem gives one incident and one escalation. Beacon writes an alert only when its state changes. It groups related alerts into one incident. It calls a person only for High and Critical.
  • Each layer tells its own owner. One down site is the customer's problem, and Pilot tells the customer through Central. Many down sites on one server is ours, and Beacon calls the on-call responder.
  • A person decides what customers see. The status page shows the measured service status automatically. A person publishes an incident as Unlisted (link only) or Public. Beacon never publishes by itself.

1Goals

Four goals pull against each other. Every rule in Beacon is a choice between them.

Find problems before customers do

Measure what customers feel (the SLI) and watch the parts that break (cause rules). Probe public endpoints from outside the region.

Do not overwhelm engineers

Call a person only for customer impact. One problem gives one incident. Everything else goes to chat or email at a lower severity.

Find regressions

Catch new kinds of errors (error fingerprints), release-wide failures, error spikes against a baseline, and slow budget burn.

Communicate simply

One incident has one update stream and one link. Customers see the status page, an Unlisted link or an email from Central.

Non-goals. Beacon does not watch each site or each VM. Their own layer does that and tells the owner. Beacon does not write to ClickHouse. Beacon does not publish incidents or decide customer messages.

3Who owns what

Each layer watches the layer below it and tells its owner when one item fails. Beacon acts when a failure is too wide for one owner, or when a watcher stops.

A failure is always visible one level up. So Beacon needs no "not reporting" check for each site or VM.

4How data gets in

Almost every signal is a metric sample or a log line in the ClickHouse of one region. SQL rules and SLI queries read it there. HTTP and TLS rules are the exception: Beacon calls the endpoint directly.

  1. A producer sends a value to the Datum of its region with a token (a signed JSON Web Token, JWT). The token names the sender's resource ID, such as the Metal Server name of a host. The sender cannot change it.
  2. Datum checks the token and writes the rows. Datum refuses a whole request when one sample is not valid. No sender retries, so a failed request is a gap.
  3. Each Resource Source (the Atlas and Cargo of each region) serves a resource list each minute. Beacon keeps only rows whose resource ID is in this list, with its type and parent.
  4. Beacon runs each rule at its interval and each SLI query each minute, as the read-only beacon user. ClickHouse limits each query to 20 seconds, 4 GB and 100,000 rows.

6How a rule alerts

A rule is one query that returns only failing rows. Each row is one problem on one resource.

-- title: Host disk almost full        <- alert title
-- severity: High                     <- highest severity of this rule
-- resource_type: Metal Host          <- rows for other types are dropped
-- interval: 300                      <- run every 5 min
-- pending_for: 300                   <- must fail 5 min before it fires
-- resolve_after: 600                 <- 10 min clean before it recovers
-- runbook_url: https://...           <- required for High and Critical
SELECT resource_id, alert_key, value, detail, severity FROM ...

A query error never resolves an alert. A firing alert that stays the same causes no database write. An unchecked resource is one with monitoring disabled, or a Suspended or Terminated one.

Alert states

  • Severity can change. A Pending alert takes the severity of its current row. A Firing alert only goes up, and then Beacon announces it and calls again.
  • Timers restart after a gap. When the last good run is older than 3 intervals, Beacon restarts the pending and clean timers.
  • Retention. Beacon keeps Cleared alerts for 7 days and other resolved alerts for 90 days.

7How we limit noise

Each step removes alerts that a person does not need. Only the last step can wake someone up.

Rule design

  • Watch one level up. No rule for one site or one VM.
  • Send counts, not items. A site is never a label value.
  • Use a rate, such as 5 failed of 20, not a bare count.
  • Return a lower severity at a lower limit, such as Low at 25% disk free.
  • Each rule points to one fix and has a runbook.

Timing

  • pending_for is at least one interval, so an alert fires on the second failing run at the earliest.
  • resolve_after is at least 2 intervals, so it does not flap.
  • A new or returned resource is not checked for 10 minutes.
  • A child resource waits 90 s before a call, so its parent's incident can take it.

Suppression

  • Silence: mutes a known problem for up to 30 days, with a reason.
  • Maintenance: mutes its scope, plus 10 min after the end.
  • Held removal: a resource list that would remove over 10% waits for an admin.
  • Region Unreachable: one Critical alert; the region's SQL rules are skipped.

Feedback

  • A failure that repeats each minute writes one Error Log.
  • One chat message for each incident in each run.
  • Each week, review the alerts of each rule. Beacon Health lists the noisiest rules.

A Scheduled maintenance can be cancelled. You can extend the end while it runs. A maintenance mutes the resources in its scope. To also mute the SLO burn alerts of its regions, set Mute SLO Burn.

8SLI, SLO and outages

The SLO is the symptom side. It calls a person when customers feel a problem, even when no cause rule knows why. This section shows every number Beacon computes, with a worked example.

The four terms

TermMeaningExample: Proxy service
SLI (service level indicator)Good events divided by valid events, measured.1,998 good requests of 2,000 valid requests = 99.9%
SLO (service level objective)Our target for the SLI over 30 days. Default 99.9%.99.9%
Error budgetThe share of valid events that may fail in 30 days: 100% minus the SLO.0.1% of requests
SLA (service level agreement)A promise to customers. It must be equal to or lower than the SLO. Beacon reports on it and alerts before we break it.99.5%

A good event and a valid event depend on the service. Its SLI query in beacon/services/*.sql defines them. For Proxy, a valid event is a request, and a bad event is a 5xx error that the proxy made itself. A 5xx error from the site's own code is good for Proxy, because the customer owns that code. The rule: count only failures that the platform causes. Else a few broken customer apps use the whole budget of a region.

One measurement, each minute

A dead host makes its VMs silent, and the Host down alert makes them count as bad. A Pilot restart or a gap in Datum leaves the reporter out, so it never looks like an outage. When the query fails or returns no valid events, Beacon stores nothing for that minute and the status is Unknown.

Error budget: a worked example

The Proxy service of one region gets 2,000 valid requests each minute. 30 days have 43,200 minutes.

StepCalculationResult
Valid events in 30 days2,000 × 43,20086,400,000
Error budget, in events86,400,000 × 0.1%86,400 failed requests
Same budget, as a full outage43,200 min × 0.1%43.2 min
Bad events so far (10 days measured)from Service Days14,400
Valid events so farfrom Service Days28,800,000
Valid events projected to 30 days28,800,000 × (30 / 10)86,400,000
Budget left1 − 14,400 / (0.1% × 86,400,000)83.3%

Formula: budget left = 1 − (valid − good) / (error budget × valid projected to 30 days). Beacon projects only until 30 days are measured. The value shows as Budget left, 30 days on the service form and in Service health. It can go below zero: then we broke the SLO.

Burn rate

The burn rate is how fast we use the budget: (1 − SLI) / (1 − SLO). A burn rate of 1 uses the whole budget in exactly 30 days.

Each burn alert checks two windows. It fires only when the burn rate meets its limit in both. The long window shows that the problem is real. The short window lets the alert resolve a few minutes after the fix. Each limit comes from budget share × 720 h / long window: for fast, 2% × 720 / 1 = 14.4.

Example. In the last hour, 2.0% of Proxy requests failed. The 1 h burn rate is 2.0% / 0.1% = 20. In the last 5 minutes, 1.8% failed: burn rate 18. Both are at or above 14.4, so fast fires. The fix lands. The 5-minute window drops below 14.4 within a few minutes, so the burn stops, although the 1 h window still shows errors. After 5 more minutes without a burn, the alert recovers.

Four guards stop false calls:

  • A window with fewer than 100 valid events does not alert.
  • Service Minutes must cover half of the window, so a new service does not call on its first bad minutes.
  • A burn calls only when 3 reporters were bad in one minute of the short window (or all, when fewer than 3 report). Else it is Low, because one bad reporter has its own cause alert.
  • A service with Page On Burn off gets Medium instead of High.

A burn alert is a normal alert. Its resource is the region (or the global resource for a global service). It fires at once (no wait) and recovers after 5 minutes without a burn.

Status of a service

A worse status must hold 3 min and a better one 2 min before it shows. Maintenance shows at once. A published outage on the same service outranks Maintenance. The status page shows the worse of this status and the impact of open published incidents. A published impact never makes the status better.

Example. A region has 3 proxies with equal traffic. One proxy is down and its node has a firing cause alert. The SLI is about 67%. That is under 95% and above 50%, so after 3 minutes Proxy shows Partial Outage. When a second proxy fails, the SLI is about 33% and Proxy shows Major Outage.

Example. A day has 10 Major Outage minutes and 20 Partial Outage minutes. Downtime = 10 + 0.3 × 20 = 16 min, so the bar is red. A bad minute that does not hold 3 minutes lowers the uptime. It does not change the status, so it is not downtime.

A declared outage (a Public incident with an impact) changes the status and the bar color. It does not change good and valid, so uptime and the error budget stay measured. A Declared service, such as Billing, has no SLI: its status comes only from published incidents, and the page says Set by incidents, not measured.

9Alerts to incidents

An incident is the record people work on. The rule: after each evaluation and region run, every firing, unsuppressed alert belongs to an open incident.

A join is never silent. Beacon posts one chat message for each incident in each run. A higher severity calls again.

Scope. An incident starts with the scope of its first alert, such as "host h12 and everything under it". Beacon computes affected resources only when a person asks. When a new incident covers alerts of another open, Internal, unacknowledged incident, those alerts move, and the empty incident closes as Merged.

Incident states

Inside Open, Post Update can set any of the three statuses from any other. A new alert moves Monitoring back to Investigating.

  • Auto resolve. When all alerts recover, Beacon resolves an Internal incident that it made. For an Unlisted or Public incident, Beacon posts to chat that a person must resolve it, so the customer gets a final update.
  • Beacon refuses Resolve while unsuppressed alerts still fire, unless the person sets Silence Hours.
  • Beacon requires a postmortem when the incident was Public or Critical, took over 1 hour, or a customer found it first. Beacon reminds in chat each day from day 3 to day 30.

11Calls and acknowledge

Beacon calls one responder at a time from an ordered list. An answered call acknowledges the incident.

  • Beacon calls the primary override until its end time, else the first active responder. Each responder must be an enabled user with the Beacon Responder or Beacon Admin role.
  • Staff can also acknowledge in Desk, or with POST /api/v2/document/Beacon%20Incident/<name>/method/acknowledge.
  • A failed call or email posts to chat who did not get it.
  • Notification states. Each call, email or chat post is one Beacon Notification row: Queued, then Sending, then Sent, Failed or Cancelled. Cancelled means notifications were paused, or the channel or responder was disabled. A row that stays in Sending means the worker stopped during the call to the provider. Beacon does not send it again, because the provider may have it. For email, Sent means Frappe accepted it into its Email Queue; check the Email Queue for delivery errors.
  • Each minute Beacon sends a heartbeat to an external service. Beacon holds the heartbeat when a rule evaluation or a notification is over 5 min late. Then the external service calls the team, because Beacon or its workers stopped.

A platform incident, from alert to customer

  • Visibility is Internal (staff only), Unlisted (anyone with the link) or Public (listed). Every incident starts Internal. Beacon never publishes and never reopens a public incident.
  • The link has a random public ID, so no one can guess it or count incidents. Regenerate Link stops the old one.
  • Followers confirm by email. Confirm and stop links open a page with a button, so link scanners change nothing.
  • Status page methods are guest methods. They return only published data and cache each result for 60 s, so outage traffic never reaches ClickHouse.

14Example: a host fails

A host with 30 VMs and 400 sites loses power at 10:00. The times are approximate.

  1. Pilots in the VMs go silent. No cause alert covers them yet, so the Sites SLI leaves them out. A Pilot restart looks the same and must not call.
  2. After 5 min the Atlas sync is old and metald is silent. host-down returns the host. After one more run it fires.
  3. Beacon opens an incident with scope "this host and everything under it". The host has no parent, so the call starts at once.
  4. Now a cause alert covers the silent reporters, so the SLIs count them as bad. A burn alert that fires later joins the same incident by pairing.
  5. The responder answers. Beacon acknowledges. The responder publishes as Unlisted and gives the link to support.
  6. The host comes back. The alert recovers after 2 min. The incident is Unlisted, so Beacon asks a person to resolve it. The responder posts a final update and resolves.

15Working in Desk

Engineers do all Beacon work in Frappe Desk. Each flow below shows what Desk does today and what we propose to make it easier. Proposals are not built yet. Each needs a mockup and approval first.

Five rules for every Beacon form.

  1. The next step is the one primary button. Today Acknowledge does this while an incident is Triggered.
  2. The runbook is one click from the call.
  3. A field that drives a state machine is read-only. Only an action changes it, and the action dialog asks only for what it needs.
  4. A confirmation says what happens next, such as "Phone calls cost money".
  5. A problem with Beacon itself shows on the Beacon home screen, not only in a log list.

17Glossary

RegionOne Frappe Cloud region, with its own Datum and ClickHouse.
ResourceOne thing Beacon watches: a host, a VM, a service node, an app such as Atlas, or the region.
Resource IDThe name of the sender, written by Datum from the token.
RuleA SQL, HTTP or TLS check that returns failing rows.
AlertOne problem on one resource, from start to end.
IncidentThe record people work on. It holds alerts, updates, calls and the postmortem.
ScopeThe part of the region an incident covers, such as a host and its VMs.
ServiceOne line on the status page, with an SLI and an SLO.
ReporterA resource that sends SLI events, such as a Pilot VM.
Bad reporterA reporter that sent bad events in the last minute. Used to pair burn and cause alerts.
Burn rateHow fast a service uses its error budget. 1 means the budget lasts exactly 30 days.
SilenceA time-limited mute for a known problem.
MaintenancePlanned work with a start, an end and a scope. Mutes alerts in its scope.
RunbookThe steps for a responder. Required for each High or Critical rule.
JWTA signed token. Datum reads the sender's resource ID from it.
Error fingerprintOne kind of error: the same exception at the same place, counted together.
BMCThe management chip of a physical server. It reports hardware events.
eBPFA small program in the Linux kernel. The IPv6 router uses one to forward traffic.
QuorumThe minimum number of storage nodes that must agree before object storage accepts a write.
Unchecked resourceA resource with monitoring disabled, or one that is Suspended or Terminated. Beacon drops its rows.
CoverageThe share of a day's minutes that Beacon measured.
