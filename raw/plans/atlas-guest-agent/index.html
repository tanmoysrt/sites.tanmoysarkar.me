Atlas guest agent plan

One small Go program inside each VM gives Metal what the hypervisor cannot see: guest load, free memory and disk use. This plan adds four guest jobs to it. For each job it shows the methods on each side, the timeouts and the fallback when the agent is missing or stops.

Context

Metal runs each VM in Firecracker. From the host, Metal can read CPU time and disk counters from the VM cgroup. It cannot read the guest load average, the guest page cache or how full the guest file system is. Those values exist only inside the guest kernel.

The guest agent is one static binary, atlas-guest-agent. The image builder installs it in every Atlas image. Because it is static, it does not depend on the guest distribution or on Python. It also replaces the two Python guest scripts: the metadata service poller and the SSH key lookup.

The agent never starts work by itself, except the metadata poller. Metal asks, the agent answers, and Metal always has a fallback when there is no answer.

One transport for all jobs

Metal talks to the agent over vsock. vsock is a socket between a VM and its host. It does not use the guest network, so a guest firewall, Docker rules or a broken network configuration cannot block it. Only the host can open a connection to the guest, so the agent needs no token.

Firecracker exposes the vsock device as a Unix socket in the VM jail. metald dials a short link to it, /run/metal/<vm-id>.vsock, because a jail path can be longer than the 108-byte Unix socket limit. metald sends CONNECT <port>, and Firecracker answers OK <host port> when the guest accepts.

In the guest, systemd holds one socket for each job (socket activation). systemd starts one short agent process for each connection. No agent daemon runs between requests, and no unit blocks boot.

Each job has its own port. A port above 65535 cannot clash with a service that reuses a TCP port number.

Each caller sets its own deadline. Every error, such as no socket, a refused port, a timeout or a bad reply, means "agent unavailable" for that call.

The metrics sampler reads one JSON line every 10 seconds from each running VM. metald does not ask a paused VM, because a paused guest cannot answer.

Freeze for clean snapshots

Problem. To capture a running VM, Metal pauses the vCPUs, takes a ZFS snapshot and resumes. The image is crash-consistent: it is equal to a disk after a power loss. Writes that the guest still holds in its page cache are not in the image, and the first boot replays the file system journal.

Change. Before the pause, the agent asks the guest kernel to freeze each file system. A freeze writes all cached data and the journal to disk, then blocks new writes. After the snapshot, the agent thaws the file systems and writes continue.

Methods

// guest side: guestagent/freeze.go
func FreezeFilesystems(connection io.ReadWriter) error

// host side: firecracker/guest_agent.go
func (runtime *Runtime) FreezeGuestFilesystems(ctx context.Context, machine vm.RuntimeMachine) (thaw func())

// vm.Runtime interface: same signature. Caller: vm.Manager.CreateSnapshot

Agent behavior

  1. Read /proc/self/mounts. Select each writable mount on a /dev/ block device. Freeze each device only once, because a bind mount shares the same file system.
  2. Freeze in mount order with the FIFREEZE ioctl. If one freeze fails, thaw the ones that are frozen and reply error <reason>.
  3. Reply frozen. Then wait until metald closes the connection, or 30 seconds, whichever comes first.
  4. Thaw in reverse order with FITHAW. The thaw also runs on SIGTERM.
  5. Write no log line while frozen. A log write to a frozen disk would block the agent.

Grow the root file system

Problem. Atlas can make a VM disk larger while the VM runs. The guest kernel sees the larger disk, but the root file system keeps its old size until a reboot.

Change. After metald applies a new disk size to a running VM, it asks the agent to grow the root file system online.

Methods

// host side

// vm.Runtime interface: same signature.
// Caller: vm.Manager.applyDesiredSpecification, after RefreshDisk, only when the VM is running.

Agent behavior

  1. Find the root mount in /proc/self/mountinfo. Read its device number and file system type. /proc/mounts can show /dev/root, which has no device file, so the agent uses /dev/block/<major>:<minor>.
  2. Run resize2fs for ext4, or xfs_growfs / for XFS. A disk that is already full size is a quick no-op.
  3. Reply ok, or error <reason> for another file system type or a failed command.

Fallbacks

CaseWhat happens
No agent, error reply or no reply in 30 secondsmetald logs a warning. The disk change still succeeds. The file system grows at the next boot, when cloud-init runs its resize step.
metald disconnects during a long resizeThe agent lets the command finish. An online grow is safe to run again.

The 30-second limit keeps the reconcile pass short, because it runs while metald holds the VM operation lock.

Clean stop and boot state

Clean stop

Today. To stop a VM, metald sends Ctrl-Alt-Del. systemd in the guest shuts down the services, then reboots. Firecracker exits on a guest reboot, because it has no power-off. After a timeout, metald kills the process.

Gap. An image can mask ctrl-alt-del.target. Then Ctrl-Alt-Del does nothing and every stop waits for the full timeout, then kills the guest.

Change. metald asks the agent first. The agent replies ok, then runs systemctl reboot --no-block. The reply comes first, so metald does not wait for the shutdown to answer.

// guest side
func RequestReboot(ctx context.Context, connection io.Writer) error

// host side, firecracker/machine.go

    // 2. if that fails: Ctrl-Alt-Del, as today

    // 4. SIGKILL, as today

Boot state

The usage report adds system_state, the output of systemctl is-system-running. Values include starting, running and degraded. It shows when the guest finished boot, and whether a unit failed.

If the command fails or takes more than 2 seconds, the field is empty and the rest of the report is unchanged. In this plan, metald only reports the value. It does not change any decision, such as the SSH check after a migration. That can follow when the value proves reliable.

Upgrades

The agent ships inside the image. A new image gives new VMs a new agent. A running VM keeps its agent until it is rebuilt from a new image. There is no self-update.

This is safe because the contract only grows. New fields in the usage report are optional, and each new job uses a new port. So any metald works with any agent version, and an old agent only misses the newer jobs.

Tests and rollout

Focused tests

  • Guest: parse /proc/self/mounts for freeze targets (bind mounts, read-only mounts, non-block mounts), and parse /proc/self/mountinfo for the root device.
  • Host: CreateSnapshot calls thaw after resume, and works when the freeze is unavailable.
  • Host: the vsock handshake reads a reply and treats a refused port as unavailable (exists).

Development host checks

  1. Build an Ubuntu 24.04 image from the branch. Create a VM.
  2. Machine image of a running VM: check frozen in the guest journal, and a clean mount without journal replay.
  3. Kill metald during a freeze: the guest thaws within 30 seconds.
  4. Grow the disk of a running VM: df / shows the new size without a reboot.
  5. Mask ctrl-alt-del.target, then stop the VM: it stops before the timeout.
  6. Live migration with a memory snapshot: the usage report continues on the destination.

Rollout

  1. Upgrade metald. Nothing changes for running VMs.
  2. Rebuild images. New VMs get the agent. Existing VMs get the vsock device at their next cold boot.

Decisions

  1. Agent upgrades only through a new image. No self-update.
  2. Ports 100000 to 100003, one systemd socket for each job.
  3. Timeouts in the table above, especially the 30-second automatic thaw.
