Pilot Metadata Config Patches

A plan to replace fixed config blocks in instance metadata with generic JSON patches. Plan Proposed

The situation

Pilot manages Frappe benches on a host. When a new VM starts from an image, Pilot reads its first settings from instance metadata. Instance metadata is a small key-value service that the cloud makes available inside the VM at 169.254.169.254. Each key is an attribute.

Today Pilot reads three fixed attributes. Each one has its own required keys, its own parser and its own write function.

AttributeContentWritten to
pilot-centralCentral endpoint, token, JWKS URL and audiencecommon_config.toml
pilot-storageSix fixed S3 keysbench.toml [s3]
pilot-telemetryEndpoint and token[telemetry]

To deliver one more setting, a developer must add a key list, a parser, a write function and a docs change. Also, the cloud limits each attribute value to 1 KiB.

Before: one custom code path for each attribute.

The idea

Deliver settings as a patch. A patch is a JSON object that describes only the changes to make to a config file. Each top-level key names a target file. Pilot merges each value into its target.

{
  "common_config":      { "proxy": { "protocol_v2": true } },
  "bench_config":       { "gunicorn": { "workers": 4 } },
  "common_site_config": { "max_file_size": 104857600 }
}

The three targets are the files an operator usually changes:

TargetFileScope
common_configcommon_config.tomlAll benches on the host
bench_configbench.tomlOne bench
common_site_configsites/common_site_config.jsonAll sites of one bench (Frappe reads it)

After: one merge step for all settings. The Central credential stays structured.

How a patch merges

Pilot uses JSON Merge Patch (RFC 7396). It is a published standard, so Pilot does not invent its own rules. The rules are:

  • An object merges into the object at the same key. The merge is recursive.
  • A scalar or an array replaces the old value.
  • null deletes the key.

Example. The file has {"s3": {"bucket": "a", "region": "x"}}. The patch is {"s3": {"bucket": "b"}}. The result is {"s3": {"bucket": "b", "region": "x"}}.

If Pilot applies the same patch two times, the result does not change. Thus a retry after a partial failure is safe.

Large payloads

A useful patch can be larger than 1 KiB. Pilot reads pilot-config, then pilot-config-1, pilot-config-2 and continues until an attribute is missing. Each attribute is a complete patch. Pilot applies them in order.

Pilot does not join chunks into one string. If one chunk of a joined string is missing, the full payload becomes incorrect JSON.

Safety rules

  • Locks. Each target uses the lock and atomic write that Pilot already uses for that file. A CLI call, an Admin request and a task worker can change the same bench at the same time.
  • Validation. Pilot validates the merged result before it writes. Unknown keys in a TOML target cause an error, so a spelling mistake does not disappear silently. External URLs get the same checks as before.
  • Failure. A bad patch stops the bootstrap with an error. The bootstrap watcher tries again. The host does not show as bootstrapped with a half-applied config.
  • Trust. Only the cloud can write instance metadata, and it already delivers credentials. Thus every key is writable. The validation is the limit.

When it runs

Pilot applies the patches one time, at bootstrap, before it marks the host as bootstrapped. Pilot does not watch for later changes. Usually a host gets its settings only when it starts for the first time.

Compatibility

  • pilot-central does not change. It controls the bootstrap state and fills the JWKS key cache, so it stays structured.
  • pilot-storage and pilot-telemetry continue to work. Pilot converts each one into a patch on the same path. The old custom code is removed.
  • The stored config does not change shape, so no data migration is necessary.

Open points

  • Per-site site_config.json targets (for example "sites": {"site.local": {...}}) are not in the first version.
  • If the cloud can list attributes, Pilot can find pilot-config* by prefix instead of probing numbers.

Next steps

  1. Add a raw, validated read-modify-write mode for common_config.toml.
  2. Add the merge and target code, and read the pilot-config* attributes.
  3. Move pilot-storage and pilot-telemetry onto the patch path.
  4. Add tests: merge rules, each target, unknown keys, chunk order, retry after failure.
  5. Update the configuration docs.
