Run OCI images on Atlas: findings and plan

Draft for discussion. Date: 3 November 2026. No Atlas code has changed. The test code is outside the repository.

Result. Docker Hub images boot on Firecracker with no Docker and no container runtime in the guest. We unpack the image into an ext4 disk, add one small init program, and boot it with the Ubuntu kernel that Atlas already uses.

Recommendation. Follow the Fly.io model for the guest. Keep the Atlas storage path: an image becomes a normal Virtual Machine Image with an ext4 root file system. Then ZFS clones, object storage, and host caching work with no first-phase change to the Metal API.

Evidence. nginx from Docker Hub answered HTTP 200 over a TAP device about 840 ms after Firecracker started. A graceful stop, disk growth, and a restart with data also worked.

Limit. All tests ran on a laptop. Nothing ran on an Atlas host or through metald yet.

Why this needs more than an unpacked image

An OCI image is a list of file system layers and one small configuration file. A layer is a tar archive of changed files. The configuration gives the program to start, its environment, its user, and its working directory. Docker Hub stores images in this format.

An OCI image is not a bootable machine. It has no kernel and no init program. Init is the first process that the kernel starts. The image also does not know how to configure the Atlas network.

Today, each Atlas guest gets these jobs from Ubuntu: systemd, cloud-init, apply-metadata, and SSH. Many Docker Hub images have none of these. Some have no shell and no Python. Our init must do the jobs that an Atlas VM needs.

What matters for Atlas. Fly needs containerd and devmapper to get thin copy-on-write disks on a host. Atlas already has this with a ZFS volume per image and a ZFS clone per VM. So Atlas does not need containerd.

The DigitalOcean warm path is under 200 ms at p50 in its internal tests. It starts from an existing checkpoint and warm caches, and it excludes first-time image import. Atlas warm images already use a similar idea. Lazy chunk loading is a separate, later project.

What we tested

We pulled nine images from Docker Hub with skopeo, flattened the layers, and applied whiteouts. A whiteout is a marker in a layer that deletes a file from a lower layer. Then we built ext4 with mkfs.ext4 -d, added a 2.8 MiB static Go init, and booted the disk.

Conditions: Fedora laptop on NVMe, Firecracker 1.16.1, Ubuntu kernel 7.0.0-42 (the Atlas HWE kernel source), 2 vCPUs, 1024 MiB memory, one attempt per image unless noted. Findings that change the design

  1. Do not mount over image directories. Our first init mounted a tmpfs on /run. This hid the /run/mysqld directory that the MariaDB image ships, and the entrypoint failed. We removed the mount and set MARIADB_ROOT_PASSWORD, and the server started. Init must match Docker here, even though Fly mounts /run.
  2. The Ubuntu kernel ignores ip=. The boot log says Unknown kernel command line parameters "ip=...". So eth0 stayed down and our first network test got no answer. Today, Ubuntu guests get their address from a systemd-networkd file in the image. Init must set the address itself. It can read the ip= value that Metal already sends from /proc/cmdline. The comment on bootArguments in Metal does not match this kernel.
  3. An exit is a normal event. ubuntu, python, and node exit at once with code 0, because they expect a terminal. Metal starts a stopped guest when its desired state is running, and a successful start gets no backoff. We read this in the code and did not run it on a host. So an exit that powers off the guest would become a boot loop. See decision 2.
  4. Images are small, so disks can be small. Our test disks were 276 to 819 MiB. The Ubuntu base is a fixed 4 GiB. The VM disk grows from the image size, so init must grow the file system itself. Ubuntu does this with cloud-init today.
  5. Whiteouts are real. postgres and mariadb each had 2. A plain tar extraction would keep files that the image deleted. The converter must handle whiteouts, and opaque whiteouts too, though none appeared in this set.
  6. Each entrypoint expects a different stop signal. nginx declares SIGQUIT and postgres declares SIGINT. Metal stops a guest with Ctrl+Alt+Del. By default the Linux kernel reboots at once on this event. Init turns this off with LINUX_REBOOT_CMD_CAD_OFF, receives SIGINT, and sends the image stop signal. This worked in the second round.
  7. Kernel modules are large. The Ubuntu modules package is 166 MiB compressed. Ubuntu images install it so that Docker and BPF work in the guest. Start without it. An image that needs modprobe will not get that module.
  8. Docker Hub limits are low for a fleet. The docs give 100 pulls per 6 hours per IP for anonymous use, and 200 per 6 hours for a free account. The response headers we saw said 100;w=3600, so the docs and the headers differ. Docker also warns about abuse limits for platforms that pull for many users from one address. Pull each digest once. Do not pull once per host.

Proposed design

Trace one image

  1. An operator runs a command with nginx:1.29-alpine. The converter resolves the tag to a digest. Atlas stores the digest, because a tag can move.
  2. The converter reads the amd64 manifest, applies the layers in order, adds init and /.atlas/image.json, and builds ext4. It never mounts the result on a host.
  3. Atlas uploads the compressed disk and creates a Virtual Machine Image. It links an existing kernel record. It gets the tag purpose=oci, so get_latest_base_image ignores it.
  4. A VM create request sends the same Metal image object as today: URLs, digests, and architecture. Metal downloads, verifies, clones, and boots, with no OCI knowledge.
  5. Init configures the guest, then starts the entrypoint.

Decisions for discussion

  1. Who uses this first? Operator-selected images, or tenants? Recommendation: operators first. Tenant import brings the untrusted archive problem, registry credentials, and quotas.
  2. What happens when the entrypoint exits? Options: power off, or keep the guest up and restart the program. A power off needs a Metal change, because Metal starts the guest again while the desired state is running. Recommendation: init restarts the entrypoint with a delay that grows to 60 s, and writes the exit code to the console. The VM stays Running in Atlas, so a failing program does not show in the VM state. Exit codes in the API can come later.
  3. Does the root disk survive a restart? Fly resets by default. Atlas VMs keep their disk. Recommendation: keep the disk. This is the current Atlas contract, and migration, snapshots, and databases depend on it. A reset mode can come later.
  4. What does user_data do on an OCI image? It has no cloud-init. Recommendation: reject the request with a clear error, and do not ignore it silently. This is a new image kind, so no existing client breaks.
  5. How does a person get a shell? Fly has SSH and an API built into init. DigitalOcean has an exec API. Many images have no shell. Recommendation: first phase shows output on the TTY console only. Then add exec through init over vsock or the serial console. The Atlas SSH console needs an SSH service and the key lookup in the guest, so it does not work on these images. The TTY console collects output while the VM runs.
  6. How does an image update work? The disk holds both the image files and the data, so a new image cannot replace the old one in place. Recommendation: a new image means a new VM until network volumes exist. Fly can replace it because its volumes are separate. This is the largest product difference from Fly.

Risks and limits

  • Untrusted archives. Path traversal, symlink escape, and decompression bombs are the main risks. Mitigations: limits, path checks, and option C for tenants. Atlas already accepts tenant-controlled ext4 through Machine images, so the host risk from the disk itself is not new.
  • Logs. Application output goes to the serial console, which replays only recent output. There is no durable log store in this plan.
  • Kernel features. With no modules, images that need extra netfilter or similar modules can fail. We need to test which features are absent.
  • Time sync. The guest has no time service. Metal steps the clock after a restore. Long-term drift is not measured.
  • Registry dependency. After import, the image lives in Atlas object storage. So a Docker Hub outage stops only new imports, not VM starts.
  • Licenses. Atlas stores a copy of each third-party image. Check this for images that an operator publishes to all tenants.

Not tested yet

  • Anything on an Atlas host: metald, jailer, ZFS, cgroup limits, mesh IPv6, public access, migration, sleep, warm start, and rescue.
  • The Metal reaction to a guest exit. We read the code only.
  • Applying metadata from MMDS: mesh address, host routes, hostname, and clock step. The test address was fixed. Ubuntu memory use, for comparison.
  • A disk resize while the guest runs. The growth test ran at boot.
  • The reasons that Traefik did not open port 8080. It likely needs configuration, which we did not give it.
