Plan: multi-tunnel WireGuard mesh

Spread VM traffic between two hosts over N WireGuard tunnels instead of one. Each VM flow uses one tunnel, so many flows can use the full 50 Gbit/s bond.

Status: proposed, not built. Measurements: WireGuard multi-tunnel throughput.

Why

The mesh sends all VM traffic between two hosts through one WireGuard interface, wg0. One tunnel stops at about 10 Gbit/s, because WireGuard does some per-peer work on one CPU. The bond under it carries 50 Gbit/s.

Tests with temporary interfaces showed that 16 parallel tunnels with distinct ports carry 45 to 49 Gbit/s. This plan makes the mesh use that design for VM traffic.

Goal and limits

  • Goal: traffic between two hosts can use both links and many CPUs. The target is more than 30 Gbit/s between two hosts with many flows.
  • No change by default: with a tunnel count of 0, hosts work as they do today.
  • No packet reordering: all packets of one VM flow use the same tunnel.
  • Not a goal: one VM flow stays at about 10 Gbit/s. One flow cannot use more than one tunnel without reordering.

How a packet moves

Today, the VM hook adds an outer IPv6 header to a VM packet. Linux then routes the packet to wg0 with the route for the remote host. With this plan, the VM hook also selects a tunnel and sends the packet to it directly.

Green boxes are new. The tunnel number i is the same on both hosts.

Example. A VM opens two TCP connections to a VM on another host. The kernel hash of the first connection gives tunnel 3. The hash of the second gives tunnel 11. All packets of each connection stay on their tunnel. The two connections use different CPUs and can use different links.

The port plan

The bond selects a link from a hash of the IP addresses and the UDP ports. The hash combines the two ports with XOR. If a tunnel uses the same port on both hosts, the ports cancel out. Then all tunnels between two hosts get the same link. The first test showed this: 5 tunnels gave 24.5 Gbit/s on one link.

A fixed port list on every host has the same problem. If every host uses 51840 + N for tunnel N, tunnel N always has equal ports on both ends. So each host needs its own port pattern.

Rule

port(host, N) = base + 4·N + 2·bit(host, N)

bit(host, N)  = bit N of a hash of the host's WireGuard public key

The 4·N part gives each tunnel its own port. The 2·bit part changes one bit that the bond hash uses for the link choice. Two hosts have different bits for about half of the tunnels, so about half of the tunnels use each link.

Illustrative values with base 51840. The real link also depends on the IP addresses, which are the same for all tunnels of a host pair.

Atlas computes the ports and sends them to Metal. The ports are explicit data, not a rule that each host must compute the same way. A unit test applies the kernel bond hash to every host pair and checks that each pair uses both links. The switch selects the link on the receive side with its own hash. More tunnels make that choice more even.

Changes by component

WG Mesh dataplane services/wg-mesh

  • Add a new array map mesh_tunnels with one value: {count, ifindex[32]}. A new map is safe for old programs, because they do not read it.
  • In add_mesh_tunnel(), read bpf_get_hash_recalc() before the outer header is added. This is the kernel hash of the inner flow.
  • After the header is written: if count > 1, return bpf_redirect(ifindex[hash % count], 0). If not, return TC_ACT_OK, as today.
  • The host hook and gateway tunnels use the same function, so they get the same behavior.
  • Attach the WireGuard ingress hook to every tunnel interface. NOT_HERE replies already use the interface that received the packet.
  • CLI: configure --tunnel wg1 --tunnel wg2 … fills the map and attaches the hooks. Upgrade and rollback attach on every interface.

Metal metal/internal/network

  • The WireGuard manager applies the same peer set to wg0 and to each tunnel interface. For tunnel N, the endpoint is <peer address>:<peer port N>.
  • Linux peer routes stay on wg0 only. Redirected packets do not use routing.
  • The sync request gets an optional tunnel_ports list for each peer. When it is missing, Metal uses only wg0. Old clients keep working.
  • Metal reads its own ports from its own entry in the peer list.
  • Metal fills mesh_tunnels only when every peer has the same tunnel count. A redirect to a tunnel that the peer does not have would drop the packet.

Atlas atlas

  • Add a region setting for the tunnel count. The default is 0.
  • Compute and store the port list for each Metal Server with the rule above. Send it in the sync request.
  • The host WireGuard script creates wg1 to wgN with the same private key and MTU as wg0, and with its own port. They get no address and no peers. With the same key, Atlas keeps one public key for each host.
  • The host firewall accepts the tunnel UDP ports from the private network.

Docs and telemetry

  • Update the WG Mesh design page, the Metal network specification, and the operations page: how to enable it and how to check the link split.
  • Add the transfer of all tunnel interfaces to the host WireGuard metrics, not only wg0.

Risks

  • Mixed tunnel counts drop traffic. Metal enables tunnels only when every peer has the same count. Atlas enables the region setting only after all hosts are upgraded.
  • A WireGuard restart detaches eBPF hooks. Today this is true for wg0. The same is true for every tunnel interface, so the attach code must cover all of them.
  • The redirect skips the host FORWARD chain. This is safe: the VM firewall runs in the VM namespace before the hook, and the host firewall covers only INPUT.
  • More peer entries. 16 interfaces with about 100 peers each give about 1,600 peer entries for each host. Keepalives cost about 64 packets per second.
  • Interfaces without an address. We expect wg1 to wgN to work without an IPv6 address. We check this in development first.
  • Link balance is statistical. The port plan balances the send side. The switch balances the receive side with its own hash.

Rollout

  1. Ship with the count at 0. Release WG Mesh, Metal and Atlas together. Hosts work as before.
  2. Development. Enable 16 tunnels on three test hosts. Check NDP lookup, NOT_HERE recovery, VM migration and gateway traffic on the tunnel path.
  3. Staging. Enable the region setting. Run iperf between VMs on different hosts with many flows.
  4. Production, one region at a time. Upgrade Atlas and metald in the region, then set the tunnel count.
  5. Rollback. Set the count to 0. Metal empties the map, and traffic uses wg0 again. No restart is necessary.

Open decisions

  1. Tunnel count. 16 for each region, the same on every host?
  2. Keys. The same private key on all tunnel interfaces, so that Atlas keeps one public key for each host?
  3. Enablement. For the whole region after all hosts are upgraded, or a fallback for each peer? The fallback needs more code.
