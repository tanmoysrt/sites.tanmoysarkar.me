Pilot startup and recovery audit

Pilot must show a usable page while a bench starts or recovers. This audit checks a new self-hosted install, a cloud-managed install, and a warm host that waits for cloud configuration. It also checks whether a user can retry after a task stops.

How can a signed-in site arrive within 20 seconds?

Lite mode is working on the audit VM. Pilot develop starts Frappe version-16-hotfix with web, jobs, and realtime in frappe.runner. A signed-in browser, a queued job, and a realtime handshake all passed. This confirms the runtime combination. It does not measure the complete cloud signup path.

The critical path is: Central queues the request → Atlas places the VM → Metal restores local memory and disk → the guest applies identity, time, and cloud configuration → Central sees the site → Pilot creates a session → the browser opens the app. Image building and the five-minute warm capture happen before signup. They must not enter this path.

Recommended sequence and ownership

  1. Cargo builds and validates. Pin Pilot and Frappe revisions. Enable lite mode. Install apps, migrate, build assets, and warm the real product landing page. Test login and a job. These steps happen before publication.
  2. Atlas stays unchanged. The user excluded Atlas changes. Its five-minute capture remains fixed. Cargo keeps incomplete preparation pending and lets systemd retry, including after restore. This improves recovery but cannot prove that every captured guest completed warmup before capture.
  3. Atlas restores generic VM state. Keep CPU, memory, local artifact, and runtime compatibility checks. Metadata is already replaced before vCPU resume. The guest metadata agent already applies host time before network identity. Preserve these useful invariants.
  4. Pilot applies tenant identity, then publishes readiness. Apply cloud configuration and seed the signing keys. Keep the pending page until the actual product page and session exchange can work. A ping alone does not validate authenticated app boot or its assets. Do not restart the ready database or rebuild assets at this point.
  5. Central hands off immediately. Create the Site record before optional remote administration. Use the automatic wildcard hostname for first access. Keep the requested domain change after login. Prefer adding a primary domain to a stable internal site name instead of moving the site directory.
  6. Frappe stays unchanged. The user excluded framework changes. Pilot keeps its existing session creation path and its measured interpreter cost. Cargo now warms the real Pilot login API and logs out afterward, without resetting Administrator's password. A future warm-handler session exchange remains an optimization proposal, not part of these PRs.

A shared password or baked session is not needed. Sessions and passwords in a memory snapshot are copied to every clone. Cargo already logs out its warmup session. Keep that behavior. A fresh session from a warm handler removes the interpreter cost without sharing a credential. Review and replace other image-wide secrets before enabling customer access.

Hypotheses still to test

Rename race. Pilot moves the site directory, reloads nginx, and immediately removes the compatibility link. nginx reload is asynchronous. An old worker or in-flight request can still name the old path. A direct request for an absent site returned HTTP 404, not the reported plain HTTP 500. This is a credible brief 404 path, not a proved cause of that plain-text error. Test slow requests and overlapping login during a real rename. A stable internal site name avoids this class of problem.

Readiness gap. Central uses a public ping before creating a session. A ping can succeed while the product landing page, user creation, or session exchange still fails. Test those three steps independently with the actual product apps and a newly created user.

Warm fallback and resource pressure. Missing host artifacts, a shape mismatch, or a restore failure can cold-boot. The current VM test does not measure this. Use Metal's existing boot kind and started/reachable metrics, then add the same request identity to Central, Pilot readiness, session creation, and browser milestones. ICMP reachability is not application readiness.

Rejected hypotheses. Admin has a 600-second idle timeout, so the five-minute capture does not by itself expire it. The warm-state metadata test with MariaDB left running did not reproduce the error. A Redis-cache stop on the login route also did not reproduce it. Do not report a database-start delay as the historical warm snapshot root cause.

Acceptance run before promising 20 seconds

Run at least 100 complete trial creations on real warm hosts. Include fresh and aged snapshots, the exact trial shape, simultaneous signups, host memory pressure, unavailable metadata, delayed key delivery, rename overlap, task cancellation, and a deliberate cold fallback. Measure request accepted, queued, dispatched, restored, mesh ready, bootstrap applied, product ready, session created, and browser usable. Report median, p95, p99, maximum, and error count. Keep cold fallback results separate. A fallback page is useful recovery, but it is not a usable signed-in site and does not satisfy this latency target.

Evidence and limits

The audit uses one development VM. It can show a failure and verify a repair under stated test conditions. It cannot prove that every request will succeed under every infrastructure failure. Page responses and API errors are recorded separately. A valid API error must remain an error; a working page must give the user a clear next action.
