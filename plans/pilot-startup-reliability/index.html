Pilot startup and recovery audit

Pilot must show a usable page while a bench starts or recovers. This audit checks a new self-hosted install, a cloud-managed install, and a warm host that waits for cloud configuration. It also checks whether a user can retry after a task stops.

In progress. No reliability claim yet. The test host is a fresh Ubuntu 26.04 VM with about 2 GB of RAM. Pilot uses develop. Frappe will use version-16-hotfix with lite mode.

Plan

  1. Inventory. Record the code revision, services, resource limits, and current host state. Preserve existing data and changes.
  2. Install and observe. Install Pilot develop. Sample the page and API during first start, setup, and the switch to production services.
  3. Trace state. Read setup, cloud configuration, routes, task ownership, process control, and browser recovery code. Find every point where partial work can become visible.
  4. Inject failures. Cancel queued and running tasks. Kill a task or worker between steps. Restart Admin and dependencies. Check what the user sees and how retry works.
  5. Repair and verify. Make small fixes at the state owner. Add regression tests. Repeat each failed experiment with the patch installed.
  6. Review and hand over. List verified behavior, remaining limits, patch locations, and the final host state. Keep the experiment history below.

Evidence and limits

The audit uses one development VM. It can show a failure and verify a repair under stated test conditions. It cannot prove that every request will succeed under every infrastructure failure. Page responses and API errors are recorded separately. A valid API error must remain an error; a working page must give the user a clear next action.

A direct Playwright check through an SSH tunnel showed the running setup screen and its output. No page error was reported. Direct public navigation was slow; it is not used as proof of page readiness.

Killed only the task wrapper during dependency installation. Pilot marked the task failed while two task-owned child processes still ran. Cleaned up both processes after the measurement. The repair stops verified children before it marks the task interrupted. The test also checks that detached children are gone. All 231 task tests and Python lint pass. A stale-process safety test caught an initial error in the repair; the final change preserves that safety check.
