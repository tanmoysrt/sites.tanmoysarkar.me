Why we rewrite

CSEMA lessons use seven formats today. Each format has its own player, look and quality. Some lessons have a narrated deck, some have Marp slides, and many have only a short write-up. Many lessons also mix teaching and testing on one page.

The goal is a new set of paths where a learner moves step by step. Each step does one job: it teaches with a Rabbit presentation, or it checks what the learner knows. Rabbit is the CSEMA presentation tool. A deck is data, one player shows all decks, and voice audio drives the timing.

The new shape

A path is an ordered list of items. Each item is one of five kinds and does one job only.

KindJob
presentationTeaches. A Rabbit deck of about 10 minutes, with no questions or tasks in it.
quizChecks understanding with multiple-choice questions.
codeChecks a skill with a coding exercise and automatic checks.
shellChecks a skill with a terminal task.
challengeChecks a skill with a CTF challenge or a lab. It uses an existing practice challenge when one fits.

Rules for a path

  • The learner moves from the plain case to the harder case. Each presentation uses only ideas that earlier items taught.
  • A presentation is about 10 minutes: about 1,300 to 1,500 words of narration in 12 to 20 scenes. One old voiced deck is about a third of this, so one presentation often holds about three old lessons.
  • Evaluations are few: usually two or three presentations, then one evaluation. Two evaluations never come in a row. Each section ends with one evaluation: a quiz, or a code, shell or challenge item where the skill is practical.
  • Quiz questions test only what the lessons taught, at the same difficulty. Titles are short, natural and inviting.
  • Each presentation sets the context first, and ends with a hook to the next item and a note to come back if the learner gets stuck.
  • The redesign can merge lessons, split them, add a missing concept, merge paths and drop duplicate paths.
  • Each item lists its sources: the old lessons it uses, or new.

Where the work lives

All work goes in var/learn-rewrite/ in the CSEMA checkout. Content does not go in the code repository, so the folder is outside it. The folder has its own local Git history, so each change has a diff and can be undone. This work does not change the database or the app.

Numbers set the order inside each level, so a new path in one track does not rename folders in another track. The kind is in the item folder name, so the tree shows learning and evaluation at a glance. Sections are listed in the path index.md, so items stay flat inside a path.

The status field in each item index.md is the only place that holds status: designed, draft, review or done. tools/progress.py reads all index.md files and writes PROGRESS.md. Rabbit build output (audio/, dist/, review/) is not in Git.

How the work runs

Claude runs the work without a stop for owner approval. Claude writes every design and deck. Codex (gpt-6-luna, medium effort) only reviews. The owner can read any track, path or deck at any time and send changes.

Design one track

We redesign one track at a time, because merges cross paths. For example, Cryptography has six old paths.

  1. Export every old lesson in the track: titles, sections, write-ups, old deck text and activities, plus the published practice challenges of the same category.
  2. Claude drafts the new paths and items from the rules above.
  3. A second pass corrects the order, the size of each presentation and the one-job rule.
  4. A script checks lengths, words, slugs, sections, the evaluation rhythm, challenge links and that each old lesson is used or dropped.
  5. Codex reviews the design and Claude applies the fixes, for at most four rounds. Claude rejects a finding that conflicts with the owner's wishes.
  6. Claude writes the track, path and item folders, runs progress.py, commits and updates this page.

Build one presentation

  1. Write deck.rabbit.yaml from the item index.md and its sources, with the Rabbit skill. Claude writes the slides and the narration.
  2. Match the quality of the Rabbit reference decks: clear and calm slides, hand-drawn diagrams, light animation that follows the narration, and one idea at a time.
  3. Run rabbit make. Fix every audit problem.
  4. Codex reviews the narration, the facts and the review pages, and Claude applies the fixes, for at most three rounds.
  5. Set the item status, run progress.py and commit.

Evaluation items keep their spec in index.md for now. They are built in a later phase.

Learning order

Every learner starts with Cyber Foundations, then takes the five core tracks in order. After the core, the learner picks one direction by interest: blue team, red team, binary or a specialty. A direction is a choice, not a requirement: a learner can come back and take another one later.

Start here

  • Cyber Foundations. Everyone starts here: your first CTF, files and hidden data, steganography, OSINT and security basics.

Then the core, in this order

  1. Operating Systems. Use the Linux and Windows command line, files, permissions and privilege escalation.
  2. Programming. Write small Python and Bash solvers, work with bytes, and automate challenges.
  3. Cryptography. Break encodings, classical ciphers, hashes, weak symmetric crypto and RSA.
  4. Network. Read packets, scan services and understand DNS, TLS and certificates.
  5. Web. Find and exploit web application bugs, the most common CTF category.

Blue team: defend and investigate

  • Forensics. For learners who like investigating: disk images, memory, artifacts and timelines.
  • SOC. After Forensics: read logs, write detections and triage alerts like a SOC analyst.

Red team: attack company networks and cloud

  • Cloud. For learners who want to attack cloud accounts, storage and containers.
  • Active Directory. For learners who want to attack company networks: Windows domains and Kerberos.

Binary: take programs apart and exploit them

  • Reverse Engineering. For learners who like taking programs apart: assembly, disassemblers and debuggers.
  • Binary Exploitation. After Reverse Engineering: memory bugs, buffer overflows and ROP.

Specialties: any time after the core

  • Artificial Intelligence. Attack AI systems: prompt injection, model and data risks.
  • Web3. Attack smart contracts on a local test chain.
