1. Why do this

Pilot has 51,600 lines of Python in pilot/ and 14,000 in admin/backend/. The main objects (Server, Bench, Site, App) are good. But much of the behavior does not live on them. It lives in loose module-level functions that take (bench_root, site_name) and similar arguments.

This causes three problems:

  • No single place to look. One task, for example "read a site's installed apps", has two copies in two modules.
  • Callers repeat setup. Each caller builds paths and passes the same arguments again.
  • Code grows by copying. There are five separate "read a log file backwards" functions.

The goal is less code and one clear owner for each behavior. No behavior changes. Each phase is one small pull request (PR) that keeps all tests green.

2. The rule: every behavior has an owner

A loose function is a function at module level that is not a method. This plan keeps a loose function only in these cases:

  • A Flask route handler or a CLI command entry point (the framework needs a function).
  • A small pure helper that has no state and no natural owner, for example normalize_host().

All other behavior goes onto a class. The class is owned by a domain object and you get it through that object:

# Before: the caller passes the bench path and the site name
from pilot.core.site.config import list_active_apps, is_setup_complete
apps = list_active_apps(site_config, bench.path, "one.local")
done = is_setup_complete(bench.path, "one.local")

# After: the site owns its database facts
site = bench.site("one.local")
apps = site.database_state.active_apps
done = site.database_state.is_setup_complete

This follows the repo rules in CLAUDE.md: object-owned syntax, @property for nouns, get_*() for work, and one owner for state.

4. Phases

The order is by risk. Deleting dead code is first because it makes the later moves smaller. Each phase is one PR. Each PR runs ruff, mypy (mypy pilot admin/backend) and the full suite in CI. No phase changes a URL, a JSON shape or a CLI command.

Each phase below gives the same five parts: problem, change (file by file), before → after code, callers that must change, and tests.

    try:
        _quick_actions().require_restart()
        bench = _bench()
        task_id = RestartDatabaseTask.queue(
            bench,
            idempotency_key=request.headers.get("Idempotency-Key"),

        return accepted_task_response(bench.path, task_id)
    except (DatabaseError, TaskConflictError) as exc:
        return error_response("database_action_unavailable", str(exc), 409)
    except ValueError as exc:
        return error_response("invalid_database_action", str(exc), 422)

5. Tests

The suite has 3,889 test functions in 67,700 lines. A full local run takes about 7.5 minutes, and one test uses almost half of that. The suite is mostly useful. The problems are its layout and the tests that check private internals.

  • Delete with the code. Tests of the wrappers and shims removed in phase 1 go away with them.
  • Delete trivial tests. 9 tests only assert is not None, isinstance or hasattr. Examples: test_resolve_returns_list_of_resolvers and test_get_package_manager_macos. A behavior test covers each one.
  • Split catch-all files. test_core.py (1,297 lines), test_commands.py (1,570) and test_managers_extra.py (972) go into files named for the object they test.
  • Mirror the source tree. The 76 flat files in tests/pilot/core/ go into site/, bench/, app/, database/ and monitoring/ subfolders.
  • Test through the public API. 4 tests import private names and 483 places read private attributes. When a public method gives the same check, use it. The worst files are test_setup_production.py (30), test_core.py (23) and test_monitor.py (22).
  • Merge into tables. Groups of near-identical tests, for example the WAF patcher rejection tests, become one pytest.mark.parametrize table.

Slow tests

I measured a full local run with pytest --durations=40: 4,482 passed in 447 s.

TestTimeCause and fix
test_site_rename.py::test_readers_keep_the_old_path_during_failed_renames_and_retries205 sThis one test is 46% of the whole run. It does 100 rounds of a failed rename plus a retry. During that time a reader thread spins without a pause and competes for the Python interpreter lock. Fix: use 10 rounds and add time.sleep(0) in the reader loop. The check stays the same: readers always see the old path.
About 40 other tests in test_site_rename.py, test_rename_site.py, test_hostname_alias_retarget.py, test_released_pin.py2–5 s each, about 100 s in totalEach rename costs about 2 s, even with mocks. Find the shared wait (probably a retry or poll in the rename flow) and make it configurable in tests.
test_editor_path_fuzz.py (2 tests)15 sFuzz tests. Keep them, but lower the number of examples in CI and keep a larger run for nightly builds.

Expected result: the full suite goes from about 447 s to about 150 s.

6. What this plan does not change

  • Imports inside functions (897 in pilot/). Most of these keep CLI start-up fast or break import cycles. The plan removes the ones that belong to deleted wrappers. It does not remove the rest without an import-time measurement (python -X importtime).
  • The Bench facade methods. bench.start(), bench.backups and similar methods delegate to helper modules on purpose. They are the public object API, so they stay. Only private delegators go.
  • Behavior, routes and CLI commands. All URLs, JSON shapes and command names stay the same.
