Beacon: incident manager and status page for Frappe Cloud V2

A design for one small Frappe app. It turns Datum metrics into alerts, groups alerts into root-cause incidents, calls the on-call engineer, and publishes a status page.

Plan · November 2026 · Final design (revision 4, with a last consistency pass) · Status: proposed · Reviewed in four rounds with two other models (GPT-6.1 Sol, high effort; Claude Fable 5.2, medium effort) · Mockups in moki: beacon-status v2

Summary. Beacon is one global Frappe app. Staff use Desk, and customers see only the status page. Every region keeps its own resource registry in Datum, and the services in that region fill it. Alert rules are ClickHouse SQL queries that return only the failing resources. Beacon stores one row for each alert episode and writes only state changes, so 100,000 resources per region are cheap. One invariant drives incidents: every firing alert that is not muted belongs to an open incident. Problems high in the tree, such as a host or a proxy, give one root-cause incident with derived impact, not one entry for each server. Datum needs four important changes: async inserts, a recent-data table sorted by metric, retention, and the registry.

1. Situation

Frappe Cloud V2 sends telemetry to Datum. Datum is a write-only service in front of ClickHouse. There is one Datum and one ClickHouse in each region. Readers query ClickHouse directly with a read-only account.

Today, alerts are temporary. A script in frappe/atlas makes three Insights Alerts: P1 every 5 minutes, and two P2 alerts every hour. Each one is a large SQL query that joins about 50 checks. When it returns rows, Insights posts a Markdown message to a chat webhook. The problems:

  • There is no state. The same problem posts on every run, and nothing says "resolved".
  • There is no acknowledgement, paging or escalation.
  • You cannot mute one host or one check, or schedule maintenance.
  • One failing check hides in a long message. There is no history for each resource.
  • The Insights SQL size limit splits one logical alert into two.

Frappe Cloud V1 (frappe/press) had a full incident system: Prometheus rules, Alertmanager webhook logs, an Incident with Validating → Confirmed → Acknowledged → Resolved, Twilio calls, night shifts and silenced alerts. We keep its ideas. We drop three things: a second alerting stack to operate, "the call was answered" as acknowledgement, and mute flags spread across many DocTypes.

2. Goals, non-goals, scale

Goals

  1. Alerts that are easy to write and have state: Pending → Firing → Resolved, one episode per problem, no duplicates.
  2. Root-cause incidents with paging, acknowledgement, updates and a root cause analysis (RCA).
  3. A status page with regions, one status for each service, 90-day uptime bars, incidents and maintenance.
  4. Unlisted incidents with a private link for affected customers, like Hetzner does.
  5. Maintenance windows that stop paging and, when planned in advance, do not count against uptime.
  6. A short integration path, so every V2 service can use it.

Non-goals for v1

  • A staff web app. Staff use Desk.
  • Customer alert rules and incidents in the Central dashboard. That is phase 4, and Central owns that UI. Central already shows metrics from Atlas and Datum.
  • Python rule scripts, probes run by Beacon, email subscriptions, AI investigation, several on-call teams.

Scale target

Up to 100,000 resources per region (most are sites), about 10 regions. The design must stay simple at that size. We do not design for millions.

3. Architecture

Beacon is one Frappe site. It runs outside the regions it watches. It reads each region's ClickHouse with a read-only user and writes nothing there. The status page is static files in an object storage bucket behind a CDN. Beacon uploads them every 30 seconds. So the status page stays up when Beacon is down, and it handles the traffic peaks that come with an outage.

PartJob
Datum + ClickHouse (per region)Stores samples, logs, traces and the resource registry. Owns telemetry.
Beacon evaluatorScheduler jobs and an RQ queue named beacon. Runs rule and service queries and writes transitions.
Beacon tickOne job every minute for time-based work: maintenance start and end, silence expiry, escalation steps, closing alerts of disabled rules, the heartbeat.
DeskStaff work incidents and configure everything. One Beacon workspace is the landing page.
Status builderRenders static HTML and JSON every 30 s and uploads only changed files.

4. Key decisions

D1
Rules are ClickHouse SQL. A query returns only failing rows. ClickHouse evaluates all resources in one set-based query, and no samples leave ClickHouse. The current checks are already SQL. A read-only profile limits time, memory, threads and concurrency. We do not add Python safe_exec: it is a second runtime that is harder to review and to limit.
D2
One result contract. A rule returns resource_id, alert_key, value, detail. alert_key separates two problems on one resource, such as two disks. A missing row means "healthy" only after a successful query. Duplicate (resource_id, alert_key) rows, or more rows than the limit, fail the evaluation. Nothing is truncated.
D3
Each region has a resource registry that its services fill. It lives in Datum. Atlas registers hosts, VMs and service nodes. A server registers its sites. Central is not in the path. Beacon checks only resources that are Active, with Active ancestors, and not excluded. So an archived or stopped resource never looks "down".
D4
One Alert row per episode, written only on transitions. A firing alert causes no writes. A mass outage writes its rows once.
D5
The incident invariant. After each evaluation and each tick, every Firing alert that is not suppressed must belong to an open incident. Beacon attaches it to an ancestor's incident, else to its group's incident, else reopens or creates one. This one rule covers new alerts, ended silences, ended maintenance and incidents that someone resolved too early.
D6
One root-cause incident, impact derived. An incident has a few scope rows, such as "host bom-h12 and everything under it" or "all sites in bom". The affected set is computed from the registry when someone asks. Child alerts join the parent incident and do not page.
D7
One Incident DocType with type Incident or Maintenance, as in the owner's model. Both have updates, scope, affected services and visibility. A separate small Silence mutes paging for a set time.
D8
A person decides what customers see. Beacon never publishes an incident and never reopens a public one. The only automatic public signal is the computed service status.
D9
Uptime counters live in MariaDB, one row per service, region and UTC day. Minutes that Beacon did not observe count as unknown, never as healthy.
D10
Desk is the admin UI. The API is small. It covers rule sync from Git, staff actions and Twilio callbacks. The public status page is static files, so it needs no API.
D11
Fail loudly, never silently resolve. A query error never resolves an alert. A region with broken telemetry gives one alert, not one for each rule. If Beacon stops, an external dead-man switch calls us.
D12
Central integration waits for phase 4. The outbox, customer rules and Central routes are designed here but not built in v1.

5. One alert, end to end

Follow a host failure in Mumbai. The host bom-h12 has 30 VMs and 400 sites.

  1. 07:12. The host loses power. VMs and sites stop reporting. Their "not reporting" rules return rows, and the alerts become Pending.
  2. 07:14. A VM alert reaches its pending_for and becomes Firing. No incident covers it, so Beacon creates an Internal incident in status Triggered. The VM has a parent, so paging waits page_delay (90 s).
  3. 07:15. "Host not reporting" becomes Firing. Beacon creates the host incident with scope "bom-h12, include descendants". The VM incident is not acknowledged and the host covers it, so it is merged. Every VM and site alert now joins the host incident.
  4. The host has no parent, so the host incident pages at once. Severity High calls the primary responder. The call says "Press 1 to acknowledge". There is no key press. After 5 minutes, Beacon calls the second responder, who presses 1. The incident moves to Investigating.
  5. The engineer uses the Publish action: visibility Unlisted, first public update, affected service "Servers · bom" with impact Major Outage. Support copies the private link and the list of affected resources from Desk and sends it to the affected teams. In phase 4, Central does this.
  6. The power supply is replaced. The alerts get clean results and become Resolved (Recovered) after resolve_after. The incident is Unlisted, so Beacon posts "all alerts resolved" to chat. The engineer posts a final update and resolves it.

7. Resource registry

Beacon must know what to track. If it looked only at telemetry, an archived resource would look like a dead one. So each region keeps a registry, and the services in the region fill it. It lives in that region's Datum, next to the metrics, so rules can join it and each region works on its own.

SourceRegistersToken
AtlasHosts, VMs (servers), proxy and WireGuard gateway nodes, storage gateways and nodes, Atlas itselfAdmin: any resource
The agent on a serverIts sites, with parent_id = the serverMachine token: itself and its direct children only, at most 5,000 rows

How a source sends. It sends its full list every 15 minutes, and each change at once. A full list can span several requests. It is committed only when the last request arrives. A change (for example, "site archived") updates the committed list at once.

PUT /v1/resources                       source from the token; at most 10,000 rows per request
{"snapshot_id": "atlas-1731480000", "final": true,
 "resources": [{"resource_id": "bom-h12", "resource_type": "Host", "parent_id": "",
                "title": "bom-h12", "status": "Active"}, ...]}
PUT /v1/resources  {"resources": [{"resource_id": "a1.example", "status": "Terminated", ...}]}
                                         no snapshot_id: a change to the committed list
CREATE TABLE datum.resources (
  source LowCardinality(String), snapshot_id String, resource_id String,
  resource_type LowCardinality(String), parent_id String, title String,
  status Enum8('Pending' = 1, 'Active' = 2, 'Suspended' = 3, 'Terminated' = 4),
  labels Map(LowCardinality(String), String),
  version DateTime64(3) DEFAULT now64(3)          -- set by Datum, not by the producer clock
) ENGINE = ReplacingMergeTree(version)
ORDER BY (source, snapshot_id, resource_id)       -- changes use snapshot_id = 'changes'
TTL toDateTime(version) + INTERVAL 30 DAY;

CREATE TABLE datum.resource_snapshot_commits (
  source LowCardinality(String), snapshot_id String, row_count UInt32,
  started_at DateTime64(3),                       -- time of the snapshot's first request
  committed_at DateTime64(3) DEFAULT now64(3)
) ENGINE = MergeTree ORDER BY (source, started_at);
-- Datum refuses a commit whose started_at is older than the source's current one.

CREATE VIEW datum.resources_latest AS
WITH current AS (
  SELECT source, argMax(snapshot_id, started_at) AS current_snapshot, max(started_at) AS current_start
  FROM datum.resource_snapshot_commits GROUP BY source
)
SELECT r.resource_id AS resource_id,
       argMax(r.resource_type, r.version) AS resource_type,
       argMax(r.parent_id, r.version)     AS parent_id,
       argMax(r.title, r.version)         AS title,
       argMax(r.status, r.version)        AS status,
       argMax(r.source, r.version)        AS owner_source
FROM datum.resources AS r FINAL
INNER JOIN current AS c ON c.source = r.source
WHERE r.snapshot_id = c.current_snapshot
   OR (r.snapshot_id = 'changes' AND r.version > c.current_start)
GROUP BY r.resource_id;
  • Tested. The tables and the view above, and counter_increase below, were run with clickhouse local 26.10.3.7 against sample data: an old list, later changes, a new list, and a counter reset. The results were as expected.
  • A full list replaces the old one. A resource that is missing from its source's latest committed list is gone. We need no delete events and no reconcile job.
  • Changes and lists do not overwrite each other. A change is stored as a changes row. It wins over the committed list until a list that started after it is committed. A late commit of an older list is refused.
  • A stale source does not shrink the list. If a source has not committed a list for 1 hour, its last list stays in use and Beacon raises one "Registry stale" alert. Rows expire after 30 days, so a source that is silent for 30 days loses its list. The alert makes sure this never happens unnoticed.
  • Moves between parents. When a site moves to another server, both servers can list it for up to 15 minutes. The newest row wins. If a resource stays in two lists for more than 30 minutes, Beacon raises one Low "Registry conflict" alert.
  • What Beacon checks. A resource is checked only if it is Active, all its ancestors are Active, monitoring_disabled is off, and it has been Active longer than the rule's new_resource_grace. A suspended host therefore also stops checks on its VMs and sites.
  • Beacon's copy. Every 5 minutes, Beacon reads resources_latest for each region (about 100,000 rows, a few MB). It compares the rows by hash with MariaDB and writes only the changes. Desk can then list resources, and Beacon can walk parents without asking ClickHouse.

8. Rule evaluation

Every minute, the scheduler queues each due Rule Evaluation as a job with ID evaluate:{rule}:{region}, with some jitter. Each job does this:

1. Region telemetry Unreachable?             -> skip. The region alert covers it.
2. Take an advisory lock for (rule, region).
3. Run the SQL with the beacon profile.
   Error, duplicates, or over 250,000 rows?   -> consecutive_errors += 1; stop. Nothing changes.
4. Gap since last_success_at > 3 x interval? -> reset started_at (Pending) and clean_since.
5. Filter rows with Beacon's Resource copy:
   unknown resource_id                        -> drop, count in unknown_rows
   not checked (status, ancestors, disabled, grace) -> drop
6. Close open alerts whose resource is no longer checked:
   Resolved (Resource removed) or Resolved (Disabled). These never count as recovery.
7. Diff the rest with open alerts:
   new row                       -> Pending (Firing at once if pending_for = 0)
   row, alert Pending            -> Firing once failing for pending_for
   row, alert Firing             -> clear clean_since
   no row, alert Pending         -> Resolved (Cleared)
   no row, alert Firing          -> set clean_since; Resolved (Recovered) after resolve_after
8. Recompute suppressed for open alerts (Silence, In Progress maintenance scope).
9. Write changes in chunks of 5,000 rows in one transaction. Update Rule Evaluation.
10. Enforce the incident invariant for this region (see Incidents).

Time-based work runs in the tick every minute. It starts and ends maintenance, recomputes suppression when a silence ends, steps escalations, and closes the open alerts of disabled rules and regions with "Disabled". After each step it enforces the invariant. The tick sends the heartbeat only if no Rule Evaluation is overdue by more than 2 intervals.

Region telemetry is checked first, every minute. Unreachable: the ClickHouse probe fails. Suspect: fewer than 50% of the region's checked resources sent a sample in the last 5 minutes. Rules still run and page, because it can be a real outage. Only the public status of that region is frozen. Two good checks return the region to OK.

9. Incidents and impact

The invariant

After every evaluation and every tick, Beacon takes one advisory lock for the region and checks each Firing alert that is not suppressed and is not in an open incident. In order:

  1. Ancestor. If an open incident has a scope row that covers the alert's resource through an ancestor, join it. No page.
  2. Group. If an open incident has the alert's group_key (rule and region by default), join it. A higher severity raises the incident and notifies again (see Paging).
  3. Reopen. If an incident with that group_key was resolved less than reopen_window_minutes ago, was Internal and was created by Beacon, reopen it to Triggered.
  4. Create. Otherwise create an Internal incident in Triggered with that group_key. If the resource has no parent, paging starts at once. Otherwise it waits page_delay, so a parent incident can merge it.

When an incident opens with a scope that covers other open incidents, Beacon merges each covered incident that nobody acknowledged and that is Internal. Their alerts move, their status becomes Merged, and merged_into is set. Staff can also merge by hand, for example to join one problem across regions.

An incident created by Beacon from a "not reporting" rule for a resource with children gets the scope row "this resource, include descendants". Other incidents start with the scope of their alerts. Staff can add scope rows.

Impact without one row for each resource

│   ├── site a1.example                     scope row 2: region bom, type Site, any

1 incident, 1 update stream, 1 private link. No row for each server or site.

Is X affected? Beacon walks up the parent chain of X (at most 4 steps). X is affected if a scope row matches X, matches an ancestor with include_descendants, or matches its region and type with a blank ID. A scope row with only a region covers the whole region.

Who is affected? Desk has "Export affected resources" (CSV), which expands the scope from the registry. In v1, support uses it with "Copy private link" to tell customers. In phase 4, Central does this through the API.

Closing

  • An Internal incident created by Beacon resolves itself when all its alerts are resolved, in any open status.
  • An Unlisted or Public incident waits for a person. Beacon posts "all alerts resolved" to chat after 30 minutes.
  • Staff cannot resolve an incident while it has Firing alerts that are not suppressed. The Resolve dialog offers "Silence the remaining alerts for N hours and resolve". So no alert is left without an incident.

Publishing

The Publish action is one dialog: visibility (Unlisted or Public), affected services with impact, and the first public message, which is required. After that, new updates are public by default. Unlisted creates a 32-character token. Internal clears it. Each visibility change is in the document history.

  • A maintenance's start and scope are locked when it starts. Its end can be extended until it passes.
  • Saving a Public maintenance without an affected service of impact Maintenance shows a warning, because then nothing is excluded from uptime.
  • No storm after a long window. When a maintenance ends, Beacon looks at the alerts in its scope that still fire. Alerts that another silence or maintenance still covers stay suppressed. Alerts that are already in an open incident stay there. All others go into one incident, "Still failing after <maintenance title>". Then normal paging applies.
  • A silence can match one disk: resource_id plus alert_key. A silence with a future starts_at takes effect at that time.

11. Service status and uptime

A service is one line on the status page, such as "Sites" or "Object Storage". A Region-scope service is defined once and evaluated in each region. A Global service, such as Dashboard or API, reads the ClickHouse of its query_region.

Each minute, the health query returns healthy and expected. expected is the number of checked resources from the registry. A resource counts as healthy only if it has a sample from the last 5 minutes, so a resource that stops reporting counts as unhealthy. Beacon refuses a result with healthy < 0 or healthy > expected and counts that minute as Unknown. Health counts platform failures only. A site that returns 500 from its own code is healthy for the platform. If it were not, a few broken customer apps in 100,000 sites would keep "Sites" Degraded.

Checked in this order:
region Unreachable, query error, invalid result, expected = 0, registry stale -> Unknown
In Progress maintenance lists this service + region (impact Maintenance) -> Maintenance
ratio = healthy / expected:  >= 99.5% Operational, >= 95% Degraded, >= 80% Partial Outage, else Major Outage

Shown on the page: worst(computed, impact of open Public incidents)
Unknown, or region Suspect: worst(last computed state before the freeze, impact of open Public incidents),
                             with "data delayed"
Minute counted as: Unknown or Suspect -> unknown; Maintenance -> maintenance if excluded_from_uptime,
                   else by ratio; otherwise the computed state. Idempotent through last_counted_minute.

observed = all minutes - unknown_minutes
eligible = observed - maintenance_minutes
down     = partial_minutes + major_minutes          (Degraded counts as up)
uptime % = (eligible - down) / eligible             eligible = 0 -> "no data"

This is service-status uptime. It is not the share of successful customer requests. The page shows coverage (observed ÷ all minutes) next to it.

  • Who is called. The primary override until override_until, if that person is an active responder, else the first active responder, then down the list in order. A responder on leave is set inactive. With no active responder who has a phone, phone calls cannot be enabled, and the workspace shows a red warning.
  • Acknowledgement is a key press. Twilio <Gather> asks for 1. Only Digits=1 counts. Beacon matches the CallSid to the Notification and the incident, checks the Twilio signature, and ignores repeated callbacks. Email links open a confirm page that sends a POST, so a mail scanner cannot acknowledge.
  • Escalation state is stored on the incident (escalation, page_round, page_index, next_page_at). The tick moves it.
  • Desk buttons: "Page on-call" for an incident that staff created, and "Send test page" in Beacon Settings to check phone numbers.
  • Paging pause. paging_paused stops all calls and emails, for example after a database restore. The workspace shows it in red.

15. Integrating a V2 service

For a node that Atlas manages, a service team does two things: export metrics and write rules. Atlas already gives the node an identity, a Datum token and a registry entry. Standard rules (not reporting, disk, memory, OOM kills, clock, failed units) apply to every registered node that runs the standard Vector host metrics.

1. Export metrics

Go services expose Prometheus /metrics on localhost. The Vector on the node scrapes it and sends it with remote write. Datum already accepts remote write v1 on /v1/ingest/remote. Add a source and append it to the existing Datum sink:

# /etc/vector/conf.d/http-proxy.toml
[sources.http_proxy]
type = "prometheus_scrape"
endpoints = ["http://127.0.0.1:9180/metrics"]
scrape_interval_secs = 15

# the node's existing sink: add "http_proxy" to inputs. One sink per machine, because
# Datum allows 12 requests a minute per token; keep batch.timeout_secs at 10 or more.

Frappe apps and Python daemons use datum_client (Batch, record). Name metrics <namespace>_<subsystem>_<target>_<unit>, for example proxy_http_responses_total. Keep labels small and stable.

2. Write rules

Put each rule in beacon/rules/<name>.sql in the service's repository. The header keys are the Alert Rule field names. Use the standard views, which Datum provides, so that counters and freshness are right:

ViewReturns
counter_increase(metric, window)resource_id, labels, increase, with resets handled for each series
latest_value(metric, window)resource_id, labels, value, ts, the newest sample in the window
last_seen(window)resource_id, last_ts, for "not reporting" rules with resources_latest
CREATE VIEW datum.counter_increase AS          -- parameterized view, shipped by Datum
SELECT resource_id, labels, length(vals) AS samples,
       arraySum(arrayMap((d, v) -> if(d >= 0, d, v), arrayDifference(vals), vals)) AS increase
FROM (
  SELECT resource_id, labels, arrayMap(x -> x.2, arraySort(groupArray((ts, value)))) AS vals
  FROM datum.samples_recent
  WHERE metric = {metric:String} AND ts > now() - toIntervalSecond({window:UInt32})
  GROUP BY resource_id, labels
);
-- The first sample in the window is the baseline. A drop means a reset: the new value is growth.
-- A series with fewer than 2 samples has increase 0; rules can require samples >= 2.
-- beacon/rules/upstream-errors.sql
-- title: Proxy 502/504 above 5% of requests
-- owner_team: http-proxy
-- severity: High
-- resource_type: Proxy Server
-- interval: 60
-- pending_for: 600
-- resolve_after: 300
-- runbook_url: https://github.com/frappe/atlas/blob/develop/docs/operate/proxy.md
SELECT resource_id, '' AS alert_key,
       sumIf(increase, labels['code'] IN ('502', '504')) / nullIf(sum(increase), 0) * 100 AS value,
       concat(toString(round(value, 1)), '% upstream errors') AS detail
FROM datum.counter_increase(metric = 'proxy_http_responses_total', window = 600)
GROUP BY resource_id
HAVING value > 5

The rule does not need to filter for Active resources. Beacon does that with its registry copy (evaluation step 5). A customer-facing service adds beacon/services/<name>.sql with a health query that returns healthy, expected.

3. Test and sync from CI

$ beacon-rules query --region bom "SELECT ..."   # ad-hoc read-only query, for writing SQL
$ beacon-rules test beacon/                      # every candidate rule and service in every region
$ beacon-rules sync beacon/                      # upsert; disable what this repository removed

beacon-rules is one standard-library Python script in the Beacon repository. It calls two API routes with a staff token. query sends one candidate with "raw": true to the test route: no contract checks, at most 100 rows, the same read-only limits. Developers do not need ClickHouse credentials. test runs the candidate SQL, not the saved rule. It checks the contract (columns, types, duplicates, row limit) and reports rows, duration and errors for each region. An unreachable region is a warning, not a failure. sync touches only rules and services of that repository, and each rule_key is <repository>:<path>.

4. Only for nodes Atlas does not manage

  • Ask Atlas for a Datum token for the machine. Atlas renews tokens daily into the node's config file.
  • Register the machine and its children with Datum.register(resources, full=True) every 15 minutes, and send changes at once.
  • A new resource_type is a plain string. It needs no Beacon release.

17. Status page

The mockups are in moki, project beacon-status, version 2. They have three layouts for the main page, a public incident page, an unlisted incident page and a history page. The ideas come from DigitalOcean (regions as rows), Railway and Cloudflare (90-day bars), Fly.io (region grid) and Hetzner (unlisted incident links).

  • Recommended: regions first. At the top there is a banner, then active incidents and maintenance. Below that, each region is one row that opens to its services with 90-day bars. The global services come last.
  • The page is static HTML that works without JavaScript. It shows "Updated <time>", so a stale page is visible.
  • A frozen region (Unknown or Suspect) shows its last state with "data delayed".

18. Desk workflow and roles

The Beacon workspace is the landing page. It shows open incidents, Firing alerts that are not suppressed, broken rules, stale registries and regions, who is primary now, and red banners for paging_paused or a missing responder.

Working an incident: Acknowledge → Post update → Publish (if customers need to know) → Resolve → write the RCA. Buttons on the form: Acknowledge, Post update, Publish, Page on-call, Merge into, Copy private link, Export affected resources, Resolve. On an alert: Silence. On the list: Create maintenance.

RoleCan
Beacon ResponderAcknowledge, update, publish and resolve incidents. Create maintenance and silences. See private links.
Beacon AdminEverything above. Also rules, services, regions, the responder list, channels, and the staff API token for rule sync.

The Beacon site's system time zone is UTC. Forms show UTC next to time fields, so a maintenance start is never ambiguous around daylight saving changes.

19. Datum changes

We reviewed frappe/datum for the expected load and the new uses. We checked each finding in the code. All numbers are per region.

Sizing assumption. 100,000 sites × 10 series every 60 s, plus 5,000 servers and hosts × 200 series every 15 s. That is about 83,000 rows/s, or 7.2 billion rows/day, which is 70–220 GB/day at 10–30 bytes per compressed row. Measure the real rate with daily_ingestion_stats before you set retention.

2 P1samples is ordered by (resource_id, metric, ts). Alert queries ask for "metric X, all resources, last minutes". CLAUDE.md says reads always name a machine. 22. What we do not build

  • A staff web app, Python rules, our own probes, a copy of the metrics.
  • A CRUD API that copies Desk.
  • Shift calendars, SMS, a severity × channel matrix, several on-call teams.
  • Email subscriptions. Feeds and JSON first.
  • Automatic publishing or automatic reopening of public incidents.
