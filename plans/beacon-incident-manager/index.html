Beacon: incident manager and status page for Frappe Cloud V2

A design for one small Frappe app. It turns Datum metrics into alerts, groups alerts into incidents, calls the on-call engineer, and runs a public status page.

Plan · November 2026 · Status: proposed · Reviewed in two rounds with a second model (GPT-6.1 Sol, high effort) · Mockups in moki: beacon-status v2

Summary. Beacon is a separate Frappe app. One global instance watches every region. Alert rules are ClickHouse SQL queries that return only the failing resources. Beacon keeps one row for each alert episode and writes only state changes. That keeps the load low at 100,000 resources per region. Alerts group into incidents. Incidents page people by phone, email and chat. Staff use Frappe Desk. Customers see only the status page. Datum needs four changes before launch. The biggest are async inserts and a small recent-data table sorted by metric.

1. Situation

Frappe Cloud V2 sends telemetry to Datum. Datum is a write-only service in front of ClickHouse. There is one Datum and one ClickHouse in each region. Readers query ClickHouse directly with a read-only account.

Today, alerts are temporary. A script in frappe/atlas makes three Insights Alerts: P1 every 5 minutes, and two P2 alerts every hour. Each alert is one large SQL query that joins about 50 checks. When a query returns rows, Insights posts a Markdown message to a chat webhook.

This works, but the team does not like it:

  • There is no state. The same problem posts again on every run, and nothing says "resolved".
  • There is no acknowledgement, no paging and no escalation.
  • You cannot silence one host or one check. You cannot schedule maintenance.
  • One failing check hides in a long message. There is no history per resource.
  • The Insights SQL size limit forces one logical alert to split into two.

Frappe Cloud V1 (frappe/press) had a full incident system: Prometheus alert rules, Alertmanager webhook logs, an Incident DocType with Validating → Confirmed → Acknowledged → Resolved, Twilio calls with day and night thresholds, night shifts and silenced alerts. We keep its good ideas. We drop three things: a second alerting system (Prometheus and Alertmanager) to operate, "the call was answered" as acknowledgement, and mute flags spread across many DocTypes.

2. Goals, non-goals, scale

Goals

  1. Alerts that are easy to configure and have state: Pending → Firing → Resolved, one episode per resource, no duplicates.
  2. Incidents that group alerts, page the on-call engineer, track acknowledgement, updates and a root cause analysis (RCA).
  3. A public status page with regions, one health status for each service, 90-day uptime bars, active incidents and scheduled maintenance.
  4. Unlisted incidents. They have a private link that we send only to affected customers, like Hetzner does.
  5. Maintenance windows that stop paging and do not count against uptime.

Non-goals for v1

  • A staff UI. Staff use Frappe Desk.
  • Customer alert rules and incidents inside the Central dashboard. That comes in a later phase, and Central owns that UI. Central already shows metrics from Atlas and Datum.
  • Python rule scripts (safe_exec), synthetic probes run by Beacon, email subscriptions, AI investigation, more than one on-call team.

Scale target

Up to 100,000 resources per region (most are sites), about 10 regions. The design must stay simple at that size. We do not design for millions.

3. Architecture

Beacon is one Frappe site. It runs outside the regions it watches, so a region outage does not take down the alerting or the status page. It reads each region's ClickHouse with a read-only user. It writes nothing to ClickHouse.

PartJob
Datum + ClickHouse (per region)Stores samples, logs and traces. Owns telemetry. Beacon reads it.
Beacon evaluatorA scheduler job and an RQ queue named beacon. It runs rule queries, compares results with open alerts and writes transitions.
Beacon DeskStaff configure rules, services, on-call and maintenance, and work incidents in Desk.
Status pageServer-rendered Frappe www pages and public JSON, built from a cache every 30 seconds.
NotifiersTwilio voice, email (Frappe Email Account) and a chat webhook (Raven or Slack style).
Central (later)Receives signed events. Shows incidents to affected teams and hosts customer alert rules.

4. Key decisions

Each decision says what we chose, why, and what we did not choose.

D1
Rules are ClickHouse SQL, not Python. A rule query returns only failing rows. ClickHouse evaluates all 100,000 resources in one set-based query, and no samples leave ClickHouse. The current checks are already SQL, so we can port them one to one. A Python safe_exec layer adds a second runtime, and it is harder to review and to limit. A read-only ClickHouse profile (time, memory, threads, concurrency, quota) limits the cost of a bad query.
D2
One fixed result contract. Every rule returns resource_id String, alert_key String, value Nullable(Float64), detail String. alert_key separates two problems on one resource, such as two full disks. A missing row means "healthy" only when the query finished without an error. Each resource type also has an explicit "not reporting" rule. It reads an inventory, because silence is not health.
D3
One Alert row per episode, and Beacon writes only transitions. An episode starts at the first failure and ends at resolve. While an alert stays firing, Beacon does not write to it. It refreshes the latest value at most every 10 minutes. A database unique key on open alerts blocks duplicates. A mass outage writes 100,000 rows one time, not every minute.
D4
Incidents are separate from alerts. People are paged for incidents, never for alerts. By default, all firing alerts of one rule in one region join one incident. When 40 servers go down in bom, you get one call, not 40.
D5
One Incident DocType with type Incident or Maintenance. Both have updates, affected services, visibility and a public page, so one DocType keeps the status page logic in one place. A small, separate Silence DocType mutes paging for a short time. A silence never changes uptime.
D6
Sparse resource registry. Beacon does not copy 100,000 resources from Central. A Resource row exists only when Beacon must remember something: monitoring disabled, a custom-rule target, an incident reference. Lifecycle comes from inventory in Datum. Topology (site → server → host) stays in Central and Atlas. With a copy, sync and deletion drift become our problem, and this avoids it.
D7
Uptime counters live in MariaDB, one row per service, region and UTC day. They count minutes per state. We do not write status back into Datum, because the status page must work when telemetry is down.
D8
Three visibility levels: Internal, Unlisted, Public. An unlisted incident has a random 32-character token. Its page is /status/i/<token>. It does not appear in lists, feeds, search or the public API.
D9
Desk is the admin UI. The API is small. The API serves only the status page, Central (later), rules synced from Git, and Twilio callbacks. We do not copy Desk CRUD into REST.
D10
Fail loudly, never silently resolve. A query error never resolves an alert. If a region's ClickHouse is down, you get one "Telemetry unavailable" alert, not 60 rule errors. If the evaluator stops, an external dead-man switch calls us.

5. One alert, end to end

Follow one real case: a host disk in Mumbai fills up.

  1. 09:14. The rule "Host disk free below 10%" runs in bom. The query returns one row: resource_id='bom-h12', alert_key='/var', value=8.7. Beacon inserts an Alert with status Pending.
  2. 09:19. The row was in every run for 5 minutes (pending_for = 300). The alert becomes Firing. No silence or maintenance covers it.
  3. The rule groups by rule and region. There is no open incident for it, so Beacon creates an Incident: severity High, visibility Internal, status Triggered. Beacon posts it to the chat webhook.
  4. High severity calls the primary responder. The call says "Press 1 to acknowledge". There is no answer. After 5 minutes, Beacon calls the second responder. That person presses 1. Twilio posts Digits=1 with the call ID. Beacon finds the Notification row and sets the incident to Acknowledged.
  5. The engineer cleans up the disk. The query stops returning the row. After 2 clean minutes (resolve_after = 120), the alert becomes Resolved.
  6. All alerts of the incident are resolved, and the incident is Internal and was created by Beacon. Beacon resolves it and posts to chat. A public or unlisted incident waits for a person to resolve it.

7. Rule evaluation

Every minute, the scheduler selects Rule Evaluation rows where next_run_at is due. It queues one job for each, with the job ID evaluate:{rule}:{region}. Each job does this:

1. Region probe failed in the last minute?  -> skip. The region alert covers it.
2. Take an advisory lock for (rule, region).
3. Run the SQL with the beacon profile.
   Error, or more than 250,000 rows?          -> consecutive_errors += 1; stop. Nothing resolves.
4. Load open alerts (Pending, Firing) for (rule, region). This is a small set in normal operation.
5. Drop rows for resources with monitoring_disabled (look up only the failing ids).
6. Diff:
   new row                -> insert Pending (Firing if pending_for = 0)
   row and open alert     -> Pending past pending_for: Firing; clear clean_since if set
   open alert, no row     -> set clean_since; past resolve_after: Resolved, open_key = NULL
7. Mark alerts covered by a Silence or an active Maintenance scope as silenced (still stored).
8. New Firing, not silenced -> attach to or create an incident (incident_grouping).
9. Write all changes in chunks of 5,000 rows in one transaction. Update Rule Evaluation.

Inventory and identity. Datum stamps a sample with the producer's ID. A server that reports its sites puts the site name in a label. Each rule must say how it gets resource_id, for example labels['site']. Each resource type needs an inventory, which is the list of resources that we expect to report. Host inventory already exists as atlas_metal_server_info. Service nodes have atlas_service_node. Sites and servers need an equivalent *_info metric. If the inventory is stale, the result is Unknown. A stale inventory must not make the list of expected resources shorter.

Git-managed rules. The current checks in alerts.py become Alert Rules. CI sends them with PUT /api/beacon/alert-rules/{id}. Desk shows them as read-only. Before the PUT, CI runs POST /alert-rules/{id}/actions/test. The test runs the query in each region and returns the rows without writing anything.

8. Incidents, maintenance, silences

Stops pagingn/aYes, for its scopeYes, for its scope
Excluded from uptimeNoYes, only for its service-region rowsNever
EndsAuto-resolves only if Internal and made by BeaconAt scheduled_end or by a personAt expires_at

Maintenance rules for uptime. Only a maintenance created before its scheduled_start can exclude time from uptime. Its scope and times are frozen when it starts, so nobody can hide downtime after the fact. Only an affected service row with impact "Maintenance" excludes minutes. A single-resource scope stops paging but does not exclude a whole service-region minute. Overlapping windows count once.

After a silence ends. Alerts stay stored while silenced. If an alert still fires when the silence or maintenance ends, it pages one time.

Unlisted pages. The token route returns only approved fields: title, status, updates marked public, affected service names and public RCA. It sends Referrer-Policy: no-referrer and X-Robots-Tag: noindex. Logs redact the token. Staff can regenerate the token, which revokes the old link. Central (later) receives the incident event with the affected resource IDs and the private URL, finds the affected teams, and notifies them. Beacon does not know about teams.

9. Service status and uptime

A service is one line on the status page, such as "Sites" or "Object Storage". A service with Region scope is defined one time and evaluated in every region, so "Sites" gives one line under each region.

Each minute, the health query returns two numbers for a region: healthy and expected. expected comes from inventory, not from "who reported". A resource that stops reporting counts as unhealthy. The ratio maps to a status:

ratio = healthy / expected
expected = 0 or inventory stale  -> Unknown
ratio >= 99.5%                   -> Operational
ratio >= 95%                     -> Degraded
ratio >= 80%                     -> Partial Outage
else                             -> Major Outage
shown status = worst(computed status, impact of an open Public incident on this service)

Each finished minute adds 1 to one counter in the Service Day row. A checkpoint (last_counted_minute) makes this idempotent. Beacon splits intervals at UTC midnight. A minute with no evaluation is Unknown. Beacon does not fill a gap with the last state.

observed = all minutes - unknown_minutes
eligible = observed - maintenance_minutes
down     = partial_minutes + major_minutes          (Degraded counts as up)
uptime % = (eligible - down) / eligible             eligible = 0 -> "no data"

This is service-status uptime. It is not the share of successful customer requests. The page shows coverage (observed ÷ all minutes) next to the percentage, so unknown time is never shown as healthy.

10. On-call and paging

The setup is for a small team. It is an ordered list of responders, an optional primary override with an end time, a backup delay and a limit on repeats.

SeverityChatEmailPhone call
Critical, HighYesYesYes, with escalation
Medium, LowYesYesNo
incident Triggered
  -> call primary (override, else first active responder)
  -> no ack in backup_after_minutes  -> call next responder ... to the end of the list
  -> a full round without ack        -> wait repeat_every_minutes, repeat (max_rounds)
  -> Twilio error                    -> Notification = Failed; post "call failed" to chat and email
ack (Digits=1, email confirm, Desk button)  -> stop escalation
resolve                                     -> stop everything
  • Acknowledgement means a key press, not a pickup. Twilio <Gather> asks for 1. Only Digits=1 counts. Beacon matches the CallSid to the Notification row, then to the incident. Beacon checks the Twilio signature, and a repeated callback has no effect.
  • Email links open a confirm page that does a POST. A mail scanner that opens links must not acknowledge an incident.
  • Deferred: SMS, shift calendars and time zones per responder. The V1 night-shift table can come back later as one extra child table.

12. Status page

The mockups are in moki, project beacon-status, version 2. There are three layouts for the main page, a public incident page, an unlisted incident page and an incident history page. Ideas come from DigitalOcean (regions as rows), Railway and Cloudflare (90-day bars), Fly.io (region grid) and Hetzner (unlisted incident links).

  • Recommended: regions first. The page has a top banner and active incidents with maintenance. Below that is one row per region. A region opens to show its services, and each service has a 90-day bar. The global platform services (Dashboard, API, Billing) come last. It scales to many regions and reads well on a phone.
  • Server-rendered Jinja pages cached for 30 seconds. They work without JavaScript. Atom and RSS feeds and the public JSON use the same cache.
  • If a region has no fresh data, its services keep their last state and show "data delayed". The page never shows green for time it did not observe.

13. Datum review

We reviewed frappe/datum for the expected production load. We checked each finding in the code. Datum runs once per region, so all numbers are per region.

Assumption for sizing. 100,000 sites × 10 series every 60 s, plus 5,000 servers and hosts × 200 series every 15 s. That gives about 83,000 rows/s, or about 7.2 billion rows/day. At 10–30 bytes per compressed row, that is 70–220 GB/day. Measure the real rate with the existing daily_ingestion_stats table before you set retention.
#FindingWhy it hurts at 100kChange
P1Each HTTP request is one ClickHouse insert (providers/clickhouse.py). There is no async_insert.Thousands of producers make hundreds of small inserts per second. Each insert is a new part. Merges fall behind and ClickHouse refuses writes (TOO_MANY_PARTS).Insert with async_insert=1, wait_for_async_insert=1. Size API concurrency for the flush wait. This is the most valuable change.
P1samples is ORDER BY (resource_id, metric, ts). Datum's CLAUDE.md says reads "always name a machine".That is no longer true. Alert and status queries ask "metric X for all resources in the last 5 minutes". The primary key cannot prune that well.Add samples_recent: same columns, ORDER BY (metric, ts, resource_id), daily partitions, TTL 2 days, fed by a materialized view. Rules look back at most 24 h. Update CLAUDE.md.
P1samples and logs have no TTL. Only traces has one (7 days).At the assumed rate, raw samples grow 70–220 GB a day, without end.Set a budget. For example, raw samples for 30–45 days and logs for 14–30 days. Keep a 1-minute rollup of selected metrics for 13 months.
P2The insights reader has SELECT plus CREATE and DROP VIEW. It has no settings profile or quota.One heavy dashboard or alert query can slow down ingestion.Add a separate beacon user that has a profile: readonly=1, max_execution_time=20, memory and thread limits, max_concurrent_queries_for_user=4 and an hourly quota.
P2When ClickHouse refuses a write under load, Datum returns 400. The client timeout is 2 s and the server timeout is 30 s.Producers treat overload as a permanent error and drop data. The timeouts do not match.Return 503 for overload errors. Align the timeouts and add jitter to producer flush times.
P2resources is a ReplacingMergeTree.Without FINAL or argMax, readers see old status rows.Add a resources_latest view: argMax(status, updated_at) grouped by resource_id.
P3labels is a Map. The client blocks only a few labels with high cardinality.Group-by on whole maps costs memory. A label that keeps changing increases storage cost permanently.Move frequently filtered labels to columns. Add server-side limits on label bytes and series per resource.

Already good: compression codecs, payload caps, no shared ClickHouse session, the trace table design and cached JWKS.

Why a recent table and not a projection. A projection cannot have its own TTL. With a projection, a second sort order would cover all of history. A 2-day table limits the cost and still gives alert queries fast metric-first reads. It is still large: at the assumed rate it holds about 14 billion rows. So measure first, and keep rule lookbacks under the retention.

15. Failure modes

FailureWhat happens
A region's ClickHouse is downThe region probe fails. One "Telemetry unavailable: bom" alert (High) is created. Beacon skips that region's rules and resolves nothing. Services show their last state with "data delayed", and the minutes count as Unknown.
A rule's SQL is brokenAfter 3 errors in a row, one "Rule broken" alert is created. Other rules keep running.
Beacon is down, or the workers are stuckThe heartbeat is sent only after an evaluation cycle completes, so it stops. An external dead-man switch calls us. An external check also watches the status page.
Twilio failsThe Notification is marked Failed. Beacon posts "call failed" to chat and email, and escalation continues.
Central is down (later phase)Outbox rows wait and retry with backoff. Paging is not affected. One failed event does not block other incidents.
A worker crashes, or a job runs twiceThe advisory lock and the unique open_key prevent duplicates. Transitions are written in one transaction.
Alerts flappending_for and resolve_after need continuous evidence. A resolved episode never reopens. A new failure starts a new episode.
