A design for one small Frappe app. It reads the health that each layer of Frappe Cloud already reports, finds problems before customers do, groups them into root-cause incidents, calls the on-call engineer, tracks SLOs and error budgets, and publishes a status page.

Plan · November 2026 · Revision 6: each layer watches the layer below, SLO burn-rate alerts, an infrastructure-only resource registry · Status: proposed · Earlier rounds reviewed with GPT-6.1 Sol (high effort) and Claude Fable 5.2 (medium effort) · Mockups in moki: beacon-status v4

Summary. Beacon is one global Frappe app. Staff use Desk as a control panel, and customers see only the status page. Every layer of Frappe Cloud already watches the layer below it: Pilot pings its sites, metald checks its VMs, and Atlas checks its hosts and service nodes. Beacon does not repeat that work. It reads the counts that each layer reports to Datum, and it acts one level up. A failing site is Pilot's job. Many failing sites in a region is Beacon's job. Beacon pages on symptoms, as Google SRE recommends: each customer-facing service has an SLO, and a fast error-budget burn calls the on-call engineer. A few cause rules (a host is down, VMs fail on one host, a service node is not ready, Atlas is silent) give the incident its root cause and scope. The resource registry holds only infrastructure (hosts, VMs, service nodes), pulled from Atlas, so it stays small. Beacon only reads ClickHouse.

1. Situation

Frappe Cloud V2 sends telemetry to Datum. Datum is a write-only service in front of ClickHouse. There is one Datum and one ClickHouse in each region. Readers query ClickHouse directly with a read-only account.

Today, alerts are temporary. A script in frappe/atlas makes three Insights Alerts: P1 every 5 minutes, and two P2 alerts every hour. Each one is a large SQL query that joins about 50 checks. When it returns rows, Insights posts a Markdown message to a chat webhook. The problems:

  • There is no state. The same problem posts on every run, and nothing says "resolved".
  • There is no acknowledgement, paging or escalation.
  • You cannot mute one host or one check, or schedule maintenance.
  • One failing check hides in a long message. There is no history for each resource.
  • The Insights SQL size limit splits one logical alert into two.

Frappe Cloud V1 (frappe/press) had a full incident system: Prometheus rules, Alertmanager webhook logs, an Incident with Validating → Confirmed → Acknowledged → Resolved, Twilio calls, night shifts and silenced alerts. We keep its ideas. We drop three things: a second alerting stack to operate, "the call was answered" as acknowledgement, and mute flags spread across many DocTypes.

2. Goals, non-goals, scale

Goals

  1. Find platform problems before a customer reports them, and page the right person once, with the root cause attached.
  2. Measure each customer-facing service with an SLI and an SLO, show the error budget, and report SLA attainment.
  3. Alerts that are easy to write and have state: Pending → Firing → Resolved, one episode per problem, no duplicates.
  4. Root-cause incidents with paging, acknowledgement, updates and a root cause analysis (RCA).
  5. A status page with regions, one status for each service, 90-day uptime bars, incidents and maintenance. Unlisted incidents with a private link, like Hetzner does.
  6. Maintenance windows that stop paging and, when announced in advance, do not count against the SLO.
  7. A short integration path, so every V2 service can use it.

Non-goals for v1

  • A staff web app. Staff use Desk.
  • Checks for a single site or a single VM. The layer that owns it already watches it and tells its owner.
  • Customer alert rules and incidents in the Central dashboard. That is phase 4, and Central owns that UI.
  • Python rule scripts, probes of public URLs, anomaly detection, SLA credits, email subscriptions, several on-call teams.

Scale target

Up to 100,000 resources per region (most are sites), about 10 regions. Sites reach Beacon only as counts, so Beacon stores about 10,000 infrastructure resources per region and a few alerts. We do not design for millions.

3. Architecture

Beacon is one Frappe site. It runs outside the regions it watches. It pulls the infrastructure list from Atlas in each region, and the map from Central server IDs to Atlas VM IDs from Central. It reads each region's ClickHouse with a read-only user and writes nothing there. Beacon serves the status page itself at /, and caches each response in Redis for one minute, so outage traffic peaks do not reach ClickHouse.

4. Key decisions

D1
Each layer watches the layer below. Beacon acts one level up. Pilot owns site health, metald owns VM health, Atlas owns host and service-node health. They already detect failures and tell the owner. Beacon reads their counts. One failing site or VM is not a Beacon alert. A failure that is too wide or too frequent for one owner to explain is.
D2
Page on symptoms, explain with causes. Each customer-facing service has an SLI and an SLO. A fast error-budget burn pages (Google SRE multiwindow, multi-burn-rate alerts). A short list of cause rules finds the broken host, node or watcher, and gives the incident its scope.
D3
Rules and SLIs are ClickHouse SQL. A rule returns only failing rows: resource_id, alert_key, value, detail. An SLI returns good, valid for each reporter, such as a VM. A read-only profile limits time, memory, threads and concurrency. No Python safe_exec.
D4
The registry holds infrastructure only, pulled from Atlas. Hosts, VMs and service nodes, with their parents and status. Sites are counts, not rows. Beacon filters rule rows with its copy, so an archived or stopped resource never alerts.
D5
One Alert row per episode, written only on transitions. A firing alert causes no writes.
D6
The incident invariant. After each evaluation and each tick, every Firing alert that is not suppressed belongs to an open incident. Beacon attaches it to an ancestor's incident, an incident in the same region with a firing cause, or a recent incident of its group, else reopens or creates one.
D7
One root-cause incident, impact derived. An incident has a few scope rows, such as "host bom-h12 and everything under it". The affected set is computed from the registry when someone asks.
D8
One Incident DocType with type Incident or Maintenance. A separate small Silence mutes paging for a set time.
D9
A person decides what customers see. Beacon never publishes an incident and never reopens a public one. The only automatic public signal is the computed service status, and it changes only after 3 bad minutes.
D10
Desk is the control panel. The API is small. It covers acknowledge and resolve for chat-ops, the resource list that sources serve, and Twilio callbacks.
D11
Fail loudly, never silently resolve. A query error never resolves an alert. A region with broken telemetry gives one alert. If Beacon stops, an external dead-man switch calls us.
D12
Central integration waits for phase 4.

  a watcher fails  -> Beacon alerts on the watcher (Atlas silent, host down, region probe)

Why this works. A failure is always visible one level up. A dead site shows in Pilot's counts. A dead VM shows in metald's counts. A dead host shows in Atlas, and its metald goes silent. A failing proxy shows in its request counts. A dead Atlas or Datum shows in Beacon's probe. So Beacon never needs a "not reporting" rule for each leaf. A silent Pilot on a healthy VM is left out of the Sites SLI, and the control panel shows the coverage.

Why Pilot splits app errors. A site that fails because of its own code is the customer's problem, and Pilot already tells them. If it counted as down, 100 broken customer apps among 100,000 sites would use the whole budget of a 99.9% SLO. So Pilot asks one question for each failed ping: is the cause inside this site, or outside it?

The rule in one line: a failure is platform_down when its cause is outside the site (process, database, or the whole bench), and app_error when only that site shows it. Pilot notifies the owner in both cases, as it does today. Only platform_down uses the Sites budget.

6. One problem, end to end

Follow a host failure in Mumbai. The host bom-h12 has 30 VMs and 400 sites.

  1. 07:12. The host loses power. Its metald stops reporting, and so do the Pilots in its VMs.
  2. 07:15. The Pilots have been silent for 3 minutes. No cause alert covers them yet, so the Sites SLI leaves them out. A Pilot restart looks the same, and must not page.
  3. 07:17. Atlas's sync for bom-h12 is older than 300 s and metald has been silent for 5 minutes. The cause rule "Host down" returns bom-h12. With pending_for 60 s it fires at 07:18. Beacon creates an Internal incident with scope "bom-h12, include descendants", severity Critical. The host has no parent, so it pages at once.
  4. 07:18. Now a cause alert covers the silent reporters, so the SLIs count them as bad. Sites: 400 of 50,000 sites is 0.8% bad, a burn rate of 8 for 99.9%. Servers: 30 of 3,000 VMs is 1% bad, a burn rate of 10. Neither passes the fast page (14.4). The Servers 6-hour alert would fire after about 3.6 hours, and it would join this incident because the incident has a firing cause alert.
  5. The primary responder does not press 1. After 2 minutes (Critical), Beacon calls the second responder, who presses 1. The incident moves to Investigating.
  6. The engineer uses Publish: Unlisted, first public update, affected services "Servers · bom" and "Sites · bom", impact Partial Outage. Support copies the private link and the VM list from "Export affected resources".
  7. 07:50. The power supply is replaced. The host syncs, VMs boot, Pilots report. The cause alert recovers after resolve_after. The incident is Unlisted, so Beacon posts "all alerts resolved" to chat. The engineer posts a final update and resolves it. The control panel shows the cost: about 0.6% of the month's Sites budget and 0.8% of the Servers budget.

8. DocType reference

Original design layouts. Every implemented DocType now has the Beacon prefix in the single Beacon module. The operator review gives the latest proposed form and tab order. These older diagrams do not certify that each evidence panel or action is complete.

Each card shows one Desk form from top to bottom. Tabs come in order, and sections stack inside a tab. Columns sit side by side, and the field order in a column is the position on the form. A grey field is read-only: Beacon sets it, or an action changes it. A red star marks a required field. Below each form, the table lists its buttons. Permissions use the two roles from "Desk workflow and roles".

Two rules keep the forms safe. First, a field that drives a state machine (status, visibility, escalation, paging paused) is read-only, and only an action changes it, so every change runs the same checks. Second, a document that Beacon writes (Alert, Rule Evaluation, Resource, Service State, Service Minute, Service Day, Notification) has no New button and no delete permission.

9. Resource registry

Beacon needs to know which infrastructure exists, and how it nests: a host has VMs, and a VM can be a proxy node. It uses this to skip archived or stopped resources, to build incident scope, and to export who is affected. Sites are not in the registry. Pilot reports them as counts per VM.

The registry has one source in most regions: Atlas. It knows every host, VM and service node. A Resource Source row in Desk points Beacon at it. Another regional service that owns infrastructure can be added the same way. A region has about 10,000 rows.

GET {base_url}/api/beacon/resources        Authorization: Bearer <token>
If-None-Match: "<etag>"                     -> 304 when nothing changed
200  ETag: "<count>-<max modified>"         one gzip response, no paging
{"resources": [{"resource_id": "bom-h12", "resource_type": "Host", "parent_id": "",
                "title": "bom-h12", "status": "Active"},
               {"resource_id": "vm-7f3a", "resource_type": "Server", "parent_id": "bom-h12",
                "title": "server-a", "status": "Active"}, ...]}

Server IDs from Central. Central mints and renews Pilot's Datum token with Central's server ID, so Pilot's rows in Datum carry that ID, not the Atlas VM ID. Central already knows the map from server ID to Atlas VM ID and region. It serves the map, and Beacon pulls it like a resource list. Atlas stores nothing extra.

GET {central_url}/api/beacon/telemetry-ids    Authorization: Bearer <token>    (ETag, as above)
{"telemetry_ids": [{"telemetry_id": "srv-a91c", "region": "bom", "resource_id": "vm-7f3a"}, ...]}
  • Beacon writes telemetry_id on the matching Resource. Rule and SLI rows match on resource_id or telemetry_id.
  • Every 15 minutes Beacon fetches the map without the ETag, so an entry that arrived before Atlas listed its VM is applied. Until then, that VM's rows count as unknown_rows. A new VM is inside its 10-minute grace for most of that time.
  • If Central is down, the last map stays. Central decides nothing about which resources exist.

Contract for a source. The list is the current state from one read. The ETag comes from the row count and the newest modified time, so an unchanged list costs one cheap query. Rows have no fields that change on their own, such as usage numbers. A source sets a resource to Suspended or Terminated before it starts to tear it down.

  • Poll and diff. Every minute, Beacon calls each enabled source with its last ETag. On a 200, it compares a hash of each row with the stored row_hash and bulk-writes only the changed rows. It also updates path (for example /bom-h12/server-a) and is_checked.
  • Removal needs two fetches. A row that is missing from two good fetches in a row becomes Terminated. One missing fetch changes nothing, so a short glitch in the source cannot close a real outage.
  • Removal closes alerts at once. When a resource stops being checked (Terminated, Suspended, an ancestor not Active, monitoring disabled), the sync resolves its open alerts as "Resource removed" in the same transaction. That is not a recovery, and it pages no one.
  • A failed fetch changes nothing. A timeout, a 5xx, bad JSON or a schema error keeps the last list. The Resource Source turns red on the control panel after 15 minutes.
  • Large removals are held. If a list would uncheck more than 10% of the source's checked resources (descendants included), or if it is empty, Beacon applies the additions and changes but holds the removals. Held resources stay checked as before, with their alerts suppressed but not resolved. Beacon posts one chat message. An admin clicks "Apply held removals" when the removal is real.
  • Unknown parent. A row whose parent is not in the registry keeps its last known parent, else it is a root. The source shows an orphan count.
  • One owner for each resource. If a second source lists an ID that another source owns, Beacon ignores the row and shows a conflict on the source.
  • What Beacon checks. A resource is checked if it is Active, all its ancestors are Active, monitoring is not disabled, and its removal is not held. The sync stores this as is_checked. The 10-minute grace after active_since is applied when rows are filtered. A suspended host therefore also stops checks on its VMs.
  • ClickHouse does not get a copy. Rules and SLI queries return resource IDs. Beacon filters the rows with its own copy. So Beacon only reads ClickHouse.

-- beacon/rules/host-down.sql
-- severity: Critical   resource_type: Host   interval: 60   pending_for: 60   resolve_after: 120
SELECT a.server AS resource_id, '' AS alert_key, a.age AS value,
       concat('no host sync for ', toString(round(a.age)), ' s, metald silent') AS detail
FROM (SELECT labels['server'] AS server, value AS age
      FROM datum.latest_value(metric = 'atlas_host_sync_age_seconds', window = 900)) AS a
LEFT JOIN (SELECT resource_id, max(ts) AS last_ts FROM datum.samples_recent
           WHERE metric = 'metal_build_info' AND ts > now() - INTERVAL 15 MINUTE
           GROUP BY resource_id) AS m ON m.resource_id = a.server

Atlas reports an age for every Running host, so the rule needs no list of expected hosts. A host's Datum token uses the host name, so resource_id and the server label match. A missing metald row reads as the epoch, which counts as silent. If Atlas itself stops, the ages stop too, and "Atlas silent" fires instead.

One evaluation

Every minute, the scheduler queues each due Rule Evaluation as a job with ID evaluate:{rule}:{region}. A region runs at most 2 jobs at a time, so one slow region cannot hold every worker. Each job does this:

1. Region Unreachable? -> skip, and count the skip as a run. The region alert covers it.
2. Run the SQL as the beacon user. HTTP timeout = max_execution_time + 5 s.
   Error, duplicates, or over 50,000 rows? -> consecutive_errors += 1; stop. Nothing changes.
   3 errors in a row -> Broken: red on the control panel, in one chat digest per region per hour.
3. Gap since last_success_at > 3 x interval? -> reset started_at (Pending) and clean_since.
4. Drop rows for unknown or unchecked resources (count unknown_rows).
5. Diff with open alerts:
     new row               -> Pending (Firing at once if pending_for = 0), suppression computed now
     row, alert Pending    -> Firing once failing for pending_for
     row, alert Firing     -> clear clean_since
     no row, alert Pending -> Resolved (Cleared)
     no row, alert Firing  -> set clean_since; Resolved (Recovered) after resolve_after
6. Write the changes with bulk SQL, in chunks of 1,000 rows. The open_key makes a retry safe.
7. If this run wrote a transition, enforce the incident invariant for this region.

Timers measure continuous time. pending_for must be at least the interval. Suppression is computed when an alert is created, and when a silence or maintenance starts, ends or changes (in the tick). It is not recomputed on every run.

11. SLOs and error budgets

This follows the Google SRE book and workbook. An SLI (service level indicator) is the share of good events: good ÷ valid. An SLO (service level objective) is the target for that share over 30 days. It is a field on each Service, 99.9% by default, and an admin can change it. The error budget is what the SLO allows to fail: 0.1% of the valid events. An SLA is a promise to customers, so it is lower than the SLO and has a contract behind it. It is an optional field on the Service, and Beacon only reports on it.

An SLI query returns one row per reporter seen in the last 30 minutes: resource_id, good, valid, last_ts. Beacon drops the rows of resources that are not checked, or that are inside a Public maintenance announced in advance. A reporter with no sample for 3 minutes counts its last valid as bad only while it or an ancestor has a Firing cause alert, such as "Host down". Otherwise it is left out. So a dead host counts its VMs and sites as down, and a Pilot restart, a sleeping VM or a Datum ingest gap never looks like an outage.

-- beacon/services/sites.sql   (one row per VM seen in the last 30 minutes)
-- Pilot ships all four states with one timestamp, summed over the VM's benches.
SELECT resource_id,
       argMaxIf(value, ts, labels['state'] = 'up') AS good,
       good + argMaxIf(value, ts, labels['state'] = 'platform_down') AS valid,
       max(ts) AS last_ts
FROM datum.samples_recent
WHERE metric = 'pilot_sites' AND ts > now() - INTERVAL 30 MINUTE
GROUP BY resource_id

Burn-rate alerts

The burn rate is how fast the budget goes: (1 − good ÷ valid) ÷ (1 − SLO). A burn rate of 1 uses the whole 30-day budget in 30 days. Beacon uses the three alerts from the SRE workbook. An alert fires only if both its long and short window are over the rate. The long window proves the problem is real. The short window makes the alert resolve a few minutes after the fix.

Budget usedLong windowShort windowBurn rateAlert
2%1 hour5 min14.4High, pages

10%3 days6 hours1Low, chat and email
  • A window with fewer than 100 valid events does not alert. A burn alert pages only when 3 or more reporters are bad in its short window. With fewer, it is Low. So one VM in a small region, or one bench of 30 sites, never pages.
  • A burn alert is a normal Alert. Its rule is the service's built-in "SLO burn" rule, its resource is the Region resource, and its alert_key is fast, medium or slow. It has pending_for 0 and resolve_after 5 minutes. A service with page_on_burn off gets Medium instead of High. A global service uses the Global resource, which Beacon creates. A minute with no valid data changes nothing, the same as a query error.
  • Each minute, Beacon writes good, valid and the number of bad reporters to Service Minute, kept 3 days, and adds good and valid to Service Day. Windows up to 3 days sum Service Minute. The 30-day budget sums Service Day. An unknown or excluded minute adds nothing.

On the control panel

The workspace shows one row per service and region: status, the SLI of the last hour, budget left for 30 days, and the 1-hour and 6-hour burn rates. The "SLO and SLA" report shows each month: SLI, budget used, and whether the SLA was met. We do not automate SLA credits or release freezes. The budget is the input for that conversation.

12. Incidents and impact

The invariant

After every evaluation and every tick, Beacon takes one advisory lock for the region. It finds Firing, unsuppressed alerts with no incident (indexed: incident IS NULL). An open alert's incident is always empty or an open incident, because resolve and merge clear or move it. For each alert, in order:

  1. Ancestor. An open incident has a scope row that covers the alert's resource through its path. Join it.
  2. Cause. The alert is an SLO burn. Join the newest open incident in its region that has a Firing cause alert. Else join the newest incident in the region opened in the last 30 minutes.
  3. Group. An open incident has the alert's group key (rule and region) in its group_keys, and it is Triggered or less than 30 minutes old. Join it. An older, acknowledged incident does not swallow a second outage.
  4. Reopen. An Internal incident made by Beacon with that group key was resolved less than 30 minutes ago. Reopen it to Triggered and clear the acknowledgement.
  5. Create. Create an Internal incident in Triggered. If the resource has no parent, paging starts at once. Otherwise it waits page_delay (90 s), so a parent incident can take it.

A new cause alert in a region whose open incident has only burn alerts joins that incident and adds its scope row.

Joining is never silent. Every alert that joins posts to the incident's chat thread. A higher severity notifies again. An incident in Monitoring goes back to Investigating and pages again.

Merging. When an incident opens with a scope that covers alerts of another open, unacknowledged, Internal incident, only the covered alerts move. The other incident becomes Merged only when it is empty. Staff can merge by hand. A manual merge also moves the group keys, so the next alert of a merged region joins the target.

Scope. "Host down" and "VMs unavailable on host" incidents get the scope row "this host, include descendants". Other incidents start with the scope of their alerts. Staff can add rows.

Host bom-h12 fails                         Proxy bom-proxy-2 fails
host bom-h12      <- scope row,            proxy node bom-proxy-2   <- scope row

Who is affected? "Export affected resources" lists the hosts and VMs in scope. The sites on those VMs come from Central in phase 4.

Closing and publishing

  • An Internal incident made by Beacon resolves itself when all its alerts are resolved.
  • An Unlisted or Public incident waits for a person. Beacon posts "all alerts resolved" to chat after 30 minutes.
  • Staff cannot resolve an incident while unsuppressed alerts fire. The Resolve dialog offers "Silence the remaining alerts for N hours and resolve".
  • The Publish action is one dialog: Unlisted or Public, affected services with impact, and the first public message. Unlisted creates a 32-character token.

18. Integrating a V2 service

A service team does up to three small things. Most services need only the first.

1. Report what you watch, as counts

If your service watches things below it, report how many there are and how many fail, each minute. Do not add a label for each item. A site, a VM or a request is never a label value. A host or a service node can be one, because there are few of them.

# Pilot, once a minute per VM (datum_client)
batch = Batch("pilot", "sites")                  # counts summed over every bench on the VM
for state in ("up", "app_error", "platform_down", "maintenance"):
    batch.gauge("", counts[state], ts=when, state=state)      # -> pilot_sites{state}, one ts

Go services expose Prometheus /metrics on localhost. A service that only writes an access log can turn it into counters with Vector's log_to_metric, as the proxy does. The Vector on the node scrapes it and sends it with remote write to /v1/ingest/remote. Use one Datum sink per machine, because Datum allows 12 requests a minute per token.

# /etc/vector/conf.d/http-proxy.toml
[sources.http_proxy]
type = "prometheus_scrape"
endpoints = ["http://127.0.0.1:9180/metrics"]
scrape_interval_secs = 15
# add "http_proxy" to the inputs of the node's existing Datum sink

2. If customers use it, define an SLI

Add beacon/services/<name>.sql. It returns one row per reporter seen in the last 30 minutes: resource_id, good, valid, last_ts. The header sets the title, scope and slo_target. Count only failures that the platform causes.

3. Add a cause rule only if it points to one fix

Add beacon/rules/<name>.sql. A family of checks is one rule, with the check name as alert_key. It returns only failing rows: resource_id, alert_key, value, detail. Do not add a rule for a single leaf that your own layer already handles. Use the views that Datum provides, so that counters and freshness are right:

ViewReturns
counter_increase(metric, window)resource_id, labels, increase, with counter resets handled for each series
latest_value(metric, window)resource_id, labels, value, ts, the newest sample in the window
CREATE VIEW datum.counter_increase AS          -- parameterized view, shipped by Datum
SELECT resource_id, labels, length(vals) AS samples,
       arraySum(arrayMap((d, v) -> if(d >= 0, d, v), arrayDifference(vals), vals)) AS increase
FROM (
  SELECT resource_id, labels, arrayMap(x -> x.2, arraySort(groupArray((ts, value)))) AS vals
  FROM datum.samples_recent
  WHERE metric = {metric:String} AND ts > now() - toIntervalSecond({window:UInt32})
  GROUP BY resource_id, labels
);
-- A drop means a reset: the new value is growth. Tested in clickhouse local 26.10.

Where the files live

In v1, rules and SLIs live in Beacon's repository. A team opens a pull request there. Beacon loads the files on bench migrate, and a loaded rule is read-only in Desk except enabled. The Test button on the Alert Rule and Service forms runs a query in every region and checks the contract. Sync from each team's own repository can come later, when more teams write rules.

25. What we do not build

  • Checks for a single site or VM. Their owner layer has them.
  • Probes of public URLs. They would wake Sleepy VMs and duplicate Pilot.
  • Anomaly detection or learned baselines. Fixed thresholds and SLO burn rates first.
  • SLA credits, and release freezes driven by the error budget.
  • A staff web app, Python rules, a copy of the metrics, a CRUD API that copies Desk.
  • Shift calendars, SMS, several on-call teams, email subscriptions.
  • Rule sync from each team's repository, for now. Rules come through pull requests to Beacon.
  • Automatic publishing or automatic reopening of public incidents.
