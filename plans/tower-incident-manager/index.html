Tower: incident manager and status page for Frappe Cloud V2

A design for one small Frappe app. It turns Datum metrics into alerts, groups alerts into root-cause incidents, calls the on-call engineer, and publishes a status page.

Plan · November 2026 · Final design (revision 5: renamed from Beacon to Tower, pull-based resource registry, DocType reference) · Status: proposed · Reviewed in four rounds with two other models (GPT-6.1 Sol, high effort; Claude Fable 5.2, medium effort) · Mockups in moki: beacon-status v3

Summary. Tower is one global Frappe app. Staff use Desk, and customers see only the status page. A few services in each region serve their resource lists on one endpoint, and Tower pulls them into its registry. Alert rules are ClickHouse SQL queries that return only the failing resources. Tower stores one row for each alert episode and writes only state changes, so 100,000 resources per region are cheap. One invariant drives incidents: every firing alert that is not muted belongs to an open incident. Problems high in the tree, such as a host or a proxy, give one root-cause incident with derived impact, not one entry for each server. Datum needs three important changes: async inserts, a recent-data table sorted by metric, and retention.

1. Situation

Frappe Cloud V2 sends telemetry to Datum. Datum is a write-only service in front of ClickHouse. There is one Datum and one ClickHouse in each region. Readers query ClickHouse directly with a read-only account.

Today, alerts are temporary. A script in frappe/atlas makes three Insights Alerts: P1 every 5 minutes, and two P2 alerts every hour. Each one is a large SQL query that joins about 50 checks. When it returns rows, Insights posts a Markdown message to a chat webhook. The problems:

  • There is no state. The same problem posts on every run, and nothing says "resolved".
  • There is no acknowledgement, paging or escalation.
  • You cannot mute one host or one check, or schedule maintenance.
  • One failing check hides in a long message. There is no history for each resource.
  • The Insights SQL size limit splits one logical alert into two.

Frappe Cloud V1 (frappe/press) had a full incident system: Prometheus rules, Alertmanager webhook logs, an Incident with Validating → Confirmed → Acknowledged → Resolved, Twilio calls, night shifts and silenced alerts. We keep its ideas. We drop three things: a second alerting stack to operate, "the call was answered" as acknowledgement, and mute flags spread across many DocTypes.

2. Goals, non-goals, scale

Goals

  1. Alerts that are easy to write and have state: Pending → Firing → Resolved, one episode per problem, no duplicates.
  2. Root-cause incidents with paging, acknowledgement, updates and a root cause analysis (RCA).
  3. A status page with regions, one status for each service, 90-day uptime bars, incidents and maintenance.
  4. Unlisted incidents with a private link for affected customers, like Hetzner does.
  5. Maintenance windows that stop paging and, when planned in advance, do not count against uptime.
  6. A short integration path, so every V2 service can use it.

Non-goals for v1

  • A staff web app. Staff use Desk.
  • Customer alert rules and incidents in the Central dashboard. That is phase 4, and Central owns that UI. Central already shows metrics from Atlas and Datum.
  • Python rule scripts, probes run by Tower, email subscriptions, AI investigation, several on-call teams.

Scale target

Up to 100,000 resources per region (most are sites), about 10 regions. The design must stay simple at that size. We do not design for millions.

3. Architecture

Tower is one Frappe site. It runs outside the regions it watches. It pulls resource lists from a few services in each region. It reads each region's ClickHouse with a limited user and writes only one thing there: its registry mirror, in its own tower database. The status page is static files in an object storage bucket behind a CDN. Tower uploads them every 30 seconds. So the status page stays up when Tower is down, and it handles the traffic peaks that come with an outage.

PartJob
Datum + ClickHouse (per region)Stores samples, logs and traces. Owns telemetry.
Registry syncEvery minute, pulls each Resource Source, updates MariaDB and writes the mirror to ClickHouse.
Tower evaluatorScheduler jobs and an RQ queue named tower. Runs rule and service queries and writes transitions.
Tower tickOne job every minute for time-based work: maintenance start and end, silence expiry, escalation steps, closing alerts of disabled rules, the heartbeat.
DeskStaff work incidents and configure everything. One Tower workspace is the landing page.
Status builderRenders static HTML and JSON every 30 s and uploads only changed files.
NotifiersTwilio voice, email (Frappe Email Account), a chat webhook.

4. Key decisions

D1
Rules are ClickHouse SQL. A query returns only failing rows. ClickHouse evaluates all resources in one set-based query, and no samples leave ClickHouse. The current checks are already SQL. A read-only profile limits time, memory, threads and concurrency. We do not add Python safe_exec: it is a second runtime that is harder to review and to limit.
D2
One result contract. A rule returns resource_id, alert_key, value, detail. alert_key separates two problems on one resource, such as two disks. A missing row means "healthy" only after a successful query. Duplicate (resource_id, alert_key) rows, or more rows than the limit, fail the evaluation. Nothing is truncated.
D3
Regional services serve their resource lists, and Tower pulls them. A few services in each region, such as Atlas and the service that owns sites, serve one endpoint with their full list. Tower polls it every minute and replaces that source's list. Central is not in the path. Tower checks only resources that are Active, with Active ancestors, and not excluded. So an archived or stopped resource never looks "down".
D4
One Alert row per episode, written only on transitions. A firing alert causes no writes. A mass outage writes its rows once.
D5
The incident invariant. After each evaluation and each tick, every Firing alert that is not suppressed must belong to an open incident. Tower attaches it to an ancestor's incident, else to its group's incident, else reopens or creates one. This one rule covers new alerts, ended silences, ended maintenance and incidents that someone resolved too early.
D6
One root-cause incident, impact derived. An incident has a few scope rows, such as "host bom-h12 and everything under it" or "all sites in bom". The affected set is computed from the registry when someone asks. Child alerts join the parent incident and do not page.
D7
One Incident DocType with type Incident or Maintenance, as in the owner's model. Both have updates, scope, affected services and visibility. A separate small Silence mutes paging for a set time.
D8
A person decides what customers see. Tower never publishes an incident and never reopens a public one. The only automatic public signal is the computed service status.
D9
Uptime counters live in MariaDB, one row per service, region and UTC day. Minutes that Tower did not observe count as unknown, never as healthy.
D10
Desk is the admin UI. The API is small. It covers rule sync from Git, staff actions and Twilio callbacks. The public status page is static files, so it needs no API.
D11
Fail loudly, never silently resolve. A query error never resolves an alert. A region with broken telemetry gives one alert, not one for each rule. If Tower stops, an external dead-man switch calls us.
D12
Central integration waits for phase 4. The outbox, customer rules and Central routes are designed here but not built in v1.

5. One alert, end to end

Follow a host failure in Mumbai. The host bom-h12 has 30 VMs and 400 sites.

  1. 07:12. The host loses power. VMs and sites stop reporting. Their "not reporting" rules return rows, and the alerts become Pending.
  2. 07:14. A VM alert reaches its pending_for and becomes Firing. No incident covers it, so Tower creates an Internal incident in status Triggered. The VM has a parent, so paging waits page_delay (90 s).
  3. 07:15. "Host not reporting" becomes Firing. Tower creates the host incident with scope "bom-h12, include descendants". The VM incident is not acknowledged and the host covers it, so it is merged. Every VM and site alert now joins the host incident.
  4. The host has no parent, so the host incident pages at once. Severity High calls the primary responder. The call says "Press 1 to acknowledge". There is no key press. After 5 minutes, Tower calls the second responder, who presses 1. The incident moves to Investigating.
  5. The engineer uses the Publish action: visibility Unlisted, first public update, affected service "Servers · bom" with impact Major Outage. Support copies the private link and the list of affected resources from Desk and sends it to the affected teams. In phase 4, Central does this.
  6. The power supply is replaced. The alerts get clean results and become Resolved (Recovered) after resolve_after. The incident is Unlisted, so Tower posts "all alerts resolved" to chat. The engineer posts a final update and resolves it.

7. DocType reference

Each card shows one Desk form from top to bottom. Tabs come in order, and sections stack inside a tab. Columns sit side by side, and the field order in a column is the position on the form. A grey field is read-only: Tower sets it, or an action changes it. A red star marks a required field. Below each form, the table lists its buttons. Permissions use the two roles from "Desk workflow and roles".

Two rules keep the forms safe. First, a field that drives a state machine (status, visibility, escalation, paging paused) is read-only, and only an action changes it, so every change runs the same checks. Second, a document that Tower writes (Alert, Rule Evaluation, Resource, Service State, Service Day, Notification) has no New button and no delete permission.

8. Resource registry

Tower must know what to track. If it looked only at telemetry, an archived resource would look like a dead one. So Tower keeps a registry for each region. A few services in each region own the resources, and each one serves its full list on one endpoint. Tower pulls the lists. Sources do not push, do not send deletes and keep no sync state.

Source (in each region)Serves
AtlasHosts, VMs (servers), proxy and WireGuard gateway nodes, storage gateways and nodes, Atlas itself
The service that owns sitesSites, with parent_id = the server (see Open questions)
Any other regional serviceThe resources it owns. A Tower Admin adds a Resource Source in Desk.
GET {base_url}/api/tower/resources        Authorization: Bearer <token>
If-None-Match: "<etag>"                     -> 304 when nothing changed
200  ETag: "<hash of the list>"             one gzip response, at most 100,000 rows
{"resources": [{"resource_id": "bom-h12", "resource_type": "Host", "parent_id": "",
                "title": "bom-h12", "status": "Active", "labels": {}}, ...]}

The list is the source's current state from one read, so it is always consistent. 100,000 rows are about 15 MB of JSON and about 1.5 MB compressed. There is no paging, so a list can never be half-read.

  • Poll. Every minute, Tower calls each enabled source with its last ETag. An unchanged list returns 304 and costs almost nothing.
  • Replace, never merge. A 200 replaces that source's whole list in one MariaDB transaction, and Tower writes only the rows that changed. A resource that is missing from the list is gone. There are no delete events, no ordering rules and no race between a change and a full list, because the source always serves what is true now.
  • Removing a resource. The source stops listing it, or lists it as Suspended or Terminated. Within a minute, Tower stops checking it, and its open alerts resolve as "Resource removed". That is not a recovery and pages no one. The default pending_for of "not reporting" rules (5 min) is longer than the poll interval, so an archived resource leaves the list before its alert can fire.
  • A failed fetch changes nothing. A timeout, a 5xx, bad JSON or a schema error keeps the last list. After 15 minutes of failed fetches, Tower raises one "Registry stale" alert. If Atlas is down, its resources stay registered, so nothing looks down because of the registry.
  • A big shrink is refused. A response that removes more than 10% of the source's rows (and at least 50 rows) is not applied. The old list stays, and Tower raises "Registry shrink refused". A Tower Admin clicks "Apply pending list" in Desk if the shrink is real. This stops a buggy or empty response from quietly closing real alerts.
  • One owner for each resource. A resource_id is unique in a region. If a second source lists an ID that another source owns, Tower ignores that row and raises one Low "Registry conflict" alert. A move inside one source, such as a site that moves to another server, is atomic: the next list has the new parent.
  • What Tower checks. A resource is checked only if it is Active, all its ancestors are Active, monitoring_disabled is off, and it has been Active longer than the rule's new_resource_grace. A suspended host therefore also stops checks on its VMs and sites.
  • Mirror in ClickHouse. "Not reporting" rules and service health queries join the registry. So when a region's copy changes, Tower writes it to that region's ClickHouse, at most once a minute. It fills tower.resources_next and swaps it in with EXCHANGE TABLES. There is one writer and one atomic swap of about 100,000 rows. If the write fails, the old mirror stays, and Tower tries again the next minute.
CREATE DATABASE tower;                 -- in each region's ClickHouse; only Tower writes here
CREATE TABLE tower.resources (
  resource_id String, resource_type LowCardinality(String), parent_id String,
  status Enum8('Pending' = 1, 'Active' = 2, 'Suspended' = 3, 'Terminated' = 4),
  checked Bool,                         -- Active, ancestors Active, monitoring not disabled
  labels Map(LowCardinality(String), String)
) ENGINE = MergeTree ORDER BY (resource_type, resource_id);
CREATE TABLE tower.resources_next AS tower.resources;

-- each sync
TRUNCATE TABLE tower.resources_next;

Tested. The swap, a "not reporting" join on tower.resources and counter_increase below ran in clickhouse local 26.10.3.7 against sample data: an old list, a new list without one site, and a counter reset. The results were as expected.

9. Rule evaluation

Every minute, the scheduler queues each due Rule Evaluation as a job with ID evaluate:{rule}:{region}, with some jitter. Each job does this:

1. Region telemetry Unreachable?             -> skip. The region alert covers it.
2. Take an advisory lock for (rule, region).
3. Run the SQL with the tower profile.
   Error, duplicates, or over 250,000 rows?   -> consecutive_errors += 1; stop. Nothing changes.
4. Gap since last_success_at > 3 x interval? -> reset started_at (Pending) and clean_since.
5. Filter rows with Tower's Resource copy:
   unknown resource_id                        -> drop, count in unknown_rows
   not checked (status, ancestors, disabled, grace) -> drop
6. Close open alerts whose resource is no longer checked:
   Resolved (Resource removed) or Resolved (Disabled). These never count as recovery.
7. Diff the rest with open alerts:
   new row                       -> Pending (Firing at once if pending_for = 0)
   row, alert Pending            -> Firing once failing for pending_for
   row, alert Firing             -> clear clean_since
   no row, alert Pending         -> Resolved (Cleared)
   no row, alert Firing          -> set clean_since; Resolved (Recovered) after resolve_after
8. Recompute suppressed for open alerts (Silence, In Progress maintenance scope).
9. Write changes in chunks of 5,000 rows in one transaction. Update Rule Evaluation.
10. Enforce the incident invariant for this region (see Incidents).

Time-based work runs in the tick every minute. It starts and ends maintenance, recomputes suppression when a silence ends, steps escalations, and closes the open alerts of disabled rules and regions with "Disabled". After each step it enforces the invariant. The tick sends the heartbeat only if no Rule Evaluation is overdue by more than 2 intervals.

Region telemetry is checked first, every minute. Unreachable: the ClickHouse probe fails. Suspect: fewer than 50% of the region's checked resources sent a sample in the last 5 minutes. Rules still run and page, because it can be a real outage. Only the public status of that region is frozen. Two good checks return the region to OK.

10. Incidents and impact

The invariant

After every evaluation and every tick, Tower takes one advisory lock for the region and checks each Firing alert that is not suppressed and is not in an open incident. In order:

  1. Ancestor. If an open incident has a scope row that covers the alert's resource through an ancestor, join it. No page.
  2. Group. If an open incident has the alert's group_key (rule and region by default), join it. A higher severity raises the incident and notifies again (see Paging).
  3. Reopen. If an incident with that group_key was resolved less than reopen_window_minutes ago, was Internal and was created by Tower, reopen it to Triggered.
  4. Create. Otherwise create an Internal incident in Triggered with that group_key. If the resource has no parent, paging starts at once. Otherwise it waits page_delay, so a parent incident can merge it.

When an incident opens with a scope that covers other open incidents, Tower merges each covered incident that nobody acknowledged and that is Internal. Their alerts move, their status becomes Merged, and merged_into is set. Staff can also merge by hand, for example to join one problem across regions.

An incident created by Tower from a "not reporting" rule for a resource with children gets the scope row "this resource, include descendants". Other incidents start with the scope of their alerts. Staff can add scope rows.

Is X affected? Tower walks up the parent chain of X (at most 4 steps). X is affected if a scope row matches X, matches an ancestor with include_descendants, or matches its region and type with a blank ID. A scope row with only a region covers the whole region.

Who is affected? Desk has "Export affected resources" (CSV), which expands the scope from the registry. In v1, support uses it with "Copy private link" to tell customers. In phase 4, Central does this through the API.

Closing

  • An Internal incident created by Tower resolves itself when all its alerts are resolved, in any open status.
  • An Unlisted or Public incident waits for a person. Tower posts "all alerts resolved" to chat after 30 minutes.
  • Staff cannot resolve an incident while it has Firing alerts that are not suppressed. The Resolve dialog offers "Silence the remaining alerts for N hours and resolve". So no alert is left without an incident.

Publishing

The Publish action is one dialog: visibility (Unlisted or Public), affected services with impact, and the first public message, which is required. After that, new updates are public by default. Unlisted creates a 32-character token. Internal clears it. Each visibility change is in the document history.

12. Service status and uptime

A service is one line on the status page, such as "Sites" or "Object Storage". A Region-scope service is defined once and evaluated in each region. A Global service, such as Dashboard or API, reads the ClickHouse of its query_region.

Each minute, the health query returns healthy and expected. expected is the number of checked resources in the registry mirror (tower.resources). A resource counts as healthy only if it has a sample from the last 5 minutes, so a resource that stops reporting counts as unhealthy. Tower refuses a result with healthy < 0 or healthy > expected and counts that minute as Unknown. Health counts platform failures only. A site that returns 500 from its own code is healthy for the platform. If it were not, a few broken customer apps in 100,000 sites would keep "Sites" Degraded.

Checked in this order:
region Unreachable, query error, invalid result, expected = 0 -> Unknown
In Progress maintenance lists this service + region (impact Maintenance) -> Maintenance
ratio = healthy / expected:  >= 99.5% Operational, >= 95% Degraded, >= 80% Partial Outage, else Major Outage

Shown on the page: worst(computed, impact of open Public incidents)
Unknown, or region Suspect: worst(last computed state before the freeze, impact of open Public incidents),
                             with "data delayed"
Minute counted as: Unknown or Suspect -> unknown; Maintenance -> maintenance if excluded_from_uptime,
                   else by ratio; otherwise the computed state. Idempotent through last_counted_minute.

observed = all minutes - unknown_minutes
eligible = observed - maintenance_minutes
down     = partial_minutes + major_minutes          (Degraded counts as up)
uptime % = (eligible - down) / eligible             eligible = 0 -> "no data"

This is service-status uptime. It is not the share of successful customer requests. The page shows coverage (observed ÷ all minutes) next to it.

16. Integrating a V2 service

For a node that Atlas manages, a service team does two things: export metrics and write rules. Atlas already gives the node an identity, a Datum token and a registry entry. A service that owns resources Atlas does not know about serves GET /api/tower/resources, and a Tower Admin adds it as a Resource Source. Standard rules (not reporting, disk, memory, OOM kills, clock, failed units) apply to every registered node that runs the standard Vector host metrics.

1. Export metrics

Go services expose Prometheus /metrics on localhost. The Vector on the node scrapes it and sends it with remote write. Datum already accepts remote write v1 on /v1/ingest/remote. Add a source and append it to the existing Datum sink:

# /etc/vector/conf.d/http-proxy.toml
[sources.http_proxy]
type = "prometheus_scrape"
endpoints = ["http://127.0.0.1:9180/metrics"]
scrape_interval_secs = 15

# the node's existing sink: add "http_proxy" to inputs. One sink per machine, because
# Datum allows 12 requests a minute per token; keep batch.timeout_secs at 10 or more.

Frappe apps and Python daemons use datum_client (Batch, record). Name metrics <namespace>_<subsystem>_<target>_<unit>, for example proxy_http_responses_total. Keep labels small and stable.

2. Write rules

Put each rule in tower/rules/<name>.sql in the service's repository. The header keys are the Alert Rule field names. Use the standard views, which Datum provides, so that counters and freshness are right:

ViewReturns
counter_increase(metric, window)resource_id, labels, increase, with resets handled for each series
latest_value(metric, window)resource_id, labels, value, ts, the newest sample in the window
last_seen(window)resource_id, last_ts, for "not reporting" rules joined with tower.resources
CREATE VIEW datum.counter_increase AS          -- parameterized view, shipped by Datum
SELECT resource_id, labels, length(vals) AS samples,
       arraySum(arrayMap((d, v) -> if(d >= 0, d, v), arrayDifference(vals), vals)) AS increase
FROM (
  SELECT resource_id, labels, arrayMap(x -> x.2, arraySort(groupArray((ts, value)))) AS vals
  FROM datum.samples_recent
  WHERE metric = {metric:String} AND ts > now() - toIntervalSecond({window:UInt32})
  GROUP BY resource_id, labels
);
-- The first sample in the window is the baseline. A drop means a reset: the new value is growth.
-- A series with fewer than 2 samples has increase 0; rules can require samples >= 2.
-- tower/rules/upstream-errors.sql
-- title: Proxy 502/504 above 5% of requests
-- owner_team: http-proxy
-- severity: High
-- resource_type: Proxy Server
-- interval: 60
-- pending_for: 600
-- resolve_after: 300
-- runbook_url: https://github.com/frappe/atlas/blob/develop/docs/operate/proxy.md
SELECT resource_id, '' AS alert_key,
       sumIf(increase, labels['code'] IN ('502', '504')) / nullIf(sum(increase), 0) * 100 AS value,
       concat(toString(round(value, 1)), '% upstream errors') AS detail
FROM datum.counter_increase(metric = 'proxy_http_responses_total', window = 600)
GROUP BY resource_id
HAVING value > 5

The rule does not need to filter for Active resources. Tower does that with its registry copy (evaluation step 5). A customer-facing service adds tower/services/<name>.sql with a health query that returns healthy, expected.

3. Test and sync from CI

$ tower-rules query --region bom "SELECT ..."   # ad-hoc read-only query, for writing SQL
$ tower-rules test tower/                      # every candidate rule and service in every region
$ tower-rules sync tower/                      # upsert; disable what this repository removed

tower-rules is one standard-library Python script in the Tower repository. It calls two API routes with a staff token. query sends one candidate with "raw": true to the test route: no contract checks, at most 100 rows, the same read-only limits. Developers do not need ClickHouse credentials. test runs the candidate SQL, not the saved rule. It checks the contract (columns, types, duplicates, row limit) and reports rows, duration and errors for each region. An unreachable region is a warning, not a failure. sync touches only rules and services of that repository, and each rule_key is <repository>:<path>.

4. Only for nodes Atlas does not manage

  • Ask Atlas for a Datum token for the machine. Atlas renews tokens daily into the node's config file.
  • Register the machine and its children with Datum.register(resources, full=True) every 15 minutes, and send changes at once.
  • A new resource_type is a plain string. It needs no Tower release.

Outbound events are signed with HMAC-SHA256, carry event_id and a per-incident sequence, and are delivered at least once:

18. Status page

The mockups are in moki, project beacon-status, version 3 (the slug keeps the old name). They have three layouts for the main page, a public incident page, an unlisted incident page and a history page. The ideas come from DigitalOcean (regions as rows), Railway and Cloudflare (90-day bars), Fly.io (region grid) and Hetzner (unlisted incident links).

  • Recommended: regions first. At the top there is a banner, then active incidents and maintenance. Below that, each region is one row that opens to its services with 90-day bars. The global services come last.
  • The page is static HTML that works without JavaScript. It shows "Updated <time>", so a stale page is visible.
  • A frozen region (Unknown or Suspect) shows its last state with "data delayed".

19. Desk workflow and roles

The Tower workspace is the landing page. It shows open incidents, Firing alerts that are not suppressed, broken rules, stale registries and regions, who is primary now, and red banners for paging_paused or a missing responder.

Working an incident: Acknowledge → Post update → Publish (if customers need to know) → Resolve → write the RCA. Buttons on the form: Acknowledge, Post update, Publish, Page on-call, Merge into, Copy private link, Export affected resources, Resolve. On an alert: Silence. On the list: New maintenance. The DocType reference lists every button and when it shows.

RoleCan
Tower ResponderAcknowledge, update, publish and resolve incidents. Create maintenance and silences. See private links. Set the primary override.
Tower AdminEverything above. Also rules, services, regions, resource sources, monitoring on resources, the responder list, channels, paging pause, and the staff API token for rule sync.

The Tower site's system time zone is UTC. Forms show UTC next to time fields, so a maintenance start is never ambiguous around daylight saving changes.

20. Datum changes

We reviewed frappe/datum for the expected load and the new uses. We checked each finding in the code. All numbers are per region.

Sizing assumption. 100,000 sites × 10 series every 60 s, plus 5,000 servers and hosts × 200 series every 15 s. That is about 83,000 rows/s, or 7.2 billion rows/day, which is 70–220 GB/day at 10–30 bytes per compressed row. Measure the real rate with daily_ingestion_stats before you set retention.
#Finding (verified)Change
1 P1Each request is one ClickHouse insert, without async_insert (providers/clickhouse.py). Many small parts make merges fall behind, and then writes are refused.Insert with async_insert=1, wait_for_async_insert=1. Size API concurrency for the flush wait. Most valuable change.
2 P1samples is ordered by (resource_id, metric, ts). Alert queries ask for "metric X, all resources, last minutes". CLAUDE.md says reads always name a machine. That is no longer true.Add samples_recent: ORDER BY (metric, ts, resource_id), daily partitions, TTL 2 days, filled by a materialized view. A projection cannot have its own TTL. Add the views counter_increase, latest_value and last_seen. Update CLAUDE.md.
3 P1samples and logs have no TTL. Only traces has one.Set a budget, for example 30–45 days of raw samples and 14–30 days of logs, plus a 1-minute rollup of selected metrics for 13 months.
4 P2resources holds only ID and status. Writes need the admin token, one resource per call, 60 a minute (routes/v1/resource.py).No change for Tower: it pulls lists from the regional services. Create the tower database in each region and let the tower user write only there.
5 P2The insights reader can create and drop views and has no limits.Add a tower user with a read-only profile: max_execution_time=20, memory and thread limits, max_concurrent_queries_for_user=4 and a quota.
6 P2A write that ClickHouse refuses under load returns 400 (not retryable). The client timeout is 2 s and the server's is 30 s.Return 503 for overload errors. Align the timeouts. Add jitter to producer flushes.
7 P2Sample timestamps are not bounded.Reject samples more than 5 min in the future or more than 2 days old.
8 P2datum_client removes a batch before it posts. It does not retry, and it logs "unreachable" only at debug level.Log "unreachable" as a warning, rate-limited. Add Datum.register(). Keep "a gap beats a stalled producer".
9 P3Rate limits are kept per process and per caller and route. Labels are a Map with few guards.Document "one sink per machine". Later, move frequently used labels to columns and add series limits.

Already good: remote write v1 support, compression codecs, payload caps, no shared ClickHouse session, the trace table and cached JWKS. Tokens last 7 days without a revocation list, and Atlas renews them daily.

23. What we do not build

  • A staff web app, Python rules, our own probes, a copy of the metrics.
  • A CRUD API that copies Desk.
  • Shift calendars, SMS, a severity × channel matrix, several on-call teams.
  • Email subscriptions. Feeds and JSON first.
  • Automatic publishing or automatic reopening of public incidents.
