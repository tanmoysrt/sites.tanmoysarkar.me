1. Situation

metald is the daemon on each Metal host. It runs the Firecracker VMs, their network, and their consoles. Atlas builds it from the monorepo and gives it to the hosts. These are the problems with that process today:

  • The binary changes without notice. Each Atlas deploy that changes metal/ builds a new metald and links it in Atlas Settings. A new host install then gets that binary at once.
  • No version on a host. Atlas does not know which metald runs on which host.
  • No phased rollout. The bulk "Upgrade Metald" action in the Metal Server list upgrades all selected hosts at the same time. It has no batches, no wait time and no stop on failure.
  • A weak health check. upgrade-metald.sh rolls back only when systemd reports the unit inactive in the first 5 seconds. A crash one minute later stays in place.
  • Refused connections during a restart. A restart closes the API listeners. Atlas calls fail with "connection refused" until the new process listens again.
  • No wg-mesh upgrade. Only the install path delivers atlas-wg-mesh. After that, nothing updates it.

2. Scope

In this change setLater, as separate work
  1. The operator can set a build version. Without one, the version is a development timestamp.
  2. Each host reports its metald and wg-mesh versions, and Atlas shows them.
  3. A new Operations module with the Metald Update doctype: batches, wait and watch, health gate, pause, resume and cancel.
  4. A safer upgrade on each host: a readiness check, a VM unit check, and self-rollback after a late crash.
  5. No refused connections during a restart: the listening sockets stay in the systemd file descriptor store.
  6. wg-mesh ships in the same update, with a CI check for BPF map compatibility.
  • An Atlas maintenance mode (writes return 503 with Retry-After), and a deploy that does not restart socket.io. This needs the production process layout first.
  • The console page reconnects after a metald restart.
  • A Metal API breaking-change check in CI (oasdiff), and feature flags so a new Atlas can call an old metald.
  • An idempotent patch runner in metald for state on the host. No current change needs it.
  • A phased http-proxy rollout that uses the same rollout code.
  • An end-to-end test on bare metal (#194), a release branch, and release reports.

tableflip is not needed. Section 7 explains why.

3. Build version

There is no release system yet. So the version is optional input to the build:

pilot --site atlas.localhost build-metald --version 1.4.0   # metald 1.4.0
pilot --site atlas.localhost build-metald                   # metald dev-20261013T101500Z
pilot --site atlas.localhost build-wg-mesh --version 1.4.0  # same rule for wg-mesh
  • Atlas runs make build VERSION=<version>. Without --version, the version is dev- followed by the UTC build time.
  • The default in metal/Makefile and services/wg-mesh/Makefile changes from git describe to the same development timestamp. This keeps one rule for each build path.
  • The after_migrate build uses the development timestamp. It still builds only when the source digest changes.
  • A --version that is different from the stored version builds again, even when the source is unchanged.
  • New fields in the Atlas Settings "Metal Daemon" section: metald_version and wg_mesh_version (read only), next to the existing file and hash fields.

4. Version on each host

  • POST /v1/sync already runs every 10 seconds for each host. Its response gets two optional fields: metald_version and wg_mesh_version. metald reads the wg-mesh version once at startup.
  • Host sync writes the values to the Metal Server only when they change. This is the same pattern as private_network_mac_address.
  • An old metald does not send the fields. The Metal Server then shows no version.
  • The Metal Server list shows a "Metald Version" column, so an operator can filter the hosts that are not on a version.

5. Metald Update doctype

An operator uses one Metald Update record to move a set of hosts to one pinned build. The record upgrades the hosts in batches. After each batch it waits, checks the health of the hosts, and then continues. On any failure it pauses.

Rollout example

Twelve hosts, with a canary size of 1, a batch size of 5 and a wait of 10 minutes:

How it works

  1. Create. The record copies the version, the files and the hashes from Atlas Settings. It adds each Running Metal Server whose metald_version is different. The operator can remove or reorder rows. The Metal Server list action "Upgrade Metald" changes to "Create Metald Update", which uses the selected servers.
  2. Start. This assigns batch numbers from the row order. It fails when another update is Running or Paused, or when a server is in another open update.
  3. Rollout job. It runs every minute with one job ID, so only one copy runs. For the current batch, it locks the record and sets each Pending row to Upgrading. It commits, and then it queues one host job for each row. A server that is not Running gets the Skipped status, which does not count as a failure.
  4. Host job. It uses the Metal Server metald_job_id, so it never runs next to another metald operation on that host. It runs upgrade-metald.sh with the pinned URLs and hashes. Then it writes only its own row: Upgraded or Failed, the SSH Task, and the message.
  5. Watch. When all rows in the batch are done, any Failed row pauses the update. If no row failed, the job sets wait_until to now plus wait_minutes.
  6. Health gate. After the wait, each upgraded host must meet two conditions. It must report the target version, and its last sync must be less than 2 minutes old. If a host fails the gate, its row becomes Failed and the update pauses.
  7. Next batch or, when no rows are left, Completed.
  8. Pause stops new batches. Host jobs that are running finish. Resume sets Failed rows back to Pending and continues. Cancel is final.
  9. Stale row. If a row is Upgrading for longer than the script timeout plus 5 minutes, and its job is gone, the row becomes Failed with the message "upgrade job stopped".
  10. Roll back the fleet. Duplicate an older Metald Update. A duplicate keeps its pinned files. The cleanup of unlinked files, which runs every 15 minutes, keeps every file that a Metald Update links.

The "Upgrade Metald" button on a single Metal Server form stays. It is the quick path for one host, and it uses the latest build.

6. Upgrade on one host

These steps are added to upgrade-metald.sh. The download, the hash check, the version smoke test and the backup already exist.

  • Both binaries. The script installs metald and atlas-wg-mesh, and keeps a .previous copy of each. metald runs EnsureHost on each start, so the restart applies the new BPF release (section 8).
  • Readiness. When startup is complete (mesh set up, consoles and listeners adopted, servers serving), metald sends STATUS=ready <version> to systemd. The script waits up to 60 seconds until systemctl show -p StatusText shows that value.
  • VM check. The script compares the number of active metal-vm@ units before and after the restart. If the number drops, the host fails. The rollout stops before the next host.
  • Self-rollback after the script ends. The script installs a drop-in, metal.service.d/rollback.conf, with OnFailure=metal-rollback.service. It also writes /var/lib/metal/upgrade.json, which records an expiry time of 30 minutes. Assume that the new metald crash-loops until systemd stops it, inside that window. The rollback unit then restores the .previous binaries and starts metal.service again. After the window, the marker has no effect.

Why STATUS and not Type=notify: with Type=notify, a rollback to an old binary that never sends READY=1 would hang until the start timeout, and then fail. STATUS works with the current unit, which already has NotifyAccess=main. If a very old unit does not have that setting, the script checks only is-active and prints a warning.

7. Restart without refused connections

  • metald stores its three listening sockets in the systemd file descriptor store. The sockets are the API (9000), coordination (9001) and migration transfer (9002) listeners. The PTY masters of the VM consoles already use this store.
  • At startup, metald takes the stored socket that has the configured address. If there is none, it listens and stores the new socket. If the address changed, it removes the old socket from the store.
  • During a restart, the kernel keeps the socket open. New connections wait in the accept queue. Atlas sees a slower response, not "connection refused". The Atlas Metal client allows 5 seconds to connect and 30 to 60 seconds to read, so a restart of a few seconds fits in that time. We will measure the restart time on the development hosts.
  • The current graceful shutdown already lets requests in progress finish, with a limit of 30 seconds.
  • Open console WebSockets and running migration streams still close. Migrations continue from their resume token, as today. Console reconnect is later work.
  • The first upgrade from an old metald still refuses connections for a short time, because the old process did not store its sockets. Later upgrades do not.

Why not tableflip

tableflip runs the old and new processes at the same time and passes the listeners from one to the other. metald owns resources that only one process can own at a time: PTY readers, VM units through D-Bus, BPF attachments, reconcilers and migration records. The old process must release all of them before the new one starts. So the overlap gives nothing that the descriptor store does not already give. tableflip would also add a dependency. The descriptor store is already in use.

8. BPF maps

A BPF map is kernel memory that a BPF program reads and writes. A map is "pinned" when a file under /sys/fs/bpf keeps it alive after the process that made it exits. Two components use BPF, and they follow different rules.

metald traffic monitor (not pinned)

  • track_traffic.o counts packets on each VM TAP device. Its maps and links belong to the metald process.
  • When metald exits, the kernel removes the links and the maps. The new process loads new maps and attaches them in its first reconcile pass.
  • The counters start again at 0. The idle baseline is the time of attachment, which is the current contract.
  • While metald is down, no packet events arrive. A sleeping VM wakes on the next client retry after the restart.
  • No state goes from one version to the next, so no compatibility rule is needed. This stays as it is.

wg-mesh datapath (pinned)

The mesh programs stay attached when no process runs. So packets continue to flow during a metald restart. An upgrade replaces the programs in this sequence (this logic already exists in services/wg-mesh/cli):

  1. The new atlas-wg-mesh opens each pinned map that has a name in its object file. It checks the type, key size, value size, maximum entries and flags with MapSpec.Compatible.
  2. It reuses the compatible maps, creates the new maps, and pins its programs under releases/<build hash>.
  3. It fills new maps from the VM interfaces on the host.
  4. tc filter replace swaps each hook atomically. If a step fails, the hooks go back to the old release.
  5. It writes build_hash, and removes the old release and the maps that no program uses.

If a map layout changed, step 1 fails with "reset is required". EnsureHost fails, so metald does not start. The script restores both old binaries. The old programs stay attached the whole time, so packets do not stop. The rollout pauses at the canary.

Rules

  • Do not change the type, key, value or maximum entries of an existing pinned map. Add a map with a new name. Old programs ignore it.
  • The content of each pinned map must be possible to rebuild from metald sync (peers, VMs and host config). A downgrade removes maps that the old object does not know.
  • New CI job: build the BPF object at the merge base and at the pull request head. Then compare all maps that have the same name with Compatible. A layout change fails the pull request and names the map. No .o file goes into Git.

10. Failure cases

CaseBehavior
The rollout job runs twiceIts job ID prevents a second copy. A Pending row becomes Upgrading only under the record lock.
A worker is killed during a host jobThe script on the host finishes or rolls back by itself. The row becomes stale, then Failed, and the update pauses.
Atlas is down during a rolloutHost scripts finish. The rollout job continues on the next tick, and the health gate uses the sync time.
A bad binary passes the canary and crashes laterSelf-rollback inside 30 minutes. Sync shows the old version, so the gate fails and the update pauses.
The metald restart stops VMsThe VM count check fails on the canary, and the rollout stops.
BPF map layout changedmetald does not start. The script rolls back, and the datapath has no gap. CI catches this before merge.
200 hostsThe batch size limits how many hosts upgrade at once. Each host job is one SSH job on the long queue.
Who writes whatThe rollout job owns the update status, the batch fields, and the change from Pending to Upgrading. A host job owns its row result. Desk actions change the status under the record lock. The rollout job reads the status again under that lock before each change.
Operator viewThe status, current batch, wait end time, row status, SSH Task and failure message, without SQL.

11. Verification

  • Go: tests for listener reuse (matched by name and address) and for the readiness status. Run go test -race on the changed packages.
  • wg-mesh CI check: a change to a map layout must make the check fail.
  • Atlas, on test.local: tests for batch assignment, the health gate, stale rows, and pause and resume, with real doctypes.
  • Live, on atlas.localhost with the waw Scaleway development hosts:
    1. Canary of 1 host. During the upgrade, a loop calls GET /v1/vms every 100 ms. Expect 0 connection errors, all VMs still running, and consoles that open after the restart.
    2. A bad build that exits after 30 seconds. Expect the self-rollback to restore the previous binaries and the update to pause.
    3. A full rollout over all development hosts, with a batch size of 1 and a wait of 2 minutes.
    4. A ping between VMs on two hosts during the wg-mesh upgrade. Expect no packet loss.

12. Commits

  1. build(metal): Default the build version to a development timestamp: the Makefiles, --version, and the Atlas Settings version fields.
  2. feat(metal): Report the metald and wg-mesh versions in host sync: the sync response, and the Metal Server fields and list column.
  3. feat(metal): Keep the listening sockets across a metald restart: listeners in the descriptor store, and the readiness status.
  4. feat(atlas): Check readiness and roll back a failed metald upgrade: the script, the rollback drop-in, and the wg-mesh install.
  5. feat(atlas): Add the Metald Update rollout: the Operations module, the doctypes, the rollout job, and the list action.
  6. build(wg-mesh): Check BPF map compatibility in CI
  7. docs(atlas): Document the metald rollout: the operator runbook and the SPEC.md updates.

13. Decisions needed

  1. Is the doctype structure and form layout above good?
  2. Are the defaults good: a canary of 1, a batch size of 5, and a wait of 10 minutes?
  3. Does wg-mesh ship in the same Metald Update as metald? I recommend yes.
  4. Is a self-rollback window of 30 minutes good?
  5. Do we replace the bulk "Upgrade Metald" list action with "Create Metald Update"? I recommend yes, so there is only one way to roll out to the fleet.
