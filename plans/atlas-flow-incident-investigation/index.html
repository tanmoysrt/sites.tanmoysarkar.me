Atlas incident investigation with Flow

A plan to run the Flow agent harness inside Atlas. Atlas gives the agent a set of deterministic, scrubbed tools. Central hands off an issue to Atlas and gets back a summary. Central never connects to a host.

Status page. Started 28 October 2026. The progress table in section 9 is the live tracker.

1. Problem

Atlas is the regional control plane. It already has dashboards and alerts in Insights. The data comes from Datum, which stores metrics and logs in ClickHouse. When an alert fires, an operator reads the charts, then connects to hosts over SSH to find the cause. This takes time, and the steps are similar each time.

Flow is the agent harness in the Frappe framework. It can run a model in a loop with tools, skills and a knowledge base. We want Flow to do the first part of an investigation.

There are three constraints:

  • Small exposure to Central. Central has only an API contract with Atlas. Central must not connect to a host over SSH. Central gets only the result of an investigation.
  • No secrets to the model. All command output and log text goes through a deterministic scrubber before the agent reads it.
  • A person approves changes. The agent asks before any action that changes state. Termination is never available to the agent.

2. Design: where the agent runs

We considered two options.

OptionHow it worksResult
A. Agent in Central, Atlas exposes raw read APIsCentral's agent calls many Atlas routes and reads raw output.Rejected. Central sees raw host data. Each new tool needs a new public route.
B. Agent in Atlas, Central hands off an issueEach region runs its own investigator. Central sends an issue and reads back a scrubbed summary.Chosen. Raw data stays in the region. The contract is two or three routes.

In option B, the Central agent uses the Atlas investigator like a subagent: it gives a task and gets a report back.

3. What Flow gives us today

Flow is in frappe/flow. A daemon (flow_harness) runs the agent loop for the bench. Frappe holds the configuration, the transcript and the HTTP API. We checked these facts in the code:

  • Models. Flow uses LiteLLM. A Flow Provider with provider=openrouter and a Flow Model with model_id=deepseek/deepseek-v4.1-flash-1017 or z-ai/glm-5.3-flash is enough. Both model IDs exist on OpenRouter.
  • Tools. An app declares flow_tools in hooks.py. Each tool is a function with the @tool decorator and a keyword argument ctx: ToolContext. The schema comes from type hints. A tool can set requires_confirmation=True. This value is a plain boolean, not a function of the arguments.
  • Agents. An app declares flow_agents. The function returns Agent objects with instructions, tools, skills and knowledge bases.
  • Skills. Flow loads <app>/skills/<name>/SKILL.md from the app repository root.
  • Knowledge base. Flow Knowledge Base with text, file, URL or DocType sources. Search is hybrid (full text and vector). It needs an embedding model.
  • Approval. A gated call pauses the Flow Run. The owner answers with frappe.flow.api.resume: Approve, Deny or free text.

Gaps that affect this plan:

  • Approval decisions are not recorded. Gated tools run as the engineer, so the existing console logs and action records name the person who approved.
  • Sessions from triggers always auto-approve. We will not use triggers for investigations.
  • The REST API has no completion callback. We start runs from Python with on_complete, so Atlas knows when a run ends.
  • A session keeps the tool set from its start. Tool changes apply only to new sessions.

4. The tool set

Each tool is small and deterministic. The agent cannot send free SQL to the database or free shell to a host without a gate. Tools live in a new Atlas module, atlas/investigation/, grouped by subject. Every tool returns scrubbed text or JSON.

5. Permission policy

Flow sets approval per tool, not per argument. So we split the tools by risk, and we use two agents with different tool sets. The model cannot change the policy, because it is fixed by which tools an agent has.

  • Atlas Investigator. Central starts it. It has read-only tools only. It never pauses for approval, because no tool in it needs approval.
  • Atlas Engineer Assistant. An Atlas engineer starts it in the Atlas desk. It has the read-only tools and the gated tools. The engineer approves each gated call in the chat.
ActionCentral investigationEngineer in Atlas
Read inventory, telemetry, logs, docsAllowedAllowed
Read-only command on a host or tenant-0 VM (allow list)Allowed, loggedAllowed, logged
Other command on a host or tenant-0 VMNot availableEngineer approves
Any SSH to a VM of a customer tenantNot availableEngineer approves
Change actions (restart, stop, migrate, reboot, resize, firewall, upgrade)Not availableEngineer approves
terminate, archive_server, delete of any recordNot availableNot available

The read-only allow list is a parser, not a prompt. It splits the command on ;, &&, || and |. It refuses redirection, command substitution and backticks. Each part must start with an allowed program, for example journalctl, systemctl status, cat, tail, head, grep, ls, df, free, ss, ip, wg show, ps, top -b -n 1, uptime, dmesg. Reads of secret paths, such as /etc/shadow and private keys, are refused.

Central investigations run as a dedicated Atlas user with an Atlas Investigator role. Each read-only tool checks this role. Gated tools also require System Manager, so the investigator user cannot use them even if a session gets them by mistake. Engineer sessions run as the engineer, so the existing console logs and action records name the person who approved.

6. Scrubbing output

A scrubber is a function that replaces sensitive text with a fixed marker. It is deterministic: the same input always gives the same output, and no model is involved. It lives in one place, atlas/core/scrub.py, and every tool calls it on its return value.

It masks credentials only. IP addresses, host names, emails and record names stay, because they are needed to investigate. It replaces, in order:

  1. PEM blocks (private keys, certificates).
  2. Known token formats: JWT, Bearer values, cloud access keys, sk- API keys, GitHub tokens, WireGuard keys.
  3. Values of secret-like keys in key=value, key: value and JSON, for example password, secret, token, api_key.
  4. Credentials in URLs (user info and signed query strings).
  5. High-entropy words. A word of 20 or more characters from a base64 or hex alphabet, with Shannon entropy above a limit, becomes [REDACTED:entropy]. UUIDs and Atlas record names are kept, because the agent needs them.
password=hunter2 token: eyJhbGciOi...   →   password=[REDACTED] token: [REDACTED:jwt]

The Metal Server Console gets a Scrub Output check, on by default. With the check on, the stored output is scrubbed. An operator can turn it off for one run. Agent tools always scrub and cannot turn it off.

A second layer is possible: Flow's daemon has an extension point for a tool_call hook, with a redact_secrets example. We do not need it at first.

7. Central to Atlas handoff

A new DocType Atlas Investigation owns the state of one handoff. Fields: issue, context JSON, requested by, status (Queued, Running, Completed, Failed), Flow Session and summary. The run uses the read-only agent, so it never waits for approval.

Route (under /api/atlas)CallerDoes
POST /investigationsCentral, tenant 0 onlyCreates the record and starts a Flow run. Returns the ID.
GET /investigations/{id}CentralStatus, summary and the full transcript: each tool call, its arguments and its scrubbed result.

Atlas sends a webhook event on each status change, through the webhook that Central already configures. Central can also poll. Authentication uses the existing Central JWT and require_central_identity. No new token type is needed.

Central gets two Flow tools: start_region_investigation and get_region_investigation. Central gets the whole investigation, with credentials masked. If the cause needs a change, the summary says so. An Atlas engineer then does the change in the Atlas desk.

Knowledge and skill

An incident-investigation skill in atlas/skills/ gives the method: read the failing alert checks, run the saved queries, find the affected resources, read logs, form a hypothesis, check it, then report. It lists the tools to prefer at each step. A short report template sets the output: symptom, evidence, cause, confidence, and suggested next step.

The Atlas knowledge base uses openai/text-embedding-3-small through OpenRouter (0.02 USD per million tokens). It takes the Atlas docs/ folder, the module SPEC.md files and the incident postmortems. A second source takes Frappe Cloud platform docs. A setup command loads them, so a new region gets the same base.

10. Decisions

  1. Who can change things. Only an Atlas engineer, in an Atlas desk session, and only after approving the call. Central investigations never get gated tools.
  2. What Central receives. The whole investigation: summary and full transcript, with credentials masked.
  3. What the scrubber masks. Credentials only. IP addresses and host names stay.
  4. Read-only commands. Allowed without approval in both agents, through the allow-list parser.
  5. Embedding model. openai/text-embedding-3-small through OpenRouter.
  6. Telemetry access. A read-only ClickHouse user on Datum for query_telemetry.
  7. Log access. SSH from Atlas for data not in Datum. A metald log route can come later if needed.
