mica metadata redesign

A plan to make the S3 metadata of mica simple, and to make garbage collection cost follow the changes, not the bucket size.

Plan, not built. 2026-11-07.

1. The situation

mica keeps each disk in S3. A disk is a list of chunks, 256 KiB each by default. The metadata tells mica which chunk object holds which part of the disk.

Today the metadata has these objects:

  • chunks/<hash>: chunk data. The key is the SHA-256 of the data. All disks share one namespace, so equal chunks are one object.
  • pages/<hash>: 1,024 chunk hashes. One page covers 256 MiB of disk.
  • manifests/<hash>: the root. It lists the page hashes of one disk version, and points to its parent root.
  • disks/<id>/head: the current root. mica overwrites it at each commit.
  • disks/<id>/attached: the node that owns the disk now.
  • gc/lock and gc/last: what a checkpoint knows about garbage collection (GC).

Nothing in S3 tells which disk owns an object. So only a global GC can decide that an object is garbage. This causes two problems.

Problem 1: GC cost grows with the bucket

One GC run does these steps (src/gc.rs):

  1. Read the head of each disk, one disk at a time. Follow up to 5 parent roots for each disk.
  2. Read each live page once, and put each live chunk hash in a set in memory.
  3. List every object in chunks/, pages/ and manifests/.
  4. Delete each object that is not live and is older than 24 hours.

An estimate for 10,000 disks, with 2 GiB of written data each and 20 ms for each request:

StepWorkTime or space
Heads and roots, in sequenceabout 110,000 small requestsabout 35 minutes
Live pages, 16 in parallelabout 1 million GETsabout 20 minutes
List all chunksabout 80 million keys, 80,000 LIST requestskeys in memory
Live chunk setabout 80 million hashesseveral GB of RAM

These numbers are estimates from the code, not measurements.

A long GC also slows every disk. While a GC runs, each checkpoint waits for it (up to 10 minutes), or reads back every object that it uploaded.

Problem 2: the safety rules are hard to keep correct

Chunk keys are content hashes. So a checkpoint can upload an object that has the same key as old garbage. GC can read the old age of that object, and then delete the new upload. mica has many parts only to prevent this race:

  • the 24-hour grace period
  • gc/lock and gc/last, read about 6 times in each checkpoint
  • the repair step, which reads back each new object after a GC
  • held copies of staged chunks, and the hold file
  • the rule that a checkpoint uploads a chunk again, also when S3 can have it

Ownership has a second gap. The head has no compare-and-swap. A node checks the attached marker, and then writes the head. After a forced takeover, the old node can still write the head one time.

2. Goals

  • The cost of GC follows the data that changed. It does not follow the number of disks or objects.
  • No global scan. No global lock. No grace period for correct operation.
  • One commit is one atomic step that also checks ownership.
  • Snapshots and clones stay free: they copy no data.
  • S3 stays the only store. No database.

3. The design

The design has four rules. Each rule removes a part of the current protocol.

Rule 1: each object has one owner disk and is never written again

Each checkpoint writes its objects into a new set. A set is a folder with a new random ID:

d/<disk>/s/<seq>-<random>/c/<chunk index>     chunk data, compressed
d/<disk>/s/<seq>-<random>/p/<page index>      page
d/<disk>/s/<seq>-<random>/t/<n>               tree node above the pages
d/<disk>/s/<seq>-<random>/root               root of this version

A page entry holds the location of a chunk and its SHA-256:

entry = owner (index into the owner table of the root)
        set   (seq + random)
        hash  (SHA-256 of the plain chunk, for checks and for "unchanged" skips)

A key is never used two times. So an upload can never get the key of garbage, and the race of problem 2 cannot occur. The grace period, gc/lock, gc/last, the repair step and held copies all go away.

A chunk that the guest writes again with the same data keeps its old entry, as today. Clones still share the chunks of their snapshot, because their pages point to the same keys.

The cost: two disks that write the same data separately store it two times. Today they share one object.

Rule 2: the head is the lock

The head holds the owner. mica changes the head only with If-Match: <etag>, a compare-and-swap in S3.

{
  "root": "d/disk-1/s/000000000000002a-9f3c11/root",
  "seq": 42,
  "owner": { "node_id": "...", "claim": "...", "since": "..." },
  "size": 21474836480,
  "limits": { ... },
  "profile": [ ... ]
}
  • Attach: GET the head, then PUT it with our owner and If-Match. If the PUT fails, another node changed the head first.
  • Commit: PUT the new head with If-Match. The PUT fails after a takeover. Then the old node stops, and it cannot write the head again.
  • Detach: PUT the head without an owner, with If-Match.

The attached object goes away, and also the second claim path for stores without conditional writes. The owner still reads the head once a minute, so an idle disk also sees a takeover.

Only the owner of a disk deletes the objects of that disk. All GC work for one disk runs on one node, so it has no races with other nodes.

Rule 3: free an object when its neighbors do not have it

A disk has a list of retained roots, ordered by seq:

  • the last 5 checkpoints (gc_keep_checkpoints)
  • the root of each snapshot of the disk

An object of the disk is in a continuous range of versions. It appears in the version that wrote it. It stays in each later version until the guest writes that chunk again. It never comes back, because of rule 1. So when mica drops one retained root, it must keep an object only if a neighbor root has it.

Drop rule. To drop retained root X, find the retained roots just before X (P) and just after X (N). Delete each object of this disk that X has and that P and N do not have. Then delete X.

Why the rule is correct: an object lives in one continuous range. If any other retained root has the object, then the neighbor on that side has it too. So the two neighbors are enough.

The work for each drop is a diff of three roots. Equal page keys mean equal pages, so mica reads only the pages that changed. The owner has these roots and pages in its local page store already. A drop needs no S3 reads. It sends one DeleteObjects request for each 1,000 deleted keys.

The owner drops the oldest checkpoint root after each commit, in the background. If the node crashes during a drop, the next owner does the drop again. Deletes can run two times without harm. The root is deleted last, so an unfinished drop is easy to find.

Rule 4: clones keep their snapshot

A clone is a disk that starts from a snapshot of another disk. Its pages point to objects of the other disk. A clone never deletes objects of another owner.

  • Clone: PUT d/<D>/clones/<S>/<C>. Then read the snapshot record. If the snapshot is marked as deleted, delete the marker and fail.
  • Delete a snapshot: mark its record as deleted. Then list its clone markers. If there are none, drop its root with the drop rule. If there are clones, the snapshot is hidden, and its root stays retained.
  • Delete a clone: delete its objects, then its clone marker. If its snapshot is marked as deleted and has no more markers, the snapshot drops.

Each side writes first and reads second. So a clone and a snapshot delete at the same time always see each other. S3 has strong read-after-write consistency, so this needs no compare-and-swap.

A disk with snapshots that the user deletes stays as a marked head. It keeps only its snapshot roots, until the last snapshot is gone. This is how a clone of a clone keeps its data: each level keeps the level below it.

Unfinished checkpoints

A checkpoint can upload objects and then fail before its commit. Before its first upload, the checkpoint writes d/<disk>/open/<set>. After the commit result is known, it deletes this marker. An open marker that is left over belongs to a set that never committed, if the head does not point into it. The owner deletes such sets at attach and once an hour. This also deletes the uploads of an old owner that continued after a takeover.

Work that the owner cannot do now

Some work belongs to a disk that another node has, or that no node has. Examples: a snapshot of a detached disk loses its last clone, or a user deletes a detached disk. The node that starts the work writes gc/pending/<disk>.

  • The owner of an attached disk does its pending work at attach, at detach and once an hour.
  • mica gc lists gc/pending/ only. For each detached disk, it takes the head with If-Match, does the work and gives the head back.

mica gc then costs one LIST plus the work that is pending. It does not read the other 10,000 disks.

A third tree level

Today the root lists every page. A root of a 1 TiB disk is about 128 KiB, and mica writes a new root at each checkpoint. The new format puts tree nodes of 1,024 entries between the root and the pages. A 1 TiB disk then has a root with 4 entries. A checkpoint writes the pages that changed, one tree node for each 256 GiB that changed, and a small root. The drop rule works on this tree in the same way: equal node keys mean equal subtrees.

5. Options that this plan does not use

OptionWhy not
A database (etcd, Postgres, FoundationDB) for heads and referencesIt gives compare-and-swap, but it is one more service to run and back up. S3 with If-Match gives the same compare-and-swap.
SQLite or redb for each disk, on the nodeThe local dirty log and the recent bitmap are fast because a write sets one bit in memory. An append for each new chunk cut parallel writes from 1,651 to 421 MiB/s before. A database commit for each flush is not faster.
An LSM on object storage, such as SlateDBIt solves the problem, but it adds its own manifest, compaction and GC.
A reference count for each object in S3Each count change needs a compare-and-swap on a shared object. A clone of a large disk changes millions of counts.
Content-hash keys inside each disk folderEqual chunks at two places in one disk share one key. Then an old key can come back, and the race of problem 2 returns inside the disk.
Keep the global GC, but make it fasterParallel head reads help step 1. The full listing and the live set in memory stay, and checkpoints still depend on GC.

6. Limits and open questions

  • Stores must support If-Match on PUT. AWS S3 supports it. Cloudflare R2 and MinIO also support it. I did not check RustFS and Hetzner Object Storage yet. Garage does not support conditional writes, so mica drops Garage.
  • No deduplication between unrelated disks. The cost is not known. Step 0 measures it on a real bucket.
  • A deleted snapshot with live clones keeps its data. The user does not see it, but S3 stores it until the last clone is deleted. mica snapshot ls can show this space.
  • Page entries grow from 32 to about 46 bytes. zstd removes most of the repeated owner and set fields. The size after compression needs a measurement.
  • New format. mica keeps no compatibility with older data. Disks are created again.

7. Steps

  1. Probe (about 10 minutes). Test PUT with If-Match and DeleteObjects on RustFS and Hetzner. Count the chunk hashes that two unrelated disks share in a real bucket. If If-Match is missing, stop and change this plan.
  2. Head as the lock. Owner in the head, If-Match on attach, commit and detach. Remove the attached marker. Run the takeover and crash tests.
  3. New keys. Sets, page entries with owner and set, the tree level, open markers. Remove gc/lock, gc/last, the repair step and held copies.
  4. Drop rule for checkpoints. The owner drops the oldest root after each commit.
  5. Snapshots, clones and deletes. Clone markers, deleted marks, gc/pending/, the new mica gc. Remove the global GC.

How to check the result

  • Model test. Run random writes, checkpoints, snapshots, clones and deletes against a memory store. After each step, check two facts: no root that is still reachable points to a deleted object, and no object stays that no reachable root needs.
  • Crash tests. The current power-cut and daemon-kill tests on btrfs, XFS and ext4. Add kills during a drop and during a clone delete.
  • Takeover test. Force a takeover while the old node uploads. The old node must fail its commit. Its leftover set must be gone after the next cleanup.
  • Scale test. 10,000 small disks in the lab RustFS, with a few writes on each. Measure mica gc time and memory, and the drop time after each commit. Compare with the current GC on the same bucket.
  • Checkpoint cost. The soak test on a 1 TiB disk. Measure the requests and the metadata bytes for each checkpoint, before and after.
