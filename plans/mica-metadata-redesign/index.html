mica metadata redesign

A plan to make the S3 metadata of mica simple and fast. Each disk owns all of its objects. Only the snapshots of one disk share blocks, as in ZFS.

Plan, not built. Second version, 2026-11-07.

1. The situation

mica keeps each disk in S3. A disk is a list of chunks, 256 KiB each by default. The metadata tells mica which object holds which chunk.

Today all disks share one namespace of chunks. The key of a chunk is the SHA-256 of its data, so equal chunks are one object. A clone of a snapshot uses the chunks of the snapshot. Nothing in S3 tells which disk owns an object. So only a global garbage collection (GC) can find garbage.

This causes two problems:

  • GC cost grows with the bucket. One GC run reads the head of each disk, one disk at a time. It reads each live page, keeps each live chunk hash in memory, and lists every object in the bucket. For 10,000 disks with 2 GiB of data each, the estimate is about 1 hour, 80 million keys to list, and several GB of RAM. These numbers are estimates from src/gc.rs, not measurements.
  • The safety rules are hard to keep correct. A checkpoint can upload an object with the key of old garbage. GC can then delete the new upload. To prevent this, mica has a 24-hour grace period, gc/lock and gc/last, a repair step, held copies of chunks, and the hold file. A running GC also slows every checkpoint on every node.

The head also has no compare-and-swap. After a forced takeover, the old node can write the head one more time.

2. The model

The new model has one idea: a disk never shares an object with another disk.

  • Each object of a disk is under d/<disk>/. Only this disk uses it.
  • The snapshots of a disk share objects with the disk and with each other. This is the only sharing.
  • Only the node that owns the disk deletes its objects.
  • mica deletes an object at the moment it becomes garbage. There is no GC run.

The model has these features:

FeatureHow
CheckpointA commit of a new version. It is not kept as a restore point.
SnapshotA named version of one disk. It shares objects with the disk.
Snapshot deleteFrees the objects that only this snapshot uses. The other objects stay with their neighbors.
RollbackA new commit with the content of a snapshot.
New disk from a snapshotA full copy inside S3 (CopyObject). The new disk owns its copies.

3. Keys

A transaction is one try to commit a new version. Each transaction has a number, the txg. The txg grows by one at each try, also after a failed try. Each transaction writes its objects into its own folder:

d/<disk>/head                               current version and owner
d/<disk>/snap/<name>                        a snapshot: its root key and txg
d/<disk>/t/<txg>-<epoch>/c/<chunk index>      chunk data, compressed
d/<disk>/t/<txg>-<epoch>/p/<page index>       page: 1,024 chunk entries
d/<disk>/t/<txg>-<epoch>/n/<node index>       tree node: 1,024 page entries
d/<disk>/t/<txg>-<epoch>/root                root of this version

The epoch grows by one at each claim of the disk. Two owners can never write the same key.

An entry in a page or a tree node holds the txg and epoch of its object and its SHA-256. The txg is the birth of the object. mica never writes a key two times. If the guest writes the same data again, the old entry stays.

A tree node sits between the root and the pages. A 1 TiB disk then has a root of 4 entries. Today the root of a 1 TiB disk is about 128 KiB, and each checkpoint writes it again.

4. The head is the lock

mica changes the head only with If-Match: <etag>. This is a compare-and-swap in S3. The head holds the owner and the transaction that is in progress:

{
  "root": "t/42-3/root",
  "txg": 42,
  "epoch": 3,
  "owner": { "node_id": "...", "since": "..." },
  "open": 43,
  "last_snapshot_txg": 30,
  "size": 21474836480,
  "limits": { ... },
  "profile": [ ... ]
}
  • Attach: GET the head. PUT it with our owner, epoch + 1 and If-Match.
  • Open: before the first upload, PUT the head with open set to the new txg.
  • Commit: PUT the head with the new root, open cleared, and If-Match.
  • Detach: PUT the head without an owner.

After a takeover, the old node fails its next PUT of the head. It cannot start a new transaction, and it cannot commit. The attached object, the claim without conditional writes, and the marker read before each commit all go away.

If a transaction fails, open tells which folder holds its uploads. The owner deletes that folder at the next open or at attach. An old owner that still uploads after a takeover writes only into its own epoch, which the new owner deletes.

5. Commit and the free rule

A checkpoint uploads changed chunks, pages, tree nodes and a root. Then it commits the head. It knows the old entry of each changed chunk, page and tree node. These old objects are now replaced.

Free rule. After a commit, delete each replaced object that was born after the last snapshot. Keep each replaced object that was born before it, because that snapshot uses it.

ZFS uses the same rule for its blocks. The rule needs only the birth txg of the replaced entries, which the checkpoint has in memory. It needs no S3 reads. mica sends the deletes in batches of up to 1,000 keys with DeleteObjects, after the commit, in the background.

The old root is replaced too. mica deletes it last. Each root names its parent root. If the node crashes before the deletes end, the parent of the head is still there at the next attach. The new owner compares the old root with the head and does the deletes again. Deletes can run two times without harm.

6. Snapshots

Create

The owner commits a checkpoint, then writes d/<disk>/snap/<name> with the root key and txg. Then it sets last_snapshot_txg in the head. For a detached disk, the node claims the disk first.

Delete

The snapshots and the head form one list, ordered by txg. To delete snapshot S, find its neighbors: the snapshot before it (P) and the next snapshot or the head (N).

Merge rule. Delete each object of S that P and N do not have. Then delete the record of S.

If S was the last snapshot, the head gets the txg of P as last_snapshot_txg. The record of S goes last, so a crash leaves a delete that can run again.

This is correct because an object lives in one continuous range of versions. It appears in the version that wrote it, and it stays until the guest writes that chunk again. It never comes back. So if any other snapshot has the object, the neighbor on that side has it too.

Equal keys of pages and tree nodes mean equal content. So the diff reads only the parts of the tree that changed between P, S and N. Only the owner does this, so no other node changes the list at the same time.

Rollback

A rollback commits a new root that has the entries of the snapshot. The free rule then handles the objects of the old head. A rollback does not delete later snapshots.

New disk from a snapshot

mica copies each object of the snapshot into the new disk with CopyObject. The data does not go through the node. Zero chunks are not stored, so they are not copied. The local cache of the snapshot can also be copied on the same node, so the new disk starts warm there.

An estimate for 2 GiB of written data at 256 KiB chunks: about 8,200 copies. With 64 copies at a time and 20 ms each, this is about 3 seconds. The time grows with the data in the snapshot, not with the disk size.

7. Delete a disk

  1. Claim the head with If-Match and mark it as deleted.
  2. List d/<disk>/ and delete everything with DeleteObjects.
  3. Delete the head last.

If the node crashes, the marked head stays. mica disk ls shows the disk as "deleting", and the same command finishes the work. The snapshots of a disk go with it.

9. Options that this plan does not use

OptionWhy not
Clones that share chunks with their snapshot (the first version of this plan)It needs clone markers, a list of pending work, and owner tables in each root. A copy in S3 is slower to create, but the rest of the design becomes much simpler.
Keep the last 5 checkpoints as restore pointsEach kept version needs the merge rule at each commit, and it reads pages. Without them, a commit frees its garbage from memory. A timed snapshot can give the same restore points later, with the same code.
Dead lists for each snapshot, as in ZFSZFS keeps a list of the blocks that each snapshot holds, so a delete needs no diff. In S3 these lists are more objects to keep correct. The diff of P, S and N reads only the changed parts of the tree.
A database (etcd, Postgres) or SQLite for each diskS3 with If-Match gives the compare-and-swap that mica needs. A database is one more service, or slower local commits.

10. Limits and open questions

  • Stores must support If-Match on PUT. AWS S3, Cloudflare R2 and MinIO support it. RustFS and Hetzner Object Storage are not checked yet. Garage does not support it, so mica drops Garage.
  • Many disks from one image cost a copy each. A fleet of 1,000 sandboxes from a 2 GiB image stores 2 TB, not 2 GiB. If this matters, sharing comes back as a separate feature later.
  • No restore point without a snapshot. A bad write in the guest is lost after the next commit, unless a snapshot exists.
  • Page entries grow from 32 to about 44 bytes. zstd removes most of the repeated txg fields. The size after compression needs a measurement.
  • New format. mica keeps no compatibility with older data. Disks are created again.

11. Steps

  1. Probe (about 10 minutes). Test PUT with If-Match, DeleteObjects and CopyObject on RustFS and Hetzner. If If-Match is missing, stop and change this plan.
  2. Head as the lock. Owner, epoch and open in the head, If-Match on each change. Remove the attached marker.
  3. New keys and the free rule. Transaction folders, entries with birth, the tree level, deletes after commit. Remove GC, the repair step and held copies.
  4. Snapshots. Create, the merge rule, rollback, and new disk by copy.
  5. Delete a disk by folder.

How to check the result

  • Model test. Run random writes, commits, failed transactions, snapshots, snapshot deletes and rollbacks against a memory store. After each step, check two facts. No reachable root points to a missing object. No object stays that no reachable root needs.
  • Crash tests. The current power-cut and daemon-kill tests on btrfs, XFS and ext4. Add kills during the deletes after a commit and during a snapshot delete.
  • Takeover test. Force a takeover while the old node uploads. The old node must fail its next head PUT. Its uploads must be gone after the next open of the new owner.
  • Cost test. The soak test on a 1 TiB disk: requests and metadata bytes for each checkpoint, and bytes in S3 after one hour, before and after.
  • Copy test. Time a new disk from a 2 GiB snapshot on RustFS and Hetzner.
