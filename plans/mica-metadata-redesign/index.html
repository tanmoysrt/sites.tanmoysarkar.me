mica metadata redesign

A plan for simple and fast S3 metadata in mica. Each disk owns its objects. The node that has the disk attached cleans up after itself. There is no GC.

Plan, not built. Third version, 2026-11-07.

1. The situation

mica keeps each disk in S3. A disk is a list of chunks, 256 KiB each by default. Today all disks share one namespace of chunks. The key of a chunk is the SHA-256 of its data, so equal chunks are one object, also across disks.

Nothing in S3 tells which disk owns an object. So only a global garbage collection (GC) can find garbage. This causes two problems:

  • GC cost grows with the bucket. One GC run reads every disk and lists every object. For 10,000 disks with 2 GiB of data each, the estimate is about 1 hour and several GB of RAM. This is an estimate from src/gc.rs, not a measurement.
  • The safety rules are hard to keep correct. A checkpoint can upload an object with the key of old garbage, and GC can then delete it. To prevent this, mica has a 24-hour grace period, gc/lock, gc/last, a repair step, held copies and the hold file. A running GC also slows the checkpoints of every disk.

2. The decisions

  • No sharing between disks. Equal data in two disks is two objects. The customer pays for the space that each disk uses.
  • The snapshots of one disk share objects with the disk. A snapshot delete frees what only that snapshot uses, as in ZFS.
  • No GC. The node that has the disk attached (the owner) deletes the garbage of that disk, and only of that disk. No command ever reads all disks.
  • Fast transfers. A checkpoint sends one small request besides its data. A read never downloads a chunk that a cache on the node has.

3. Objects in S3

d/<disk>/head                        current version, owner, next txg
d/<disk>/snap/<name>                 snapshot: txg of its version
d/<disk>/<txg>/c/<chunk index>        chunk data, compressed
d/<disk>/<txg>/p/<page index>         page: 1,024 chunk entries
d/<disk>/<txg>/root                  root: one entry for each page

A transaction is one commit of a new version of the disk. Each transaction has a number, the txg, and writes its objects into its own folder. mica never writes a key two times.

An entry in a page or a root has two fields:

txg    the folder of the object: its birth
hash   SHA-256 of the plain data: for checks and for cache lookups

A zero entry means a zero chunk or a zero page. Zero chunks are not stored.

4. The head is the lock

mica changes the head only with If-Match: <etag>. This is a compare-and-swap in S3. If another node changed the head, the PUT fails.

{
  "txg": 42,
  "next": 43,
  "owner": { "node_id": "...", "since": "..." },
  "lost": [],
  "size": 21474836480,
  "limits": { ... },
  "profile": [ ... ]
}
  • txg is the committed version. Its root is d/<disk>/42/root.
  • next is the folder of the next transaction. Each commit sets it. So a checkpoint needs only one PUT of the head.
  • lost lists folders of transactions that never committed. The owner deletes them.

Attach

  1. GET the head.
  2. If next has a folder, it holds uploads that never committed. Add it to lost.
  3. PUT the head with our owner, next set to the next unused txg, and If-Match.
  4. Delete each folder in lost, then clear lost at the next commit.

After a forced takeover, the old node can still upload into its next folder for a short time. Its commit fails, because the head changed. The new owner deletes that folder at attach. It deletes the folder again at its detach, to catch uploads that arrived late.

Checkpoint

  1. Upload each changed chunk into d/<disk>/<next>/c/. Skip a chunk whose hash equals its current entry.
  2. Upload each changed page, then the root.
  3. PUT the head with txg = next, a new next, and If-Match.
  4. Delete the garbage with the free rule, in the background.

If the PUT of the head fails with a network error, GET the head to learn the result. If another node has the head, stop. Do not delete anything. If the commit did not happen, delete the keys that this try uploaded, then try again. The owner knows these keys, because it uploaded them.

5. The free rule

A commit replaces the old entry of each changed chunk and page. It also replaces the old root. The checkpoint has these old entries in memory.

Free rule. After a commit, delete each replaced object that was born after the newest snapshot. Keep each replaced object that was born before it, because that snapshot uses it.

ZFS uses the same rule for its blocks. The rule needs no S3 reads. mica deletes up to 1,000 keys in one DeleteObjects request.

If the node crashes before the deletes end, the old root is still in S3, because mica deletes it last. At the next attach, the owner compares the old root with the head and does the deletes again. A delete can run two times without harm.

6. Snapshots

Create

The owner commits a checkpoint. Then it writes d/<disk>/snap/<name> with that txg. The owner keeps the list of snapshots in memory. It reads the list with one LIST at attach. A detached disk is claimed first, and given back after.

Delete

The snapshots and the head form one list, ordered by txg. To delete snapshot S, find the snapshot before it (P) and the next snapshot or the head (N).

Merge rule. Delete each object of S that P and N do not have. Then delete the record of S.

This is correct because an object lives in one continuous range of versions. It stays until the guest writes that chunk again, and it never comes back. So if another snapshot has the object, the neighbor on that side has it too.

The record of S goes last. A crash leaves a delete that can run again. Equal page entries mean equal pages, so the diff reads only the pages that changed between P, S and N.

Rollback

A rollback to snapshot S first deletes each snapshot newer than S, with the merge rule. ZFS does the same. Then it commits a new root with the entries of S. The free rule deletes what only the old head used.

The newer snapshots must go. If they stayed, an object of S could be in S and in the head, but not in the snapshots between them. Then a later merge could delete an object that the head still uses.

New disk from a snapshot

mica copies each object of the snapshot into the new disk with CopyObject. The data stays inside S3. An estimate for 2 GiB of written data: about 8,200 copies, about 3 seconds with 64 copies at a time.

7. Fast reads: check the node first

Each entry has the hash of its chunk. Before a download, mica looks for the hash in the cache indexes of all disks on the node. These indexes are in memory already. If another cache has the chunk, mica links the file into the cache of this disk. It does not download the chunk.

This helps in these cases:

  • A new disk from a snapshot on the same node starts warm.
  • Many disks from the same image on one node download each chunk one time.
  • A rollback finds its old chunks in the cache.

S3 stores the data one time for each disk. The node keeps it one time for each hash, while a cache has it.

8. Delete a disk

  1. Claim the head and mark it as deleted.
  2. List d/<disk>/ and delete everything with DeleteObjects. The snapshots of the disk go with it.
  3. Delete the head last.

If the node crashes, the marked head stays. mica disk ls shows the disk as "deleting", and the same command finishes the work.

11. Limits and open questions

  • Stores must support If-Match on PUT. AWS S3, Cloudflare R2 and MinIO support it. RustFS and Hetzner Object Storage are not checked yet. Garage does not support it, so mica drops Garage.
  • No restore point without a snapshot. After the next commit, the older version is gone.
  • A rollback deletes the newer snapshots. To keep a newer snapshot, make a new disk from it before the rollback.
  • A cache link shares one file between disks. Each disk budget counts the file. The real use of the node disk can be lower than the sum of the budgets.
  • Page entries grow from 32 to 40 bytes. zstd removes most of the repeated txg fields.
  • New format. mica keeps no compatibility with older data. Disks are created again.

12. Steps

  1. Probe (about 10 minutes). Test PUT with If-Match, DeleteObjects and CopyObject on RustFS and Hetzner. If If-Match is missing, stop and change this plan.
  2. Head as the lock. Owner, next and lost in the head, If-Match on each change. Remove the attached marker.
  3. New keys and the free rule. Transaction folders, entries with birth and hash, deletes after commit. Remove GC, the repair step and held copies.
  4. Node cache lookup by hash before each download.
  5. Snapshots: create, the merge rule, rollback, and new disk by copy.
  6. Delete a disk by folder.

How to check the result

  • Model test. Run random writes, commits, failed commits, snapshots, snapshot deletes and rollbacks against a memory store. After each step, check two facts. No reachable root points to a missing object. No object stays that no reachable root needs.
  • Crash tests. The current power-cut and daemon-kill tests on btrfs, XFS and ext4. Add kills during the deletes after a commit and during a snapshot delete.
  • Takeover test. Force a takeover while the old node uploads. The old commit must fail. No folder of the old node may stay after the detach of the new owner.
  • Transfer test. Checkpoint requests and time, cold reads, and a new disk from a 2 GiB snapshot on the same node and on another node. Compare with the current build.
