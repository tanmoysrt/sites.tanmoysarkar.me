CSEMA Go Rewrite Plan

The plan rewrites the CSEMA cybersecurity learning platform from Django + Next.js as one small Go binary (Echo, GORM, MariaDB 11.8) with an embedded Nuxt UI, plus a small agent on each lab host. It starts from what people actually use, and it keeps only what that use needs. This is the last big refactor, so every choice favours less code.

Status: plan only. No rewrite work has started. The work branch is refactor/go-rewrite (local). Measured on 31 Oct 2026 against a local copy of the production database.

1. Summary

The platform grew one feature at a time. It now has 45 Django apps, 308 tables and 669 API routes. Most of them are hidden, empty or unused. One production container runs 7 processes. A small change often touches 3 or 4 parts.

The rewrite keeps the features people use and makes each one as simple as possible. "Simple" is the main rule. When two designs work, we choose the one with fewer parts.

Logging everyone out at cutover is accepted. Users log in again once. Passwords keep working.

2. How we measured usage

Hidden pages and dead routes look the same as live ones in code, so we used 5 sources:

  1. Browser crawl. We signed in with 2 local test accounts (a learner on the highest plan and a staff user) and opened 61 pages with Claude in Chrome. A marker request before each page let us assign each backend call to its page.
  2. Static scan of the frontend. 388 API calls with their HTTP methods, including actions that a page load does not run.
  3. Route table. All Django URL patterns, matched against the frontend calls.
  4. Database. Row count and newest write time for each of the 265 models.
  5. Django admin log. Which models staff change by hand.
Production has no access logs (nginx and uvicorn logging are off). Row counts and last-write dates are the best usage signal we have.

6. Notes on parked modules

These modules each have their own runtime, UI or data model. They leave the core now and come back later. By Conway's law, a module comes back as a new package in the same repository and binary, unless a separate team owns it or its runtime must be isolated. Only then is it a separate service. SOC and network labs, for example, need their own runtime images on the lab hosts, but their APIs and UI still fit in the core.

8. Target architecture

  • HTTP. Echo serves /api/*, the embedded UI and /files/*. The binary gets its own TLS certificate (ACME, HTTP-01). No nginx.
  • Embedded UI. The nuxi generate output is embedded with go:embed. Unknown paths return 200.html.
  • Background work. Goroutine tickers handle event wave releases, monthly lab hours, session clean-up and newsletter batches. The mail outbox sends all mail.
  • No third-party calls from the browser. No analytics, no tracking pixels, no external fonts or icons.
  • Labs. The core talks to each lab host over SSH (section 15).
  • Other parts outside the binary: the code runner (Python sandbox, used by code exercises), SMTP and Razorpay.

10. Module design

The core has 9 feature packages and 3 platform packages. A new developer reads one package to understand one feature.

Boundaries follow the team (Conway's law)

A system copies the communication structure of the people who build it. In the last 6 months, one engineer made every commit in all 4 repositories. Today's split (separate backend, frontend, events app and orchestrator repositories, 7+ processes) makes that one person coordinate with themselves across 4 codebases for each feature. The new structure matches the real team:

  • One repository, one core binary. A second binary only where the runtime is on another machine: csema-lab-agent on lab hosts. The code runner sandbox stays separate for isolation.
  • Modules follow the people who ask for changes, not technical layers. Each area is a vertical slice: Go packages, their tables, a UI folder and an admin section. One person can own a whole area when the team grows. A CODEOWNERS file maps folders to owners at that point.

One package, one shape

internal/practice/
├── model.go       GORM structs for this package's tables (columns only)
├── practice.go    type Service struct{ db *gorm.DB } and the rules (plain methods)
├── http.go        Routes(g *echo.Group) and handlers: read input → call Service → write JSON
└── admin.go       admin handlers for this package's tables

Rules

  1. Each table has one owner package. Only the owner writes to it. Any package can read with SQL joins.
  2. XP has one write path: progress.Record(tx, …). It adds the progress row and updates users.xp in the same transaction. users.xp is the one column that a non-owner writes.
  3. Handlers are thin. No SQL and no rules in a handler.
  4. No interfaces unless there are 2 real implementations. No repository layer: the Service uses GORM directly.
  5. GORM, plainly. Models have columns only, with no relation fields, so GORM never saves related rows by surprise. Joins are written where they are needed. No hooks.
  6. Admin endpoints live in the owner package (admin.go), so the rules for a table stay in one place.
  7. One error type: server.Err(status, code, message). Clients get {"error":{"code","message","fields"}}.
  8. No hard-coded values. Infrastructure (domains, keys, SMTP, paths) comes from one Config struct, loaded from env and checked at start. Business values (lab hours per tier, ranks, onboarding roles, rate limits, feature switches) come from the settings table through server.Setting(key), cached and edited in admin. Content (paths, challenges, plans, coupons) is data. The UI has no URLs, prices, lists or constants: it reads them from the API.

Database connection

  • One *gorm.DB (gorm.io/driver/mysql) shared by all packages. Pool: at most 10 open connections, 5 idle, 5-minute lifetime. DSN: parseTime=true, loc=UTC, charset=utf8mb4.
  • GORM settings: SkipDefaultTransaction and PrepareStmt on, the slog logger, UTC NowFunc.
  • Transactions: db.Transaction(func(tx *gorm.DB) error { … }). Each request uses at most one.
  • Schema: for now, AutoMigrate from the models during development. Proper migration tooling comes later, before the first deploy. The deploy rule stays the same: a release only adds columns, tables or indexes (expand), and a later release removes old ones (contract).

11. Data model and ERD

The model has 23 tables. Four ideas make it small:

  1. One table for "done". progress stores every completion: a solved challenge, a machine flag, an unlocked hint, a finished activity, module or path, and an event solve. XP, leaderboards, streaks, the activity heatmap, badges and certificates all come from this one table.
  2. JSON for parts that belong to a parent. A quiz's questions, a code exercise's tests, a challenge's hints, files and lab spec are always read and saved together with their parent and are never queried on their own. The rule: if we never query it alone, it is a JSON column. The API never sends answers, flag hashes or tests to the browser.
  3. Status columns, not more tables. Team invites and join requests are rows in team_members with status = invited or requested. Event allow-lists are rows in event_entries with status = allowed. Contact, ambassador, waitlist, event-support and challenge-report forms are rows in form_entries. Newsletter opt-in is one row in subscribers for each email.
  4. Reuse. Event challenges are normal challenges linked to an event. They stay unpublished in Practice until staff publish them after the event. Event teams are normal teams with event_id set and a join code. Event solves and hints are progress rows with event_id set.

12. API

Conventions

  • Prefix /api. Plural nouns. Content uses slugs in URLs (/api/challenges/sql-101). Things that users create use ids.
  • Auth: the csema_session cookie (HttpOnly, Secure, SameSite=Lax), or Authorization: Bearer <token>.
  • Lists: ?cursor=&limit= (default 50, maximum 200). The response is {"items":[…],"next":"…"}.
  • Writes return the changed object. Errors use the one error shape.
  • One call for each screen. GET /api/me gives the user, plan, offer banner and the settings the UI needs. GET /api/home gives the whole Home page.

13. Sessions and compatibility

  • Sessions. A random 32-byte token. Only its SHA-256 hash is stored in sessions. Login deletes the user's other sessions (the current one-session rule). Sessions last 30 days and slide on use.
  • Passwords. Django hashes (pbkdf2_sha256$…) are checked with x/crypto/pbkdf2. On the next login they are rehashed with argon2id.
  • Google and GitHub. A user is matched by verified email, as today. No extra table.
  • Flags. Stored hashes are HMAC-SHA256 with the old secret key as pepper. The same value becomes the FLAG_PEPPER setting.
  • At cutover everyone logs in once more. Passwords keep working. We do not bridge the old JWTs.
  • Kept as is: only the Razorpay webhook and the OAuth callback URLs. Old email links and /media/… URLs are not kept. Files are served at /files/….

15. Machine lab hosting

Machine labs, red-team labs, shell labs and (later) SOC and exam labs run as containers on shared lab hosts. A small Go agent, csema-lab-agent, runs on each host. The core's labs package places sessions and controls the agents.

Why we change it

Measured (Sep to Oct 2026)Value
Lab sessions218 sessions, 21 accounts
Peak concurrent sessions2
Real play timeabout 17 h
Cloud VMs created since 3 Aug61, about 2,263 VM-hours
Failed starts15% (32 of 218), all from network hops between services
Typical lab memory128–256 MB

The VM-hours are about 100 times the play time. The cost comes from warm and short-lived VMs, not from players.

Design

  • Add a host by hand. You create a Debian 12 machine and add the core's SSH key. In admin you click Add host. The core connects once as root, installs Docker and nftables, creates a restricted user (socket forwarding only), uploads the agent and starts it with systemd.
  • Control link. The agent serves HTTP only on a Unix socket. The core reaches the socket through one SSH connection for each host. There is no public control port and no API key.
  • Desired state. The core sends the full list of sessions for the host. The agent compares it with the running containers, fixes any difference and reports back. The agent also stops sessions at their deadline by itself.
  • Placement. The host with the most free memory. Labs share hosts.
  • Lab hours. Each tier's monthly allowance is a setting. Hours left = allowance minus this month's seconds_used. No credit table.
  • Isolation now. Standard containers with memory, CPU and PID limits. nftables rules stop labs from reaching the internet, the host or other sessions.
  • One release. Core and agent have one version. A core upgrade pushes the agent to every host.

Network

Each session gets its own Docker network, a /27 from 198.18.0.0/17, which is the pool that CLAUDE.md already pins. There is no VPN.

How a player reaches a lab

  1. SSH gateway (main path). The agent has a built-in SSH server on port 22. The host's own admin SSH moves to port 2222. The UI shows one command and a password for each session: 
    ssh s-1234@ssh.lab.<base>                       shell in the attack box
ssh -L 8080:198.18.3.5:80 s-1234@ssh.lab.<base>   reach a target port from your laptop
ssh -D 1080 s-1234@ssh.lab.<base>                SOCKS proxy for a browser or proxychains
ssh -R 4444:localhost:4444 s-1234@ssh.lab.<base> catch a reverse shell on your laptop
ssh -J s-1234@ssh.lab.<base> root@198.18.3.5      jump to a target's own SSH
    The gateway allows forwards only into the user's own session network. A reverse forward (-R) listens on the session network's gateway address, so a target can connect back. Players need nothing but ssh, and it works where UDP is blocked. The limit: no raw UDP or ICMP from the player's own machine. Those tools run in the attack box.
  2. Web challenges: https://<token>.lab.<base>. Wildcard DNS points at the host. The agent gets the wildcard certificate (ACME DNS-01) itself.
  3. Terminal in the UI: browser → core (checks the user) → SSH tunnel → agent → docker exec with a PTY in the attack box. No ttyd container.

Agent API (Unix socket)

GET  /health                  version, Docker status
PUT  /state                   desired sessions and images (full list, with SSH passwords)
GET  /state                   actual sessions, IPs, ports, errors, memory and network use
GET  /exec/{session}          WebSocket: interactive PTY

16. Deploy and size budget

  1. Copy the new binary and run systemctl reload csema.
  2. The running process starts the new binary and passes it the listening socket (tableflip).
  3. The new process applies schema changes (expand only) and reports ready.
  4. The old process stops accepting, finishes requests (30-second limit), closes UI terminals with code 1012 and exits. Clients reconnect. Lab SSH sessions are not affected: they end at the agent, not the core.
  5. If the new process fails its health check, it exits and the old one keeps serving.
BudgetLimitHow
Binary< 50 MB (target 30)CGO_ENABLED=0 -trimpath -ldflags "-s -w". CI fails above the limit.
Memory at idle< 50 MB (target 30)GOMEMLIMIT=48MiB, 10 DB connections, no big caches.
Not in the binary—Lesson presentations, uploads and large images, in /var/lib/csema/files.
