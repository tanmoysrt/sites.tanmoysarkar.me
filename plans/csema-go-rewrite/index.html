CSEMA Go Rewrite Plan

The plan moves the CSEMA cybersecurity learning platform from Django + Next.js to one Go binary (Echo, sqlc, MariaDB) with the UI embedded in it. It starts with what the product actually uses today, maps that to APIs and tables, and then gives the build phases, the cutover and the checks.

Status: plan only. No rewrite work has started. The work branch is refactor/go-rewrite (local, both repositories). Measured on 31 Oct 2026 against a local copy of the production database.

1. Why we rewrite

The platform grew one feature at a time. Each feature added a Django app, a set of routes and a set of pages. Many of those features are now hidden, empty or replaced, but their code, tables and background jobs still run.

The result is hard to change and expensive to run. One production container runs nginx, uvicorn with 4 workers, 2 Celery workers, Celery beat and Redis. The frontend is a separate Next.js deployment with server routes. A small change often touches 3 or 4 of these parts.

The goal is one small program that does the same job for the features people use:

  • One Go binary. It serves the API, the WebSockets, the background jobs and the UI.
  • MariaDB is the only stateful dependency. Redis, Celery and Channels go away.
  • Binary size is less than 50 MB, and a deploy causes no downtime.
  • A smaller, clearer UI that is built from the same component set on every page.

2. How we measured usage

We did not trust the code alone. Hidden pages and dead routes look the same as live ones in code. We used 5 sources and compared them.

  1. Browser crawl. We signed in with 2 local test accounts, a learner with the highest plan and a staff account. We opened 61 pages with Claude in Chrome. A marker request before each page let us read the backend request log and assign each API call to the page that made it.
  2. Static scan of the frontend. We extracted 388 API calls from the TypeScript source, with their HTTP methods. This also finds actions that a page load does not run, for example "submit flag".
  3. Route table. We dumped all Django URL patterns and matched each frontend call to a route.
  4. Database. For each of the 265 models we counted rows and found the newest write time.
  5. Django admin log. This shows which models staff change by hand.
Production has nginx and uvicorn access logs turned off. Because of this we have no real traffic counts per endpoint. Row counts and last-write dates are the best usage signal we have. Phase 0 turns on a sampled access log for 2 weeks to confirm the decisions below.

Other facts that change the plan:

  • The real product data is small. Without the marketing decision table, the database is about 90 MB.
  • Large static files live in git: lesson presentations (323 MB), challenge artwork (51 MB), marketing images (47 MB), frontend images (94 MB). User uploads are 1.6 GB. None of these can go into a 50 MB binary.
  • The code uses no Postgres-only features (no ArrayField, no django.contrib.postgres, no DISTINCT ON). It has 76 JSONField columns and 18 files with raw SQL. MariaDB is a safe target.
  • A standalone events app (separate repository) signs users in with a short-lived SSO token and calls the /api/events/ routes. Its API contract must stay stable, or we rewrite that app too.
  • The red-team orchestrator (separate repository) calls an internal API (/internal/redteam/…, 17 routes) with a service key. This contract must stay stable.

6. Notes on parked modules

These modules do not fit the core platform. Each one has its own runtime, its own UI style or its own data model. They leave the core UI and API now. Later, each one becomes a separate microservice that uses the core platform through a small, fixed interface.

Interface that every future microservice uses

  • Identity. The core issues JWTs. It publishes its public key at /.well-known/jwks.json (EdDSA). A microservice checks tokens itself and does not call the core on each request.
  • Entitlements. GET /internal/v1/users/{id}/entitlements returns the plan tier and the active date window.
  • Progress and points. POST /internal/v1/achievements records XP, a solve or a badge, and is idempotent by key. The core stays the only owner of points and leaderboards.
  • Hosted labs. Microservices that need a VM use the core machines API (lab sessions on pool VMs), as SOC Arena and shell labs do today.
  • UI. Each microservice serves its own UI under its own path or subdomain. The core UI only links to it.

7. Target architecture

The binary has these parts:

  • HTTP API. Echo v4 routes under /api/v1. Handlers are thin. Each domain package has a service layer that calls sqlc queries.
  • Embedded UI. The built SPA (single-page app) is embedded with go:embed and served with pre-compressed Brotli and gzip files. Unknown paths return index.html.
  • WebSocket hub. One in-process hub with topics (user:{id}, event:{id}, team:{id}, admin). It replaces Channels and Redis. The database stays the source of truth, so a client resyncs over REST after it reconnects.
  • Job runner. A jobs table with a lease column (locked_until). Workers claim jobs with SELECT … FOR UPDATE SKIP LOCKED (MariaDB 10.6+). A small cron loop adds the periodic jobs. It replaces Celery and beat.
  • Files. A storage interface with two drivers: local disk (default) and S3-compatible. Uploads, lesson presentations and challenge files use it. The binary serves files with long cache headers and ETags.
  • Cache and rate limits. In-process, with a size limit (for example otter or a small LRU). No Redis.

External services stay outside the binary: the code runner (Python sandbox), the red-team orchestrator, SMTP, Razorpay, and, later, the parked microservices.

Main libraries: Echo v4, sqlc (MySQL engine), go-sql-driver/mysql, goose (migrations), golang-jwt/jwt/v5, coder/websocket, cloudflare/tableflip, log/slog. We add a dependency only when the standard library cannot do the job.

Schema rules for MariaDB 11.4 LTS:

  • utf8mb4 and utf8mb4_unicode_520_ci everywhere, InnoDB, strict SQL mode.
  • Keep the current integer primary keys, so that links, JWT user_id claims and orchestrator references stay valid.
  • All times are DATETIME(6) in UTC. Booleans are TINYINT(1). JSON is JSON with a CHECK (JSON_VALID(…)) constraint, mapped to json.RawMessage in sqlc.
  • Every foreign key has an index. Leaderboard and feed queries get covering indexes, checked with EXPLAIN in CI.
  • sqlc's MySQL engine does not parse INSERT … RETURNING. We use LastInsertId.

10. API design

We rewrite the UI in the same release, so we can redesign the learner API. We keep the old shape only where a client outside this repository depends on it (see section 11).

Rules

  • One prefix: /api/v1. Plural nouns, kebab-case, no api_ prefixes and no /api/…/api/… nesting.
  • List endpoints use cursor pagination and a hard limit (default 50, maximum 200). Today some lists return every row, for example /api/challenges/.
  • One error shape: {"error":{"code":"…","message":"…","fields":{…}}}.
  • The API contract is an OpenAPI file in the repository. The TypeScript client is generated from it, so the frontend and backend cannot drift apart.

Fewer calls for each page

Every page load today makes 7 "shell" calls: branding, notifications, profile, tracking, current offer, event collaborations and ambassador status. Home adds about 15 more. The new API gives each screen one call:

GET /api/v1/practice?tab=…    one tab, paged, with filters

11. Compatibility rules

We rewrite everything in one release. To make that safe, the cutover must not log anyone out, break a link or change a stored secret.

  • Passwords. Django stores pbkdf2_sha256$<iterations>$<salt>$<hash>. Go checks this format with x/crypto/pbkdf2. On the next successful login, it rehashes the password to argon2id.
  • Sessions. Today's tokens are HS256 JWTs (60-minute access, 3-day refresh, user_id claim). For 3 days after cutover, Go also accepts these tokens and exchanges them for new ones. After that, it accepts only its own EdDSA tokens. The single-session rule keeps working through user_sessions.
  • Flags. Stored flag hashes are HMAC-SHA256 with the old secret key as the pepper. Go uses the same pepper value as a separate config key (FLAG_PEPPER). It does not reuse it as a signing key.
  • Frozen contracts. These keep their exact paths and payloads: the orchestrator internal API (17 routes), the events app API (until we decide on that app), Razorpay and email-provider webhooks, OAuth callback URLs, /unsubscribe/… and /r/… links in sent emails, /media/… URLs and the events SSO handoff.
  • IDs. All primary keys stay the same.

12. UI plan

The current UI has a good base: a dark theme, a clear 6-item sidebar and dense, readable cards. Its problems are structure and weight, not style.

Problems we found

  • Too many requests for each page, as section 10 describes.
  • Dead, hidden and redirect-only pages still ship, and a duplicate route folder exists (exams/%5Bid%5D/take next to exams/[id]/take).
  • The admin "Tools" page is a mix of 9 unrelated tabs: jobs, study materials, blogs, interviews, battleground, exam upload, learning upload, student skills and mailing.
  • The API layer is split into client.ts, client-part2.ts, client-part3.ts and client-part4.ts plus 30 domain files, with hand-written types.
  • Next.js server routes act as proxies (AI simulation, forensics, GNS3, web proxy, file proxy). They cannot exist in a static embedded UI.
  • Heavy or duplicate libraries: 2 chart libraries (ApexCharts and Recharts), jQuery, 2 globe libraries, Genkit (AI SDK in the browser bundle), a page-flip library and html2canvas.
  • The notifications WebSocket reconnects in a loop when the channel layer times out.

New UI

  • Stack. Vite + React 19 + TanStack Router (typed routes) + TanStack Query. We keep Tailwind and the Radix/shadcn components we already use, and move them into one web/src/ui folder with design tokens.
  • Public pages. Landing, pricing, news and legal pages are pre-rendered to static HTML at build time for SEO. They are part of the same embedded build.
  • Information architecture. Home · Learn · Practice (Challenges, Machines) · Compete (Leaderboard, Teams) · Profile. Events stays an external link. Teams moves under Compete. Seasons and SOC leave the Practice tabs until their services return.
  • Admin. Admin gets its own area with clear sections: Users, Content (paths, modules, challenges, files), Machines, Events, Billing (plans, payments, coupons), Moderation, System. These sections replace the Django admin for the 8 models staff edit, and the "Tools" tab mix.
  • One page pattern. Each page has a header (title, one primary action), a filter bar, the content, and empty, loading and error states. A review checklist enforces the pattern.
  • Budget. Initial JavaScript is less than 200 KB gzip. Each route is a separate chunk. Lesson presentations load from file storage in an iframe, not from the bundle.

13. Zero-downtime deploy and size budget

  1. The deploy copies the new binary and sends SIGHUP (systemctl reload csema).
  2. The running process starts the new binary and passes it the listening socket (tableflip).
  3. The new process runs pending migrations, then opens the database pool, warms caches and reports "ready".
  4. The old process stops accepting connections and lets in-flight HTTP requests finish (30-second limit). It closes WebSockets with code 1012 ("service restart"). Clients reconnect to the new process and resync.
  5. If the new process fails its health check, it exits. The old process keeps serving.

Migrations use the expand/contract rule. A release only adds columns, tables and indexes. The release after that removes old ones. So the old binary always works with the new schema during the handover. Jobs use database leases, so two processes can overlap safely.

The binary runs under systemd on the host. A container is optional. MariaDB runs as its own service (managed or on the same host). One instance is enough for the current load. Section 9's design (DB leases, no in-memory source of truth) leaves room for 2 instances later.

14. Phases and steps

We do the rewrite as one project with one cutover. The phases set the build order. Phase 4 (UI) starts when Phase 1 has the API contract, and then runs in parallel with Phases 2 and 3.

Phase 0. Prepare

Depends on: nothing · Exit: the new layout is in place, the baseline is recorded, and the scope is approved

  1. Approve the keep, park and drop list (section 5) and answer the open questions (section 17).
  2. Turn on a sampled access log in production for 2 weeks. Confirm that the parked and dropped routes get no traffic.
  3. Restructure the repository on refactor/go-rewrite. Move Django to legacy/django/, lab runtimes and packs to labs/, and course content and artwork to content/. Django must still start from the new path.
  4. Record golden fixtures. A script calls each of the 213 used core routes against the local copy and saves the JSON responses. These are the reference for parity checks.
  5. Write docs/api-map.csv with all 213 routes and the new route for each one.
  6. Archive the parked and dropped data. Export each table to compressed CSV with a checksum file.

Phase 1. Foundation

Depends on: Phase 0 · Exit: a user can log in to the Go binary with an old password and an old token

  1. Go module skeleton, config (env + file), structured logging, health and readiness endpoints, graceful shutdown with tableflip.
  2. MariaDB 11.4 in Docker for local development. goose migrations and sqlc config. A CI job runs sqlc vet, the migrations and the tests.
  3. Identity domain: login (PBKDF2 check and argon2id rehash), JWT (EdDSA plus the HS256 bridge), refresh, OTP, email verification, password reset, Google and GitHub OAuth, single session, the SSO handoff for the events app.
  4. Platform parts: job runner, email outbox (SMTP), file storage interface, WebSocket hub, rate limiter, audit log.
  5. The csema import-pg tool for identity tables, with row-count and checksum checks.
  6. The OpenAPI file for /api/v1, with the TypeScript client generated from it.
  7. A size and memory check in CI.

Phase 2. Core learner domains

Depends on: Phase 1 · Exit: the parity harness passes for practice, machines, learning and compete

  1. Practice: catalog, filters, hints, flag submit (HMAC pepper), solves, badges, writeups, feedback.
  2. Machines: credits, plans, sessions, start, stop and heartbeat, machine flags, certificates, and the orchestrator internal API (frozen contract).
  3. Learning: paths, modules, quizzes, progress, certificates. Coding exercises call the code runner over HTTP. Shell practicals use lab sessions.
  4. The content import command. Convert the Python seed courses into content/courses/*. The check: importing into an empty database gives the same rows as today.
  5. Compete: the leaderboard and teams (invites, requests, announcements).
  6. Notifications over REST and WebSocket.
  7. Extend import-pg to these domains.

Phase 3. Rest of the core

Depends on: Phase 1 (it can overlap with Phase 2) · Exit: every row in api-map.csv has a handler or a "removed" reason

  1. Billing: plans, Razorpay orders and subscriptions, webhook signature checks, coupons, offers, bills. Use Razorpay test mode only, never the live keys.
  2. Events: a one-to-one port of the routes that the events app uses, plus the event, spectator, team-chat and admin-ops WebSockets, and the wave-unlock job.
  3. Onboarding survey, blog, ambassador, waitlist, contact.
  4. Admin APIs for the admin sections in section 12. These replace the Django admin.
  5. Scheduled jobs: wave unlocks, lifecycle emails, idle-connection cleanup (no longer needed) and practical-exam result sync (if exams stay).
  6. The /unsubscribe/… and /r/… handlers for old emails.

Phase 4. New UI (in parallel from Phase 1)

Depends on: the Phase 1 OpenAPI contract · Exit: all learner and admin flows pass end-to-end tests against the Go binary

  1. Set up Vite, React, TanStack Router and Query, and Tailwind tokens. Move the shared components into web/src/ui.
  2. Build the app shell and /me/bootstrap. Then, in order: Home, Learn (path, lesson player, quiz, code, shell), Practice (catalog, challenge, machine), Compete, Profile, Billing.
  3. Build the admin area (section 12).
  4. Pre-render the public pages (landing, pricing, news, legal).
  5. Remove the dead pages, redirects and libraries listed in section 12.
  6. Embed web/dist in the binary with pre-compressed files.

Phase 5. Migration rehearsal and parity

Depends on: Phases 2, 3 and 4 · Exit: 3 clean rehearsals in a row and an approved parity report

  1. Take a fresh production snapshot. Run import-pg into an empty MariaDB and record the time (target: under 10 minutes).
  2. Check the row count and a column checksum for each table, plus spot checks on users, points, solves and payments.
  3. Parity harness: replay the golden fixtures and recorded flows against Django and Go on the same snapshot, then compare the normalized responses.
  4. Run end-to-end tests (Playwright) on the main flows: sign up, onboard, lesson, quiz, flag, start machine, team, checkout (test mode), admin edit.
  5. Load test with the existing loadtest/ scenarios. Compare p95 latency and memory with today.

Phase 6. Cutover

Depends on: Phase 5 · Exit: Go serves all traffic for 7 days without a rollback

  1. Announce a short read-only window (target: under 15 minutes). The window is necessary because the data moves between database engines.
  2. Put Django in read-only mode. Take the final snapshot, run import-pg, and run the checks.
  3. Point DNS or the proxy at the Go binary. Watch errors, logins and payments.
  4. Rollback plan: keep Django and Postgres untouched for 7 days. A rollback switches the proxy back. Writes made in Go after cutover are replayed with a small export tool.
  5. After 7 days, delete legacy/django/ and turn off the old container, Redis and Celery.

Phase 7. Parked services (later)

Depends on: Phase 6 · Exit: each service is live behind the interface in section 6

The order is up to the product. A suggested order: Zero Hour (it needs only the catalog and achievements), then SOC Arena, Network labs, Forensics, and the Growth engine.

15. How we check success

CheckPass condition
Data migrationRow counts and checksums match for every migrated table. 0 orphan foreign keys.
Login continuityA sample of old password hashes and live tokens works after cutover. Logout rate does not spike.
Flag continuityEvery stored flag hash in a sample verifies with the known flag.
API parityThe golden fixtures and recorded flows match after normalization (ordering, timestamps, renamed fields).
Frozen contractsThe orchestrator, the events app and the webhooks pass their contract tests unchanged.
Performancep95 latency is the same or better than today for the 20 busiest routes. Idle RSS is less than 50 MB.
SizeThe binary is less than 50 MB in CI.
Zero downtimeA deploy during a load test gives 0 failed HTTP requests, and all WebSockets reconnect within 5 seconds.
Code sizeThe Go core is under 40k lines (excluding generated code), against 172k lines of Python today.

16. Risks

RiskEffectMitigation
A hidden dependency on a parked moduleA core page breaksThe 2-week access log in Phase 0, plus the parity harness.
The events app breaksLive events failFrozen contract and contract tests. Do not cut over during an event.
Data differences between the engines (time zones, JSON, collation)Wrong dataStore UTC only, validate JSON, choose the collation on purpose, and run 3 rehearsals.
One big release is lateTwo systems run for longerFreeze new features in Django during the rewrite. Phase 0 limits the scope with data, and Phase 4 runs in parallel.
The Django admin is goneStaff cannot edit contentAdmin sections cover the 8 models in the admin log, and the content importer covers bulk edits.
Single instanceA host failure stops the serviceThe same risk exists today. Backups and a restore runbook. DB leases allow a second instance later.

17. Open questions

  1. Events app. Do we keep its API contract and leave the app as it is, or do we rebuild events inside the new UI (and later retire that app)?
  2. Exams. Do we keep the results read-only in the profile, as proposed, or do we also need registration and the practical-exam integration at cutover?
  3. Bug bounty, academic, corporate. They have UI but 0 rows. Is it correct to drop them?
  4. Growth engine. Can it stop at cutover? Or must the Python version keep running against a copy of the data until it is rebuilt?
  5. "< 50 MB". Is this the binary size, the memory, or both? The plan targets both.
  6. Files. Local disk or object storage for uploads and lesson presentations?
  7. MariaDB hosting. Managed or self-hosted, and in which region relative to the app host?
